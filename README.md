# 계약 목록 (pclm)

나라장터 업무 화면을 브라우저 확장으로 수집하거나 ERP JSON 을 가져와 SQLite에 쌓고, 문서 자동
생성기가 읽을 뷰로 내놓는다. 웹ERP의 DB에 닿을 수 없어 조달 자료가 화면과 파일로만 흩어져 있는
자리를 위한 것이다.

```
나라장터 화면 ─(확장)─┐
ERP JSON ─────────────┼──▶ SQLite ──▶ 뷰 ──▶ 문서 자동 생성기
계획 엑셀 (동결) ────┘       ▲
                              └── 손으로 채우는 열 (진행상태·담당·메모…)
```

현재 앱의 수집 입구는 확장과 ERP JSON이며 계획 엑셀 경로는 코드를 보존한 채 동결했다.
PDF 를 읽던 입구는 걷었다(ADR-028) — 확장이 같은 자료를
화면에서 더 정확히 가져오게 되어 두 입구를 유지할 값이 없어졌다.

## ERP 통합 수집

접수·공고·계약 JSON을 확장 수집과 같은 매핑·변경 검토 경로로 저장한다.
왼쪽 메뉴 **나라장터** 화면의 「고급」에서 매핑 편집, 샘플 검증, 버전 활성화, 파일 가져오기를 제공한다.
Chrome/Edge 확장은 나라장터 탭을 앱의 지금 보는 화면에 이어 주는 다리이고, 가져오기는 앱이 같은 활성 매핑으로 한다(ADR-042).
단일 `계약목록.exe`의 **나라장터 → 확장 준비**에서 설치 파일과 앱 연결을 준비한다.
브라우저에서 개발자 모드를 켜고 안내된 폴더를 로드하면 된다. 별도 확장 다운로드나 등록 스크립트는 필요하지 않다.
손으로 로드하는 것은 처음 한 번뿐이다. exe 를 새 판으로 바꾸거나 옮기면 앱을 켤 때 확장 파일과 연결을 고치고,
확장은 나라장터 화면을 열 때 새 판으로 스스로 다시 불러온다.
브라우저가 켜져 있으면 확장이 옛 exe 를 쥐고 있어 덮어쓰기가 막힌다 — 옛 exe 의 이름을 `계약목록.old.exe` 로 바꾼 뒤
새 exe 를 놓으면 된다. 확장은 저절로 새 exe 에 다시 붙고, 옛 것은 다음에 앱을 켤 때 저절로 치운다(ADR-035).
나라장터 업무 화면의 **현재 화면 엑셀로 내보내기**는 앱 연결 없이 필드·표를 `.xlsx`로 저장한다.
화면에 로딩된 범위만 포함하며 원본 ID와 수집 정보를 함께 남긴다.
전체 ERP 화면 수집은 문서 번호로 화면을 가리고, 읽힌 필드·표만 검토해 담는다.
설치와 검토 절차는 [통합 수집 안내](docs/erp/integration.md)를 참고한다.

## 쓰는 법

계획·현황은 현재 개발을 동결하여 앱 탐색과 설정의 계획 엑셀 입구에서 숨겼다.
기존 데이터·화면·가져오기·CLI 코드는 보존한다. 다시 제공할 때는
`frontend/src/features.ts`의 `PLANNING_ENABLED`와 관련 UI 테스트를 함께 검토한다.

자료 목록 도구 모음의 **열 관리**에서 사용자 열을 만든다. `이름 : 꼴` 은 사람이 채우는 입력열(글·고르기·날짜·숫자),
`이름 = 식` 은 식이 채우는 가공열이다. 가공열은 품목·이 행의 열·연결 문서에서 시작해 단계를 잇는 흐름식이고,
**값 흐름 보표**가 표본 문서 셋에서 단계마다 그 시점의 값을 보인다. 흐름식은 글로도 고칠 수 있고, 흐름식으로 적을 수
없는 것은 계약면 뷰만 읽는 SQL 로 꺼내 직접 고친다(되돌아오지 않는다). 연산자를 눌러 가공열을 **값으로 굳히면**
계열마다 최신 차수의 값이 입력값으로 쓰인다 — 쓸 칸 수를 먼저 센다. 저장된 식이 깨지면 그 열만 빈 값으로 나가고
열 관리에 까닭이 보인다. 설계는 [열 관리 재설계](docs/column-management.md)에 있다.
가공열은 표·엑셀과 외부 공개 뷰에 함께 나타난다. 문서 생성기는 일반 열처럼 읽으며,
이름 변경에 대응할 식별자 연결 규칙은 [데이터셋 규약](docs/dataset-contract.md#사용자-정의-가공열-스키마-22)에 있다.

서식 하나를 위한 필드 묶음은 사이드바의 **맞춤 뷰**에서 짓는다. 한 줄은 **조달 건**(`v_통합` 과 같은 사슬)이라 기준을 고르지
않는다 — 접수·공고·계약의 필드를 지금 표본의 값을 보며 섞어 담으면 같은 건끼리 앱이 잇고, 가공이 필요한 필드만 가공열과 같은
편집기로 다듬는다(`공고.공고명` 꼴). 사람이 정하는 것은 계약이 여럿인 건을 계약마다 한 줄로 둘지 한 줄로 모을지 하나다.
화면은 필드 목록과 미리보기를 한 목록으로 보인다. 뷰는 `u_<이름>` 으로 서고 문서 생성기의 시트 목록에 그대로 뜬다 — 면 뷰
(`v_공고` 등)를 보조열로 넓히지 않는다. 설계는 [맞춤 뷰](docs/user-views.md)에, 소비 규칙은
[데이터셋 규약](docs/dataset-contract.md#맞춤-뷰-스키마-24)에 있다.

저장한 보기는 **설정 → 보기 구성**에서 골라 JSON으로 내보내고 다른 작업자료에 가져올 수 있다.
보기의 이름·열 차례·값 흐름 또는 SQL·계약 모으기 방식과 필요한 맞춤 열 정의를 옮기며 조달 자료와 입력값은 담지 않는다.
가져오기 전에 이름·의존 열·충돌·식 오류를 확인한다. 같은 보기 이름은 복사본으로 추가하고 같은 맞춤 열 정의는 재사용한다.
정의가 다른 맞춤 열이 있으면 전체를 취소하므로 원본에서 열 이름을 바꿔 다시 내보낸다.
SQL의 간접 참조가 있으면 맞춤 열 정의 전체가 포함된다. [구성 파일 규약](docs/dataset-contract.md#보기-구성-json-파일)에 꼴과 검증 규칙을 적었다.

```
pclm plan [엑셀]                 연간 조달계획을 읽어 넣는다 (조달요구번호 기준 업서트)
                                 인자가 없으면 지난번에 고른 엑셀을 다시 읽는다
pclm status                      쌓인 상태 · 차수
pclm 현황                        계획을 분모로 본 진행 (지금 지표는 가상이다)
  --아님 <계약번호> <공고번호>   이 짝은 아니다 (다시 후보로 오르지 않는다)
  --해제 <계약번호>              링크를 푼다
  --명시                         ERP 명시 참조로만 다시 잇는다 (있던 링크는 둔다)
pclm set  [키 열 값]             손으로 채우는 값 (인자 없으면 열 목록)
pclm fix  <키> <열> [값]         수집한 값을 고친다 (값 없으면 원래대로)
pclm delete <키>                 레코드를 지운다 (무엇이 사라지는지 세어 보인다)
  --계열                         그 본번호의 전 차수를 지운다
  --예                           실제로 지운다 (없으면 세어 보이기만)
pclm export [경로]               계약면을 엑셀로 (그 시점의 사진)
pclm submit [경로]               내 자료 한 벌을 제출본 파일로 뜬다 (.pclm)
  --이름 <이름>                  제출본 파일 이름에 쓸 내 이름을 정해 둔다
pclm merge <폴더|파일…>          제출본을 모아 취합본 하나로 짓는다 (매번 처음부터)
  --out <경로>                   취합본을 놓을 자리 (기본은 지금 폴더)
  --home <폴더>                  다른 홈의 작업자료를 연다 (기본은 창과 같은 홈)
  --file <파일>                  다른 자료를 열어 본다 — status · 현황 · export 만, 읽기 전용
```

명령줄은 **배포물에 들어가지 않는다**(창만 나간다). 여기서는 `./run.ps1 -Cli status` 로 돌린다.

자료의 정체는 접수번호·공고번호·계약번호와 차수다. 같은 화면을 몇 번 수집해도 행이 늘지 않는다.

`plan` 은 **동결한 계획 가져오기 코드의 CLI 입구**다 — 확장·ERP JSON 은 접수·공고·계약을, 이쪽은
엑셀에서 계획을 들인다. 서식은 조달계획 양식에 고정되어 있어 짚어 줄 것이 없다 — 첫 줄이 그 양식의 머리글이면 그대로
읽힌다. 필수 둘(조달요구번호·담당자)이 없으면 **한 줄도 넣지 않는다** — 절반만 들어가면 그 뒤로
무엇이 덜 왔는지 아무도 모른다. 한 번 고른 엑셀은 설정에 남아 다음부터는 `pclm plan` 만 쳐도
같은 파일을 다시 읽는다. 계획변경은 차수를 올리지 않고 **같은 조달요구번호를
덮어쓴다**(ADR-023).

`set` 과 `fix` 는 담기는 자리가 다르다. `set` 은 **사람이 세운 열**(진행상태·메모)이고,
`fix` 는 **수집한 칸의 정정**이다. 정정은 수집한 표를 건드리지 않고 위에 얹히므로 언제든
원래 값으로 되돌아간다. 다시 수집할 때 정정과 부딪히면 어느 쪽을 둘지 사람이 고른다(ADR-020).

변경공고·변경계약은 차수가 오른 별개의 행으로 쌓이고, 뷰는 최신 차수만 낸다.

**취소와 재공고는 차수로 잡히지 않는다.** 공고가 취소되면 같은 본번호에 차수가 하나 올라
`실공고(취소공고)` 가 앉지만, 그 뒤에 다시 나가는 재공고는 **본번호가 갈린다** —
`R26BK09011054` 가 취소되고 `R26BK09012082` 로 다시 나가는 식이다. 둘을 잇는 단서는 공고의
「관련공고」 칸 하나뿐이라, 담긴 그대로 `v_공고` 의 `관련공고` 로 낸다(ADR-025).

담는 데서 멈춘다. 취소공고도 여느 공고처럼 줄을 갖고, 재공고는 별개의 조달 건으로 선다 —
어느 쪽이 살아 있는지는 그 칸을 보는 사람이 정한다(ADR-016). 재공고와 원공고는 한 건으로
묶여(ADR-026) 잇기 후보에 한 줄로 서고, 거기서도 잇는 것은 명시 참조나 사람이다(ADR-029).

## 여럿이 쓸 때 — 제출과 취합

담당자마다 자기 자료가 따로 쌓인다. 그것을 모으는 길이 **제출**과 **취합**이다(ADR-024).

```
pclm submit               내 자료 한 벌을 제출본 파일로 뜬다 → 제출_홍길동_20260729.pclm
pclm merge <받은폴더>     받은 제출본들을 모아 한 벌로 짓는다 → 취합_20260729.pclm
```

같은 일을 창의 **설정**에서도 한다. 창은 폴더를 묻고, 명령줄이 찍는 그 보고를 취합본 옆에
`취합_날짜.txt` 로 남긴다 — 창에는 알림 한 줄만 서기 때문이다.

**공유 DB 하나를 두지 않는 까닭.** WAL 은 네트워크 파일시스템에서 돌지 않고, 계약면이 "쓰는
주체는 하나" 라고 약속했다. 각자 자기 자리에 쓰고, 모으는 것은 사본이다.

**취합본을 고쳐 쓰지 않고 매번 처음부터 짓는 까닭.** 이 저장소는 묘비를 두지 않는다 — 누가
자기 자료에서 지운 건은 다음 취합본에 그냥 없어야 하는데, 고쳐 쓰면 지운 것이 영영 남는다.
그래서 취합본은 자료가 아니라 **결과물**이다. 사람이 손보는 자리로 쓰지 않는다.

**받는 것은 파일 이름이 아니라 파일이 밝힌 역할로 고른다**(ADR-024 개정·ADR-031). 파일마다
작업자료·제출본·취합본·백업 중 무엇인지 적혀 있어, 이름을 바꿔도 취합본이나 백업은 입력에서
빠지고 까닭이 한 줄씩 남는다. 받은 파일은 열지 않고 읽기 전용으로 한 벌 떠서 그 사본을 읽는다.
제출본·취합본은 뜰 때마다 새 신원을 받고, 고른 자리에 작업자료가 있으면 덮지 않는다.

**같은 건이 갈리면 기계가 판정하지 않는다**(ADR-016 의 결). 늦게 적힌 것을 싣되 **무엇을
밀어냈는지 한 줄씩 알린다** — 누가 옳은지는 원본을 본 두 사람이 안다. 딸린 품목은 부모를 따라
통째로 가고, 사람이 세운 열은 합집합이다. 제출한 사람의 설정(이름·계획 엑셀 자리)은
넘어오지 않는다. `--이름` 으로 정하는 이름의 쓰임도 **제출본 파일 이름 하나뿐**이다 — 담당자가
누구인지는 계획 엑셀이 쥔다(ADR-023).

알맹이는 SQLite 이지만 확장자는 `.pclm` 이다. 메일 게이트웨이가 `.db` 를 막는 일이 있어서다 —
그것마저 막히면 압축해서 보낸다.

## 밖으로 내놓는 것

뷰 열 개가 유일한 약속이다. 자세한 것은 [`docs/dataset-contract.md`](docs/dataset-contract.md).

| 뷰 | 성격 | 한 줄 |
|---|---|---|
| `v_통합` | 조인 | 조달 건 1건 — 접수·공고·계약 중 들어온 것 |
| `v_접수` | raw | 접수 1건 |
| `v_접수품목` | raw | 접수 품목 1줄 = 조달요구 1건 |
| `v_공고` | raw | 공고 1건 |
| `v_공고품목` | raw | 공고 품목 1줄 |
| `v_계약` | raw | 계약 1건 |
| `v_계약품목` | raw | 계약 품목 1줄 |
| `v_통합차수` | 조인 | 조달 건 1건 × 공고 문서 한 장 |
| `v_공고차수` | raw | 공고 문서 한 장 |
| `v_계약차수` | raw | 계약 문서 한 장 |

`v_통합`의 줄 하나는 **조달 건**이다 — 접수만 들어온 것, 공고까지 온 것, 어디에도 매달리지
못한 계약이 모두 제 줄로 선다. 계약이 있는 것만 세려면 `계약번호 <> ''` 로 거른다.

끝의 셋은 **차수를 편 것**이다. 앞의 일곱이 계열마다 최신 차수 한 줄로 접어 내는 자리를,
그 셋은 접지 않고 문서 한 장마다 줄을 세운다 — 변경 전 차수도, 취소공고도, 취소되어 재공고로
갈린 원공고도 제 줄로 선다. 열은 짝이 되는 뷰와 같고, 화면에서는 탭이 아니라 「차수」 눈이다.

`v_계획` 도 서 있지만 **약속에 들지 않는다** — 열 구성이 아직 앉지 않아 밖에 내놓지 않고,
엑셀로도 나가지 않는다.

뷰·열 이름은 **제자리에서 바뀔 수 있다** — 옛 이름을 나란히 남기지 않는다(ADR-034). 받는 쪽은
없는 필드를 경고하므로 거기서 안다.

값은 모두 문서에 그대로 찍힐 문자열이다. 금액 `164,872,340`, 날짜 `2026/09/20`, 빈 값은 빈 문자열.

어댑터는 이쪽에 두지 않는다. 계약이 SQLite 파일과 뷰 이름뿐이라 받는 쪽이 이 문서만 보고
붙인다. 문서 자동 생성기(hwpx-filler)의 것은 그쪽 `src/hwpxfiller/data/pclm.py` 에 있다.

## 화면

`계약목록.exe` 를 열면 창이 뜬다. WebView2 위에 React 로 그리며, 디자인 토큰과 글꼴을
hwpx-filler 와 공유한다.

- **자료 넣기** — 자료가 들어오는 문은 왼쪽 메뉴의 **나라장터** 하나다. 오늘 들어온 수집과 확장 상태를 거기서 본다. 접수·공고·계약은 브라우저 확장이 이어 준 나라장터
  화면을 **지금 보는 화면**에서 가져오고, 파일로 받은 것은 나라장터 화면의 **JSON 파일로 가져오기**로 넣는다. 둘은 같은
  매핑·변경 검토 경로를 탄다. 창에 파일을 끌어다 놓아도 받지 않는다.

- **지금 보는 화면** — 창 오른쪽 기둥. 확장이 붙어 있으면 Chrome 에서 보고 있는 나라장터 화면이 이 작업자료에서
  무엇이 되는지(새 자료·새 차수·바뀐 칸·사람이 고친 칸)를 계약면 표기 그대로 비추고, 수집과 같은 저장 절차로 그 자리에서
  가져온다. 새 값과 바뀐 값은 들어가고, 지우는 것(비우기·복원·행 지우기)은 고를 때만 한다(ADR-041). 붙어 있지 않거나 열람 창이면 레일로 접힌다. **펼치면** 작업 영역을 차지해 왼쪽에 화면 그대로(이름표와 보이는
  글), 오른쪽에 작업자료에 설 모양을 나란히 두고 같은 자리를 함께 밝힌다. 확장의 연결·판·사이트 접근은 「Chrome 확장 상태」 에서 본다.
  확장은 연결 다리라 나라장터 화면에 수집기를 띄우거나 따로 저장하지 않는다(ADR-042).

- **엑셀 내보내기** — 표 도구 모음에서 **검색 결과**·**선택한 행**·**전체 자료**를 구분한다.
  앞의 둘은 현재 표의 열과 정렬 순서 그대로 시트 한 장을 만든다. 선택한 행은 체크박스로 고른 행이며,
  셀 범위는 Ctrl+C로 복사한다. **전체 자료**는 검색·선택과 무관하게 `pclm export`와 같은 파일을 낸다.
  `Views.Exported`의 `통합`·`접수`·`접수품목`·`공고`·`공고품목`·`계약`·`계약품목`·`ERP원천`·
  `계약업체`·`ERP접수` 열 장이다. 전체 자료에는 차수 뷰를 싣지 않지만, 차수 표에서 현재 검색 결과를
  내보내면 그 표 한 장을 저장한다. 저장 위치를 묻고 이름에 날짜를 붙인다. 파일을 수정해도 DB로 돌아오지 않는다.

- **제출·취합** — **설정 안**에 있다. 제출본은 뜰 자리를 묻고(`제출_홍길동_20260729.pclm`),
  취합은 제출본이 든 폴더를 고르면 그 폴더에 `취합_날짜.pclm` 과 결과 글 `취합_날짜.txt` 가
  떨어진다. 겹친 것을 한 줄씩 적은 그 글이 알림의 본체다 — 창에는 셈만 서고, 무엇이
  밀려났는지는 거기서 읽는다. 받은 제출본이나 지은 취합본은 **다른 자료 열어 보기**로 본다
  (아래).

- **통합 · 접수 · 공고 · 계약** — 사이드바에서 같은 높이의 독립된 메뉴로 이동하며 현재 메뉴만 강조한다.
  통합은 **구조**(접수 → 공고 → 계약이 한 사슬로 나란히, 계약
  아래 명세, 차수는 접어 이름표로)와 **표**(내보낼 모양 그대로) 두 눈으로 본다. 두 눈이 같은
  것을 센다 — 어느 쪽에도 아직 안 들어온 자리가 빈 칸으로 서 있다. 손으로 채우는 열은 초록이고 그 자리에서
  고친다. 키 문법은 엑셀 그대로다: 화살표로 옮기고, F2나 타자로 고치기 시작하고, Enter 로 넣고
  아래, Tab 으로 넣고 오른쪽, Esc 로 되돌린다. 머리글로 정렬하고(금액은 수로) Ctrl+F 로 거른다.

- **계획·현황 동결** — 두 화면과 계획 엑셀 설정 입구는 보이지 않는다. 계획 뷰·가져오기·CLI와
  시험용 현황 지표 코드는 보존하며 이번 UI 작업으로 활성화하지 않는다.

- **수집한 값도 고친다** — 번호·차수·가공열과 통합에서 붙여 온 다른 자료의 열을 제외한 수정 가능 칸을 같은 키 문법으로
  고칠 수 있다. 고친 칸에는 표시가 붙고 무엇을 무엇으로 바꿨는지 짚으면 나온다. **Ctrl+Delete
  로 원래대로.** 고친 값은 수집한 표 위에 얹히므로 다시 수집해도 살아 있다 — 부딪히면 수집
  검토가 어느 쪽을 둘지 묻는다.

- **여러 행·셀 작업** — 체크박스와 Shift+클릭으로 행을 선택하고, 머리의 체크박스로 검색 결과 전체를
  선택한다. 행을 고르면 같은 값 입력·자료 삭제가 나타난다. 셀은 드래그·Shift+클릭·Shift+방향키로
  사각형 범위를 고른다. Ctrl+C로 복사하고 Ctrl+V로 엑셀 값을 붙여넣으면 변경 전·후를 검토한 뒤
  한 번에 적용한다. 잘못된 대상이나 값, 다른 작업에서 바뀐 값이 있으면 일부만 저장하지 않는다.
  사용자 입력은 본번호 전체, 수집값 정정은 해당 차수에 적용된다. 검색을 바꾸면 선택을 해제한다.

- **선택 자료 삭제** — 행 체크박스로 고른 자료를 삭제하며 활성 셀만으로는 삭제 버튼이 나오지 않는다.
  통합에서는 먼저 접수·공고·계약 중 대상을 고른다. 같은 자료가 여러 행에 반복되면 한 번만 센다.
  선택한 차수 또는 해당 본번호의 전 차수를 고르고 하위 자료·정정값·사용자 입력값·연결의 영향을 확인한다.
  확인 이후 자료가 바뀌면 다시 검토하며 실제 삭제도 한 번에 처리한다. Delete는 셀 내용 비우기이고
  자료 삭제가 아니다. **묘비는 두지 않는다** — 같은 자료를 다시 수집하면 다시 선다.

- **문서 관계** — 수집된 접수·공고·계약의 명시 참조로 자동 구성한다. 이름·수량·단가로
  추천하거나 수동으로 연결하지 않는다. 참조 대상이 나중에 수집되면 자동으로 반영되고,
  참조 변경·삭제·취합 때도 관계를 다시 계산한다. 기존 수동·추정 링크는 보존하지 않는다.

- **설정** — 제출자 이름, 제출·취합, **저장 위치**와 작업자료를 다루는 동작을 둔다(아래).
  입력열·가공열 편집은 **열 관리 열기**로 전용 작업공간에 연결한다. 계획 엑셀 입구는 동결해 숨겼다.
  자료 설정은 작업자료 파일에 담기므로 다른 작업자료로 바꾸면 그쪽 설정이 따라온다.

  **창** 절은 이 컴퓨터에서 창을 어떻게 다룰지다 — 자료가 아니라 홈의 `window.json` 에 적혀 작업자료를
  바꿔도 따라가지 않고, 누르는 그 자리에서 선다. **알림 영역에 두기**를 켜면 닫기(X)가 창을 끝내지 않고
  알림 영역으로 숨긴다(처음 한 번 풍선으로 알린다). 아이콘을 두 번 누르면 다시 열리고, 정말 끝내는 길은
  아이콘 메뉴의 「끝내기」 다. **Windows 에 로그인하면 자동으로 켜기**는 사용자 레지스트리의 `Run` 에
  `"exe" --background` 를 적는다 — 알림 영역 두기가 켜져 있으면 창 없이 아이콘만, 아니면 작업 표시줄에 내려 둔
  채 선다. 켜져 있는지는 레지스트리만 본다(작업 관리자에서 끈 것도 꺼짐). 업무 홈에서만 다루고, 켤 때마다 지금
  exe 자리로 고쳐 적는다. 압축 파일 안에서 곧바로 켠 창(임시 폴더)은 곧 지워질 자리라 그대로 적지 않고,
  켤 때 exe 를 `%LOCALAPPDATA%\Programs\계약목록\계약목록.exe` 에 복사해 두고 그 복사본을 적는다 — 설정에서 미리
  알린다. 그 뒤 새 판 압축을 받아 켜면 복사본을 새 판으로 바꾼다. 끌 때 복사본은 남는다. 열람 창에는 이 절이 없다.

머리에 서는 것은 지금 할 수 있는 일과 지금 쌓인 것뿐이다. 제품 이름은 걸지 않는다.

자료는 **작업자료** `.pclm` 파일 하나에 쌓인다. 처음 열면 홈 `%LOCALAPPDATA%\Pclm` 에
`계약자료.pclm` 이 선다. 어느 파일이 작업자료인지는 **파일 밖** 홈의 `config.json` 쪽지 하나가
적고 — 어느 파일을 열지를 그 파일 안에 둘 수는 없다 — 창·명령줄·확장·밖에서 읽는 쪽이 모두 그것만
본다(ADR-030, [`docs/dataset-contract.md`](docs/dataset-contract.md) §1). 지금 쓰는 자리는
`pclm status` 가 첫 줄에, 설정 창이 "저장 위치" 에 적는다.

쪽지가 깨졌거나 가리키는 파일이 없으면 **빈 자료를 새로 세우지 않는다.** 시작 창이 파일을 찾을지
새로 만들지 묻고, 명령줄은 까닭을 적고 그친다. 창은 홈마다 하나만 뜬다 — 다시 띄우거나 내 작업자료를 두 번
누르면 떠 있는 창이 (알림 영역에 숨어 있었어도) 앞으로 나온다. 판을 올리기 전에는 홈의
`backups` 에 백업을 뜬다.

설정의 저장 위치 아래 네 동작이 작업자료를 다룬다.

- **작업자료 옮기기** — 같은 자료를 다른 자리로. 옛 자리의 파일은 창을 다시 띄울 때 지운다.
- **작업자료 바꾸기** — 다른 작업자료를 쓴다. 제출본·취합본·백업을 고르면 그 사본을 새
  계약자료로 떠서 쓴다 — 원본은 그때의 기록이라 그대로 둔다.
- **새 계약자료** — 빈 것부터 시작한다.
- **백업 만들기** — 지금 시점을 한 파일로 뜬다. 작업자료는 그대로다.

앞의 셋은 바꾸는 일이라, 확인 창이 어느 파일이 작업자료가 되는지 말한 뒤 바꾸고 창을 다시 띄운다.
바꾸는 사이에 수집이 저장하면 바꾸기 전 자료에 들어가거나 거절될 뿐 엉뚱한 자리에 쌓이지 않는다
(ADR-032). **확장은 자료 자리를 보지도 옮기지도 않는다** — 자리는 이 창에서만 다룬다.

**다른 자료 열어 보기**는 바꾸는 일이 아니다. 남의 자료·제출본·취합본을 따로 뜨는 **열람 창**에서
연다 — 원본을 한 벌 떠서 그 사본을 읽기 전용으로 열므로 원본은 판도 내용도 바뀌지 않는다(ADR-031).
열람 창에서는 고치는 칸·삭제·연결·계획·제출·취합·수집 도구가 잠기고, 내보내기는 열려 있다.
창을 한 번 켜면 `.pclm` 이 이 exe 에 이어져, 받은 파일을 **두 번 누르기만 해도** 열람 창이 뜬다(내
작업자료면 보통 창). 연결은 켤 때마다 지금 exe 자리로 고쳐 적는다 — 업무 홈에서만, 사용자 레지스트리에만.
명령줄에서는 `--file <파일>` 이 같은 일을 `status`·`현황`·`export` 에 한다.

실제 자료를 건드리지 않고 돌려 보려면 `--home <폴더>` 로 홈을 따로 둔다. `--db` 는 없어졌다.

## 이렇게 만든 까닭

설계 결정과 뒤집힌 판단의 근거는 ADR에 있다([색인](docs/adr.md) ·
[본문](https://claude.ai/code/artifact/195ea37e-5746-44f2-9fb0-3e3e73126797)).
코드 주석의 `ADR-007` 같은 인용은 색인에서 해소된다. 몇 가지만 옮기면:

- **PDF 입구를 걷었다**(ADR-028). 한동안 내려받은 입찰공고서·계약서 PDF 를 괘선으로 격자를
  세워 읽었다. 접수서 PDF 를 막은 뒤(ADR-027) 공고·계약도 확장이 같은 자료를 화면에서 더
  정확히 가져오게 되어, 두 입구를 함께 유지할 값이 없어졌다. 그때 들어온 자료는 진짜 키로 선
  것이라 그대로 남아 있다.

- **검산하지 않는다**(ADR-016). 조달 자료의 숫자는 나라장터가 검증해 올린 것이라 어긋나지 않는다.
  읽은 값이 맞는지는 원본을 보는 사람이 정한다. 막는 것은 번호를 읽지 못한 자료 하나다.

- **사람이 고친 값도 수집한 표를 건드리지 않는다**(ADR-020). 잘못 들어온 칸을 그 자리에서
  고치면 한 칸 안에서 원본에 적힌 값과 사람의 판단이 섞여, 그 뒤로 무엇이 무엇인지 가릴 수도
  되돌릴 수도 없다. 따로 담고 뷰가 위에 씌운다. 덮개는 **차수**에 매단다 — 1차에서 고친 금액이
  2차 변경계약에 얹히면 확인한 적 없는 숫자가 확인된 얼굴로 문서에 찍힌다.

- **손으로 적은 값은 수집이 닿지 않는 표에**(ADR-007). 열을 지워도 정의만 걷고 값은 남아, 같은
  이름으로 다시 세우면 되살아난다.

- **열 이름은 SQL에 넣기 전에 막는다.** 뷰는 앱이 열릴 때마다 다시 지어져, 따옴표 하나 섞인
  이름이 들어가면 그 뒤로 앱이 뜨지 못한다. 겹치는 이름은 SQLite 가 조용히 `이름:1` 로 바꾼다.

- **관계는 명시 참조의 파생값이다**(ADR-040). 비교·추천·확정·거절 기능은 없다.
  앱의 오연결은 버그로 고친다. 참조 없음·대상 미수집은 임의 연결로 보충하지 않는다.

- **사람이 붙인 것은 차수가 아니라 계열에**(ADR-012). 차수에 매달았더니 변경계약 한 건에 값이
  뷰에서 사라졌다.

- **펼 수 없는 것은 펴지 않는다.** 공고 하나에 계약이 여럿, 계약 하나에 명세가 여러 줄이라
  평평한 표로 펴면 위쪽 값이 아래 줄마다 되풀이된다. 통합 구조 화면은 사슬로 낸다.

- **주민등록번호는 담지 않는다.** 수집 매핑이 그 필드를 허용하지 않아 들어올 자리가 없고,
  로그에도 남기지 않는다.
  상호·사업자등록번호·대표자명은 계약 문서에 인쇄되는 사업체 정보라 담는다.

## 만들기

앱 아이콘 원본은 `scripts/generate-app-icon.ps1`의 벡터 도형이다.
`powershell -NoProfile -ExecutionPolicy Bypass -STA -File scripts/generate-app-icon.ps1`으로 여러 해상도가 담긴
`src/Pclm.App/Assets/app.ico`를 다시 만든다. 실행 파일·창·알림 영역에서 함께 쓴다.

```powershell
npm install                        # 처음 한 번
npm run build                      # 화면 짓기 (src/Pclm.App/wwwroot 로 나온다)
npm test                           # 화면 시험
dotnet build                       # 빌드
dotnet test tests/Pclm.Core.Tests  # 시험
```

.NET 8 SDK 와 Node 가 필요하다. SDK 판은 `global.json` 이 8.0 대로 묶는다. 창을 띄우려면
WebView2 런타임도 있어야 하는데 Windows 11 에는 보통 들어 있다.

**화면을 먼저 지어야 한다.** `wwwroot` 는 빌드 산출물이라 저장소에 없다.

## 돌려 보기

```powershell
./run.ps1                          # 창 (지어 둔 화면 · 배포본과 같은 모양)
./run.ps1 -Dev                     # 창 (화면은 개발 서버에서 · 고치면 곧바로 바뀐다)
./run.ps1 -HomeDir artifacts/dev-home  # 다른 홈으로 (실제 자료를 건드리지 않고)
./run.ps1 -Cli status              # 명령줄
npm run dev                        # 브라우저만 (가짜 다리)
```

`npm run dev` 는 가짜 다리(`mock.ts`)를 물려 화면만 손보게 해 주므로 진짜 다리와 어긋난 것이
드러나지 않는다. **`-Dev` 는 화면만 개발 서버에서 받고 다리와 DB 는 진짜를 쓴다** — 다만 홈은
`artifacts/dev-home` 이라 실제 자료는 아니다. 그냥
`./run.ps1` 은 지어 둔 화면이 소스보다 오래되었으면 알아서 다시 짓는다.

어느 자료를 여는지 늘 첫 줄에 적는다. 디버그 빌드에서는 F12 로 개발자 도구가 열리고 배포본에는
그 문이 없다(깃발이 아니라 빌드 설정). VS Code 로 붙을 자리는 `.vscode/launch.json`.

## 내놓기

```powershell
./publish.ps1          # dist/계약목록/ 와 zip 하나
./publish.ps1 -NoZip   # 폴더만
```

화면부터 짓고 그다음 실행 파일을 짓는다. 순서를 건너뛰면 화면 없는 앱이 나가므로 사람이 아니라
스크립트가 그 순서를 쥔다.

```
dist/계약목록/
  계약목록.exe   74MB
```

**나가는 것은 파일 하나다**(ADR-019). self-contained 라 .NET 을 설치하지 않은 컴퓨터에서도 돌고,
SQLite 네이티브도 화면(`wwwroot`)도 그 안에 들어 있다. 받는 쪽은 exe 를 아무 데나 두고 열면 된다.

화면을 안에 넣을 수 있는 까닭은 **폴더 매핑을 쓰지 않기** 때문이다. WebView2 의
`SetVirtualHostNameToFolderMapping` 은 디스크의 진짜 폴더를 요구해서 배포 단위를 폴더로
묶어 버린다. 대신 `WebResourceRequested` 로 요청을 가로채 exe 안의 리소스를 메모리에서
내준다(`MainWindow.xaml.cs`). `publish.ps1` 은 exe 말고 다른 것이 하나라도 남으면 **실패한다** —
딸린 파일이 생기면 받는 쪽이 exe 만 복사해 가서 알맹이 빠진 것을 열게 된다.

**명령줄(`pclm.exe`)은 배포물에 넣지 않는다.** 자기 런타임을 통째로 안고 있어 41MB 를 더하는데
받는 쪽은 창만 쓴다. 개발할 때는 `./run.ps1 -Cli` 로 돌린다.

버전은 `Directory.Build.props` 의 `<Version>` 한 곳에서 정해 실행 파일과 zip 이름에 쓴다.
서명하지 않은 실행 파일이라 처음 열 때 SmartScreen 경고가 뜬다(추가 정보 → 실행).

## 시험

계약면을 박제해 두고 대조한다. 열 이름과 순서뿐이라 개인정보가 없어 저장소에 함께
둔다(`tests/Pclm.Core.Tests/contract/views.txt`). 자료를 세우는 시험은 지어낸 값을 쓴다.

```powershell
$env:PCLM_UPDATE_GOLDEN=1; dotnet test tests/Pclm.Core.Tests   # 계약면 박제 새로 쓰기
```

**바뀐 내용을 눈으로 확인한 뒤에만** 새로 쓴다. 자동 갱신은 회귀를 덮어버린다.

화면 시험은 `npm test`. 표의 편집이 화면과 DB 가 조용히 갈라질 수 있는 자리라, 저장이 거부되면
화면이 옛 값으로 돌아가는지와 넣기가 꼭 한 번만 일어나는지를 붙들어 둔다.

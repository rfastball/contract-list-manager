# 데이터셋 규약

이 문서는 **이 저장소가 바깥에 내놓는 유일한 약속**이다. 소비자(문서 자동 생성기 등)는 여기 적힌
것만 의존하고, 테이블·컬럼 같은 내부 구조는 예고 없이 바뀔 수 있다.

어댑터 구현은 이 저장소에 두지 않는다. 소비자 쪽에서 이 문서만 보고 붙이면 된다.
문서 자동 생성기(hwpx-filler)의 것은 그쪽 `src/hwpxfiller/data/pclm.py` 에 있다.

---

## 1. 접속

| 항목 | 값 |
|---|---|
| 쪽지 | `%LOCALAPPDATA%\Pclm\config.json`. `{ "version": 1, "workfile": "<전체 경로>", "datasetId": "<hex>" }` |
| 파일 | 쪽지의 `workfile` — 작업자료 `.pclm` 파일 하나. SQLite 단일 파일 |
| 표지 | `PRAGMA application_id` = `0x50434C4D` (`'PCLM'`). 확인을 권한다 |
| 저널 | **WAL**. 이쪽이 쓰는 동안에도 읽기가 막히지 않는다 |
| 연결 | **읽기 전용을 쓸 것.** 예: `file:<경로>?mode=ro` (URI 모드) |
| 인코딩 | UTF-8 |

읽기 전용으로 열면 소비자가 실수로 쓸 수 없다. 이 파일의 쓰기 주체는 계약 목록(창·`pclm`·확장 호스트)뿐이다.

**자리는 하나다.** 창·명령줄·확장 호스트가 같은 쪽지 하나를 보고, 그 쪽지가 작업자료 파일 하나를
가리킨다. 밖에서 읽는 쪽에는 **가리킬 자리가 하나**여야 한다 — 어느 것이 진짜인지 파일을 열어 보기 전에는
알 수 없는 자리가 여럿 서면 안 된다. 지금 쓰는 파일은 `pclm status` 가 첫 줄에 적는다.

**어느 파일인지는 쪽지가 적는다.** 그것을 파일 안에 적을 수는 없다 — 그 값을 읽으려면 파일을 먼저 열어야
하고, 어느 것을 열지가 바로 그 값이다. 그래서 **이 하나만** 파일 밖 고정 자리에 둔다. 나머지 설정(제출자
이름·계획 엑셀 자리)은 여전히 파일 안이라 자료와 함께 옮겨 다닌다. 쪽지의 `datasetId` 는 작업자료의
신원이다 — 소비자는 쓰지 않아도 된다.

```python
# 소비자가 자리를 찾는 법
import json, os, pathlib, sqlite3

cfg = pathlib.Path(os.environ["LOCALAPPDATA"]) / "Pclm" / "config.json"
workfile = pathlib.Path(json.loads(cfg.read_text(encoding="utf-8"))["workfile"])  # 없으면 여기서 실패한다
if not workfile.is_file():
    raise FileNotFoundError(f"작업자료가 없습니다: {workfile}")

con = sqlite3.connect(workfile.as_uri() + "?mode=ro", uri=True)
if con.execute("PRAGMA application_id").fetchone()[0] != 0x50434C4D:
    raise ValueError(f"계약 목록 자료(PCLM) 파일이 아닙니다: {workfile}")
```

`config.json` 이 없거나, 깨졌거나, `workfile` 이 가리키는 파일이 없으면 **물러나지 않고 실패한다.**
다른 자리를 짐작해 여는 것보다 멈추는 쪽이 낫다 — 짐작한 자리에는 낡은 자료나 빈 자료가 있을 수 있고,
그것으로 지은 문서는 오류 없이 틀린다.

## 2. 뷰가 계약면이다

테이블을 직접 읽지 말 것. **이 문서에 나열한 뷰만이 약속**이다.

| 뷰 | 성격 | 한 줄이 뜻하는 것 | 열 (+사용자 열) |
|---|---|---|---|
| `v_통합` | **조인** | 조달 건 1건 — 접수·공고·계약 중 <b>들어온 것</b> | 56 (+계약 2) |
| `v_접수` | raw | 접수 1건 (최신 차수) | 39 (+접수 0) |
| `v_접수품목` | raw | **접수** 품목 1줄 = 조달요구 1건 | 26 |
| `v_계약` | raw | 계약 1건 (최신 차수) | 30 (+계약 2) |
| `v_공고` | raw | 공고 1건 (최신 차수) | 41 (+공고 2) |
| `v_공고품목` | raw | **공고** 품목 1줄 | 18 |
| `v_계약품목` | raw | **계약** 품목 1줄 | 14 |
| `v_통합차수` | **조인** | 조달 건 1건 × <b>공고 문서 한 장</b> | 58 (+계약 2) |
| `v_공고차수` | raw | 공고 문서 한 장 (<b>차수를 좁히지 않음</b>) | 41 (+공고 2) |
| `v_계약차수` | raw | 계약 문서 한 장 (<b>차수를 좁히지 않음</b>) | 30 (+계약 2) |

**끝의 셋은 차수를 편 것**이다(ADR-026). 위의 `v_공고`·`v_계약`·`v_통합`은 계열마다
최신 차수 한 줄로 접어 내는데, 그 셋은 접지 않고 문서 한 장마다 줄을 세운다 — 변경 전 차수도,
취소공고도, 취소되어 재공고로 갈린 원공고도 제 줄로 선다. **열은 짝이 되는 뷰와 한 글자도 같다**
(`v_통합차수` 만 끝에 둘이 더 붙는다). 최신만 필요하면 접힌 쪽을, 이력이 필요하면 편 쪽을 본다.

**이름은 제자리에서 바뀔 수 있다**(ADR-034). 뷰 이름이든 열 이름이든 바꿀 일이 생기면 옛 이름을
나란히 남기지 않고 그 자리에서 바꾼다 — 받는 쪽은 없는 필드를 경고하므로 거기서 안다. 옛 이름의
뷰는 DB 를 열 때 치워진다.

괄호 안은 **사람이 채우는 열**이다. 이 열은 `user_column` 에 등재된 만큼 붙는데, **쓰는 사람이
직접 세우고 지우고 이름을 바꾼다**. 그래서 개수도 이름도 설치마다 다르다 — 위 숫자는 기본
열만 쓸 때다. 받는 쪽은 열 개수나 자리가 아니라 **이름**으로 붙어야 하고, 없을 수도 있다고
보아야 한다. 미리 세워 두는 것은 계약에 `진행상태`·`메모`, 공고에 `검토여부`·`메모` 넷뿐이다.
접수에는 미리 세워 두는 열이 없다 — 필요하면 쓰는 사람이 만든다.

계약 쪽 사용자 열은 `v_계약` 에 붙고, `v_통합`은 그 뷰의 열을 사람 열까지 받으므로 같은 열이
공고 열 **앞에** 온다. 자리는 이렇게 바뀔 수 있으니 이름으로 붙으라는 말이 그래서 나온다.

`v_통합`·`v_통합차수` 만 조인된 뷰다. 나머지는 쌓인 그대로를 낸다 — 열이 겹쳐도 역할이 다르다.
통합은 **링크가 확정돼야** 공고·접수 열이 채워지지만, raw 뷰는 링크와 무관하게 그 자체를 낸다.

**한 줄이 뜻하는 것이 시트마다 다르다.** 받는 쪽이 한 줄로 문서 한 장을 만든다면, 계약 단위 문서에는
`v_통합`이나 `v_계약` 을, 품목 명세에는 `v_계약품목`(계약)·`v_공고품목`(공고)·
`v_접수품목`(접수) 을 쓴다. 섞으면 안 된다.

### 접수는 조달의 맨 앞칸이다

수요기관이 **조달요구번호마다** 요청을 내고, 조달청이 그것을 모아 국방계약요청접수서로 접수한
뒤 하나의 공고를 낸다. 그래서 접수서 한 장은 요청 여럿을 묶은 것이고, `v_접수품목` 의
줄 하나가 **조달요구 하나**다(`조달요구번호`). 기본 관계는 **접수 1 : 공고 1 : 계약 1** 이다.

**접수와 공고를 잇는 것은 품목의 수량·단가다.** 접수서·공고서 어디에도 조달요구번호와 공고번호를 잇는
명시적 키가 없어서, 품목 줄 수가 두 곳에서 같고 각 줄의 **(수량, 단가)가 다중집합으로 완전히
같을 때만** 잇는다. 줄 차례는 다르다 — 접수는 요청번호순, 공고는 세부품명·수량순이라 자리끼리
맞추면 틀린다. 통과하면 (수량,단가) 짝이 서로 달라 줄이 일대일로 정해지고, 그 짝이
`v_접수품목` 의 `입찰공고번호`·`공고순번` 에 실린다. **세부품명번호는 근거로 쓰지 않는다** —
협의·요청 누락으로 접수와 공고가 다를 수 있어 나란히 보이기만 한다(ADR-021).

통과 후보가 둘 이상이면 기계가 고르지 않고 **사람에게 넘긴다**. 한 공고에 접수는 하나뿐이다.

### 공고 품목은 두 곳에서 나온다

한 공고에 품목이 여러 줄일 수 있어서, 품목은 `v_공고품목` 이 전부 낸다. `v_공고` 에도
일곱 열로 비치는데(`수요기관`·`세부품명`·`세부품명번호`·`수량`·`단위`·`납품기한`·`인도조건`),
**하나로 정할 수 있을 때만** 채운다.

정하는 규칙은 이렇다.

- **칸마다** 본다. 그 칸의 값이 **모든 줄에서 같으면** 채우고, 줄마다 갈리면 빈다.
  세부품명이 여러 가지여도 수요기관·단위·납품기한·인도조건이 줄마다 같으면 그 칸은 찬다 —
  갈리는 칸은 `v_공고품목` 으로 읽어야 한다. **빈 줄도 한 값**이다 — 한 줄만 적고 나머지가
  비었으면 갈린 것으로 보고 빈다.
- **수량은 합**이다. 승강판 1대 + 2대는 3대다. 단, **단위가 모든 줄에서 같을 때만** 더한다 —
  단위가 같아야 더한 수가 뜻을 갖는다. 단위가 갈리거나 수량이 빈 줄이 있으면 수량도 빈다.

줄이 여럿인 것과 물건이 여럿인 것은 다르다. 같은 물건을 여러 수요기관에 나눠 넣느라 줄만
늘어난 공고가 흔한데(절단기 12줄, 승강판 2줄), 그런 건은 물건이 하나이므로 그대로 실린다.

**첫 줄을 싣지 않는 까닭.** 첫 줄만 비치면 줄마다 값이 다른 공고에서 첫 물건의 값이 공고
전체의 값처럼 보인다. 잘린 것은 눈에 띄지 않지만 틀린 값은 그대로 문서에 찍힌다 — 없는 편이 낫다.

`담당부서`·`담당자`·`담당자전화`·`담당자팩스` 도 같다. 담당자가 한 사람일 때만 채우고,
수요기관이 여럿이면 빈다. `v_공고품목` 은 줄의 수요기관에 맞는 사람을 붙여 낸다.

**`공고담당자` 와 `담당자` 는 다른 사람이다.** 앞은 공고를 낸 조달청 쪽(`공고기관`) 담당자,
뒤는 물건을 받는 기관(`수요기관`) 쪽 담당자다. 합치지 않는다.

### 납품기한은 한 칸이다

양식은 `납품일수`·`납품기한` 두 칸으로 적지만 뜻하는 것은 하나다 — 언제까지 넣어야 하는가.
뷰는 `납품기한` 한 칸으로 합쳐 낸다.

| 양식에 적힌 것 | 뷰가 내는 것 |
|---|---|
| 납품기한 `2026/09/26` | `2026/09/26` — 그 날이 기한이다 |
| 납품일수 `90` | `계약 후 90일 이내` — 계약일부터 센다 |
| 둘 다 없음 | 빈 문자열 |

날짜가 박힌 공고는 일수를 `0` 으로 적어 두므로 **날짜를 먼저 본다**. 그 `0` 을 그대로 풀면
"계약 후 0일 이내"라는 없는 말이 나온다.

계약 쪽 `납품기한`(`v_계약`·`v_계약품목`)은 날짜뿐이라 이 규칙이 없다.

### 한 공고에 계약이 여럿일 수 있다

분할 낙찰이나 수요기관이 여럿인 경우 **공고 하나에 계약이 여러 건** 달린다(공고 1 : 계약 N).
반대 방향은 없다 — 계약은 공고 하나만 가리킨다.

`v_통합`은 이럴 때만 줄이 갈라져 **계약마다 한 줄**이 된다. 한 공고에 계약이 둘이면 그 공고 열이
두 줄에 똑같이 반복된다. 계약을 하나씩 세우려면 그게 옳은 모습이다.

```
R26TA0911050700  164,872,340 │ R26BK09017075-000  196,500,000
R26TA0912063900  318,642,760 │ R26BK09017075-000  196,500,000   ← 같은 공고
```

공고를 축으로 세고 싶으면 `v_공고`를 쓴다. 그쪽은 계약이 없는 공고도 모두 낸다.

### 최신 차수만 나온다

변경공고·변경계약은 차수가 올라간 **별개의 행**으로 쌓이지만, 뷰는 최신 차수 하나만 낸다.
과거 차수가 필요하면 별도 뷰를 요청하라 — 지금은 노출하지 않는다.

**사람이 붙인 것은 차수를 따라가지 않는다.** 손으로 채운 열과 확정한 링크는 차수가 아니라
본번호(계열)에 매달려 있어서, 변경계약이 들어와 최신 차수가 바뀌어도 그대로 따라온다.
기계가 읽은 값만 차수마다 갈린다.

### 이름이 바뀔 때

뷰·열 이름은 **제자리에서 바꾼다**(ADR-034). 판을 붙인 새 뷰를 나란히 세우고 옛 것을 남기던
규칙은 걷었다 — 소비자는 하나이고, 없는 필드를 시끄럽게 경고하므로 이름이 바뀐 것을 거기서 안다.

- 바뀐 이름은 이 문서에 함께 적는다
- 옛 이름의 뷰는 남기지 않는다 — DB 를 열 때 치워진다
- 이름을 바꾸지 않는 변경(열을 끝에 더하는 것)은 저쪽 연결을 끊지 않는다

## 3. 값 표현

모든 컬럼은 **문서에 그대로 찍힐 문자열**이다. 소비자가 다시 손질할 필요가 없게 만든다.

| 종류 | 표기 | 보기 |
|---|---|---|
| 금액 | 세 자리마다 자릿점. 뜻 없는 소수부는 뗀다 | `164,872,340` · `54,957,446.667` |
| 비율 | 백분율 숫자 그대로. `%` 는 붙이지 않는다 | `84.245` · `0.075` |
| 날짜 | `yyyy/MM/dd` | `2026/09/20` |
| 일시 | `yyyy/MM/dd HH:mm:ss` | `2026/07/02 16:59:28` |
| 예/아니오 | 사람이 읽는 말 | `가능` · `불가` |
| 빈 값 | **빈 문자열.** NULL 을 내보내지 않는다 | `` |

빈 값을 NULL 이 아니라 빈 문자열로 내는 이유는, 받는 쪽의 **빈 값 경고가 살아나게** 하기 위해서다.
값이 없다는 사실이 조용히 사라지면 빈칸이 그대로 문서에 남는다.

단가에 소수점이 실재한다(`54,957,446.667`). 반올림하지 않고 원본 정밀도를 지킨다.

### 값은 읽은 것이거나, 사람이 고친 것이다

뷰의 값은 **확장·ERP JSON 으로 수집한 것**이거나 **사람이 손으로 고친 것**이다. 검산을 하지 않으므로
(ADR-016) 잘못 읽힌 칸을 바로잡는 것은 사람이고, 그렇게 고친 값이 뷰에 그대로 실린다.

**받는 쪽이 할 일은 없다.** 열 이름도 개수도 위의 표기 규칙도 그대로다 — 달라지는 것은 값의
출처뿐이고, 그 출처는 밖으로 내보이지 않는다. 문서에 찍을 값으로는 둘이 같은 자격을 갖는다.

고친 값은 수집한 표를 건드리지 않고 따로 담긴다(ADR-020). 그래서 같은 자료를 다시 수집해도
고친 것이 살아 있고, 되돌리면 수집한 값이 그대로 돌아온다. 다시 수집한 값과 부딪히면 어느 쪽을
둘지는 수집 검토에서 사람이 고른다.

## 4. 컬럼

### `v_통합` — 가장 자주 쓰는 시트

접수 → 공고 → 계약을 한 줄에 모은 것이다. 계약은 언제나 공고 뒤에 오고 공고는 접수 뒤에 오므로
방향은 하나뿐이다.

계약 쪽 30열(+사용자 열), 공고 쪽 17열, 접수 쪽 9열이 이 차례로 선다.

**줄 하나는 계약이 아니라 조달 건이다.** 셋 중 어느 것이 없어도 줄은 선다 — 접수만 들어온 것,
공고까지 온 것, 어디에도 매달리지 못한 계약이 모두 제 줄로 있다. 없는 단계의 열은 빈 문자열이다.
그러니 **계약이 있는 것만 세려면 `계약번호 <> ''` 로 거른다.**

한 공고에 계약이 여럿일 때만(분할 낙찰·수요기관 복수) 줄이 갈라져 계약마다 한 줄이 된다.
흔한 1:1:1 은 그대로 한 줄이다.

```
품명, 수량, 단위, 계약금액, 수수료, 지체상금률, 하자보수보증금률,

지급방법, 수요기관, 검사기관, 검수기관,
```

```
진행상태, 메모
```


### `v_접수` (raw)
```

외국산여부, 요청구분, 공개여부, 전담관, 담당과, 담당자,
선급금선고지, 선급금지급가능, 기타사항,
수요기관, 수요기관코드, 기관담당자, 기관담당자전화, 기관담당자팩스,
```

조달요구 하나가 납품장소마다 줄을 갈라 와도 **번호는 한 번만** 서고, 차례는 처음 나온 순번이다.
낱낱은 `v_접수품목` 이 한 줄씩 낸다.

끝 일곱 열은 **칸마다 모든 줄이 같을 때만** 찬다 — 규칙은 `v_공고` 와 같다("공고 품목은
두 곳에서 나온다"). 수량은 단위가 모두 같을 때 합이다. `납품기한` 은 접수서가 날짜 대신 문장을 적는 일이 많아
`계약후 90일 이내` 처럼 **적힌 그대로** 온다.

### `v_접수품목` (raw)
```
접수번호, 요청명, 순번, 조달요구번호, 국방조달계획년도, 변경차수,
세부품명, 세부품명번호, 물품식별번호, 규격, 검사형태, 취소여부,
수량, 단위, 단가, 금액, 면수,
인도조건, 납품일수, 납품기한, 납품장소, 재고번호, 규격번호, 지출요청번호,
입찰공고번호, 공고순번
```
줄 하나가 **조달요구 하나**다. 끝 두 열은 잇기가 지은 짝이다 — 이 조달요구가 공고의 몇 번째
품목이 되었는가. 접수가 공고에 이어지지 않았으면 둘 다 빈 문자열이다.

### `v_계약` (raw)
위 "계약 쪽" 30열 + 사용자 열이다. 공고·접수 열은 붙지 않는다.

### `v_공고` (raw)
```
입찰공고번호, 공고본번호, 차수, 공고명, 공고종류, 게시일시,
입찰방식, 낙찰방법, 낙찰하한율, 계약방법, 계약구분,
사업예산, 배정예산, 추정가격, 기초금액, 분할납품, 하자담보기간,
공고기관, 공고담당자, 집행관, 지역제한, 사전규격등록번호,
개찰일시, 입찰개시일시, 입찰마감일시, 등록마감일시,
수요기관, 세부품명, 세부품명번호, 수량, 단위, 납품기한, 인도조건,
담당부서, 담당자, 담당자전화, 담당자팩스, 관련공고, 공고건, 현행공고,
입찰방법
```
`관련공고`·`공고건`·`현행공고`·`입찰방법` 을 뺀 끝 열한 개는 **하나로 정할 수 있을 때만** 찬다. 규칙은
위 "공고 품목은 두 곳에서 나온다".

`입찰방식` 은 **더 수집하지 않는다** — 값이 사실상 전부 `전자입찰` 이라 문서에 쓸 데가 없다.
열은 이름째 남지만(판 올림 규칙) 새로 수집한 공고에서는 빈 문자열이다. 전에 담긴 값을 따로
지우지는 않는다.

`관련공고` 는 **이 공고가 대신하거나 이 공고를 대신하는 공고**의 번호다. 문서의 「관련공고」
칸에 적힌 그대로, 쉼표로 이어 붙인다 — 재공고는 자기가 대신하는 취소공고와 그 당초를 함께
적으므로 둘 이상이 온다(`R26BK09011054-001,R26BK09011054-000`). 없으면 빈 문자열이다.

**이 칸은 사실이지 판정이 아니다.** 문서에 적힌 그대로일 뿐, 어느 쪽이 살아 있는지를 이 칸이
말하지는 않는다(ADR-025).

`공고건` 과 `현행공고` 는 그 칸을 **읽어서** 지은 값이다(ADR-026).

- `공고건` — 취소·재공고로 **본번호가 갈린 공고들을 묶은 이름**. 그 묶음이 아는 본번호 중 가장
  이른 것이라 `R26BK09011054` 처럼 원공고의 번호가 된다. 갈리지 않은 공고는 제 본번호가 곧
  이름이다. **이 번호의 공고가 DB에 없을 수 있다** — 재공고서가 가리키는 원공고를 아직(또는
  영영) 받지 못한 경우다. 사람에게 보일 번호로 쓰지 말 것.
- `현행공고` — 그 건에서 **대체되지 않은 공고 한 장**의 번호(`R26BK09012082-000`). 같은
  본번호에 더 높은 차수가 없고, 다른 본번호가 관련공고로 자기를 가리키지도 않는 것이다.
  건의 문서가 서로를 가리켜 남는 것이 없으면 빈 문자열이다.

접수·계약 링크는 계열이 아니라 **건**에 매달린다. 그래서 취소된 원공고 줄과 재공고 줄은
`공고건` 이 같고, 한 조달 건에 접수는 여전히 하나다.

`입찰방법` 은 `계약방법` 과 `계약구분` 을 **줄여 이은** 값이다 — `제한(총액)`, `일반(단가)`.
줄임은 글자가 똑같을 때만 한다.

| 계약방법 | → | 계약구분 | → |
|---|---|---|---|
| 일반경쟁 | 일반 | 총액계약 | 총액 |
| 제한경쟁 | 제한 | 일반단가계약 | 단가 |
| 지명경쟁 | 지명 | 단가계약 | 단가 |
| 수의계약 | 수의 | 제3자단가계약 | 제3자단가 |

**둘 중 하나라도 표에 없으면 통째로 빈 문자열이다.** `제한()` 처럼 반쪽을 내거나
`계…… (명칭 미확정)` 같은 코드를 그대로 싣지 않는다 — 틀린 글자는 그대로 문서에 찍히지만
빈칸은 받는 쪽의 빈 값 경고에 걸린다. 재료는 **사람이 고친 뒤의** 두 칸이라, `계약방법` 을
고치면 이 칸도 따라 바뀐다. 이 칸 자체도 고칠 수 있고, 고친 값이 이긴다.

### `v_공고품목` (raw)
```
입찰공고번호, 공고명, 순번, 수요기관, 세부품명, 세부품명번호, 물품식별번호,
규격, 수량, 단위, 추정단가, 납품기한, 납품장소, 인도조건,
담당부서, 담당자, 담당자전화, 담당자팩스
```

### `v_계약품목` (raw)
```
계약번호, 계약건명, 순번, 품명, 규격, 물품분류번호, 물품식별번호,
수량, 단위, 단가, 금액, 수요기관, 납품기한, 인도조건
```

## 5. 키

| 키 | 꼴 | 설명 |
|---|---|---|
| 접수번호 | `R26DC00000001-000` | 접수번호 + `-` + 접수차수 |
| 입찰공고번호 | `R26BK09017075-000` | 본번호 + `-` + 차수(3자리) |
| 계약번호 | `R26TA0911050700` | 본번호 + 차수(끝 2자리) |

차수는 원본이 `000` / `00` 이고 변경될 때마다 오른다. `접수본번호`·`계약본번호`·`차수` 컬럼으로
따로도 낸다.

**접수의 키는 나라장터의 접수번호·접수차수 그대로다**(ADR-027). 접두어를 달지 않는다. 접수번호는
확장이 화면에서 수집할 때 읽는다. 수요기관이
손에 쥔 것은 대개 자기 조달요구번호라, **아무 조달요구번호로도 그 접수를 찾을 수 있다**
(`pclm set MPKPLA26910290 …`).

> 스키마 18 전에는 이 열이 `대표조달요구번호`·`대표조달요구본번호` 였고, 값은 접수서가 묶은
> 조달요구번호의 최소값이었다. 키가 접수번호가 되며 **이름을 제자리에서 바꿨다**(ADR-014 의 예외,
> ADR-027). 옛 이름으로 저장된 필드 연결은 새 이름으로 다시 짚어야 한다. 판올림은 PDF 에서만 온
> 접수를 지운다 — 접수번호를 모르니 옮길 자리가 없다.

**접수·공고·계약을 잇는 것은 확정된 링크뿐이다.** 계약서에 공고번호가 찍히지 않고, 접수서와
공고 사이에도 명시적 키가 없기 때문이다. `pclm link` 로 후보를 보고 확정하며, 확정 전까지
통합 뷰에서는 서로 다른 줄에 따로 서고 이어지지 않은 쪽 열은 빈 문자열이다. 링크를 세우는 것은
**ERP 명시 참조와 사람의 확정뿐**이다(ADR-029) — 접수↔공고의 수량·단가 다중집합(ADR-021)과
계약↔공고의 건명 일치는 후보를 추천하는 데만 쓴다. 옛 판이 그 추천만으로 이어 둔 링크(ADR-015)는
지우지 않고 남아 있으며, 확정된 링크와 똑같이 통합 뷰를 잇는다.

링크는 **본번호끼리** 맺는다(`R26TA09110507` ↔ `R26BK09017075` ↔ `R26DC00000001`).
차수끼리가 아니다 — "이 계약 건이 저 공고에서 나왔다" 는 사실은 변경계약이 나와도 그대로이기
때문이다. 그래서 한 번 확정한 링크는 차수가 올라도 유지된다.

**한 공고에 접수는 하나뿐이다.** 스키마가 그것을 강제한다 — 둘째를 이으려 하면 통합 뷰의 줄이
조용히 두 배가 되는 대신 넣는 자리에서 실패한다. 반면 **한 공고에 계약은 여럿**일 수 있다.

## 6. 컬럼 이름을 한글로 두는 이유

받는 쪽이 어휘를 따로 선언하지 않으면 **키를 그대로 사람이 읽는 이름으로 취급**한다.
한글 컬럼이면 엑셀 머리글과 똑같이 동작해서, 어댑터가 이름 대응표를 들고 있을 필요가 없다.

## 7. 담지 않는 것

**주민등록번호는 어디에도 없다.** 수집 매핑의 허용 목록에 없어 들어올 자리가 없고, 로그에도 남기지 않는다.
상호·사업자등록번호·대표자명은 계약 문서에 인쇄되는 사업체 정보라 담는다.

원본 문서도, 가져오기 기록도 보관하지 않는다(스키마 19 에서 `document` 를 걷었다, ADR-028).
**DB가 유일한 진실**이다.

---

## 8. 엑셀 내보내기

`pclm export` 와 화면의 **엑셀로 내보내기** 는 같은 뷰 일곱 개를 시트 일곱 장
(`통합`·`접수`·`접수품목`·`공고`·`공고품목`·`계약`·`계약품목`)으로 낸다. 시트 이름은 뷰 이름에서
머리 `v_` 만 뗀 것이다.
파일 이름에 날짜가 박힌다(`관리대장_20260829.xlsx`).

**차수를 편 셋은 엑셀로 나가지 않는다.** 같은 자료를 접은 것과 편 것 두 벌로 실으면 받는 쪽이
어느 장을 세어야 하는지 묻게 된다. 필요하면 DB의
뷰를 직접 읽는다.
화면에서는 그 이름을 채운 채로 저장할 자리를 묻는다 — 앱이 정한 자리에 조용히 떨어뜨리면
어디로 갔는지 모르는 사진이 쌓인다.

이 파일은 **그 시점의 사진**이다. 여기에 손으로 적은 것은 DB로 돌아오지 않는다 —
되돌리는 경로는 만들지 않는다. 쓰임새는 보관·공유·다른 도구로의 반출이다.

모든 셀은 텍스트 서식으로 고정한다. 엑셀이 긴 번호를 지수로 바꾸거나 자릿점을 지우지 않게.

---

## 9. 앞으로

- **과거 차수 조회**: `v_공고차수`·`v_계약차수`·`v_통합차수`로 냈다(ADR-026). 위 2절.
- **`v_계획`**: 연간 조달계획을 분모로 세운 뷰가 DB 안에 서 있으나 **아직 굳지 않았다** —
  열 구성이 앉을 때까지 밖에 내놓지 않는다(엑셀로도 나가지 않는다). 약속은 위의 열 장이고
  이것은 거기 들지 않는다.

**사용자 열은 약속이 아니다.** 뷰 이름과 뷰가 내는 열 이름은 바뀌면 이 문서에 적힌다는 약속이지만,
사람이 채우는 열은 쓰는 사람의 것이라 언제든 늘고 줄고 이름이 바뀐다. 받는 쪽이 거기에
필드를 걸었다면 **없어질 수 있다는 전제**로 걸어야 한다.

**검산은 하지 않는다.** 한동안 문서 안의 숫자끼리 맞춰 보고 어긋난 행에 의심 표시를 달았는데,
그 값은 나라장터가 검증해서 올린 것이라 어긋나는 일이 사실상 없었다. 남은 것은 정상인 문서에
붙는 경고뿐이었고, 그것이 **읽어서 쌓는다**는 이 저장소의 본분을 흐렸다.

## 부록 — 소비자 쪽 어댑터 스케치

참고용이다. 이 저장소에는 코드를 두지 않는다. 실물은 hwpx-filler 의
`src/hwpxfiller/data/pclm.py` — 뷰 넷만 허용목록으로 받고, `mode=ro` 로 붙고,
NULL 을 빈 문자열로 받는다.

```python
class SqliteDataSource:            # 범용 소스 — 조달 스키마를 알지 않는다
    def __init__(self, path: str, view: str): ...
    def records(self) -> list[dict[str, str]]:   # SELECT * FROM <view>
        ...
    def fields(self) -> list[str]: ...           # cursor.description
    def field_labels(self) -> dict[str, str]:
        return {}                                # 한글 컬럼이라 어휘 선언이 필요 없다
    def source_pointer(self) -> str:
        return f"sqlite:{self.path}#{self.view}"
```

`source_pointer()` 는 생성 원장에 출처를 남기는 용도다. 쿼리나 값이 아니라 **가리키는 곳만** 적는다.


## ERP 수집 확장 (스키마 17)

접수의 내부키는 접수번호 그대로다(스키마 18, ADR-027) — 스키마 17 에서는 `ERP:<접수번호>` 였다.
접수/통합 뷰의 `접수번호` 칸은 접수번호 + `-` + 접수차수다. 실제 조달요구번호는 접수 품목의
`조달요구번호`에서 읽는다. 수집 원천을 구분해야 하는 소비자는 다음 별도 뷰를 사용한다.
`v_ERP접수` 의 `대표조달요구본번호` 는 열 구성을 바꾸지 않으려고 이름을 그대로 두었다 — 값은
그 접수 품목의 최소 조달요구번호이고, 키가 아니다.

| 추가 뷰 | 한 행의 의미 | 열 |
|---|---|---|
| `v_ERP접수` | 수집 원천이 있는 접수의 차수 하나 | 내부키, 접수차수, ERP접수번호, 대표조달요구본번호, 요청명, 접수일자 |
| `v_ERP원천` | 원천 행에서 관찰한 필드 하나 | 자료종류, 내부키, 차수, 수집프로필, 원천표, 원천행키, 필드, 수집값, 매핑판, 수집시각 |
| `v_계약업체` | 계약 차수에 속한 업체 하나 | 계약번호, 순번, 원천업체번호, 상호, 사업자등록번호, 대표자, 계약지분율, 계약지분금액 |

원천 뷰의 수집값은 채택된 업무값과 다를 수 있다. 변경 검토에서 기존값을 유지해도 관찰한 원천을 보존하기 때문이다.
기본정보만 재수집해도 기존 품목 원천은 유지한다. 매핑판·수집시각은 문서의 마지막 수집 기준이며 수집프로필은 필드별 출처다.
알 수 없는 값은 빈 문자열, 0은 `0`으로 내보낸다. 복합 원천행키는 불투명한 문자열이다.

업체가 여러 곳이면 기존 계약 뷰의 단일 업체 칸을 임의의 첫 업체로 채우지 않는다. 상세는 `v_계약업체`를 읽는다.
같은 ERP 접수로 묶인 공고의 현행이 모호하면 기존 `현행공고`는 빈값이다. 이는 자료 삭제나 연결 해제를 뜻하지 않는다.

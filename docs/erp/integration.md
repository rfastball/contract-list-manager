# 접수·공고·계약 통합 수집

기본 매핑은 [수집 필드 목록](fields.md)을 구현한 `crates/pclm-core/src/erp/mapping.json`이다. JSON과 확장 입력은 같은 변환·미리보기·저장 경로를 사용한다. PDF 입구(PDF 드롭·폴더 가져오기·PDF 비교)는 걷었다(ADR-028) — 자료는 확장·JSON 으로만 들어온다(계획 엑셀 입구는 ADR-047 이 걷었다).

## 메인 프로그램

1. **나라장터 → JSON 파일로 가져오기…**를 누른다. 「고급 · 수집 규칙과 지난 수집 다시 보기」 가 펴진다.
2. 자료를 읽은 화면의 프로필을 선택하고 JSON 파일을 연다. 받는 화면은 메뉴 번호의 허용 목록으로만 가리고, 화면 하나에
   프로필 하나다(ADR-037) — 목록은 기본 `mapping.json` 에서 `screen:{code, name}` 을 단 프로필이고, 같은 프로필이 그 화면의
   고유키(`identitySource`·`baseField`·`seqField`)를 든다. 번호가 목록에 있고 그 고유키가 읽혀야 받는다. 지금은 여덟이다:
   계약요청접수상세조회-국방부(01117) `g2b-request-v1`, 계약요청접수상세조회-일반용역(01112) `g2b-request-b-v1`,
   계약요청접수상세조회-물품(01114) `g2b-request-goods-v1`, 입찰공고작성[물품](01179) `g2b-notice-a-v1`, 입찰공고작성[일반용역](01181) `g2b-notice-a-service-v1`,
   입찰공고상세(01196) `g2b-notice-b-v1`, 물품·일반용역 계약서(01579) `g2b-contract-v1`,
   물품·일반용역 변경계약서 작성(01608) `g2b-contract-change-v1`. 접수 B(`g2b-request-b-v1`)는
   계약요청접수상세조회-일반용역(01112)을 받는다 — 번호·차수가 머리에 있고 품목은 `gvDmndItem` 에 온다. 계약요청접수상세조회-물품(01114)은 머리의
   고유키가 같아 접수 B 의 필드·표를 그대로 쓰는 프로필이다(품목 표 이름은 01112 의 것을 따랐고 01114 의 품목 부분은 아직 대조하지 않았다). 입찰공고작성[일반용역](01181)은 입찰공고작성[물품](01179)과 칸이 같아 공고 A 의 필드·표를
   그대로 쓰는 프로필이다(화면 하나에 프로필 하나). 공고 작성 화면의 「미리보기」 창은 같은 첨부 표(`*_grdFile`)를 한 벌 더 싣는데,
   와일드카드 출처가 여러 표에 맞으면 빈 표를 버리고 남은 것이 내용까지 같으면 하나로 본다 — 서로 다르면 거절한다. 변경계약서 작성은 번호·차수를 품목 표에서
   읽고, 서명 전이라도 그 차수의 계약으로 담는다(계약일은 화면에 없어 걷지 않는다). 입찰공고작성[물품](01179)의 게시일시(`pbancPstgDt`)는
   그 화면의 「미리보기」 창(입찰공고 상세)에만 있어, 미리보기를 연 채로 읽을 때만 담긴다 — 닫혀 있으면 걷지 않은 칸이라
   이미 담긴 게시일시를 그대로 둔다. 그 창은 업무 영역(`#mf_wfm_container`) 밖에 서고 ID 머리만 그 영역의 것이라, 확장은
   영역 밖의 `mf_wfm_container_…` 칸도 보이는 것만 읽는다(닫힌 창의 칸은 읽지 않는다). 결재일시(`atrzDt`)로 대신 채우지 않는다. 파일은 `pointInfo` 의
   `depth3 → depth2 → depth1` 중 비지 않은 가장 깊은 단을 그 화면의 번호로 본다. 번호가 없거나 목록에 없으면 거절하고,
   프로필이 그 화면의 것이 아니면 맞는 프로필을 알려 준다. 나머지 프로필(`g2b-public-notice-header-v1`)은 매핑에 남아
   있지만 `screen` 이 없어 받지 않는다. 받는 화면을 넓힐 때는
   기본 `mapping.json` 의 그 프로필에 `screen` 을 달고 고유키·필드를 함께 맞춘다.
3. **활성 매핑으로 미리보기**를 누른다. 기존 품목과 새 원천 행의 키가 다르면 행 대응 또는 새 행 추가를 선택하고 다시 미리보기한다.
4. 기존값과 다른 값, 사라진 원천 행, 사용자 정정값은 각각 유지/적용을 선택한다. 선택하지 않은 충돌은 저장되지 않는다. 미수집 필드는 건드리지 않는다.
5. **검토한 자료 저장**을 누른다. 메인 목록도 갱신한다. 응답이 끊기면 같은 요청 결과 확인으로 재시도한다. 창을 닫았다면 이력과 현재 자료를 먼저 확인한다.

파일 수집은 파일에 포함된 범위다. 실제 화면의 전체 품목을 검증했다는 뜻이 아니다. 빈값과 0은 구분하며, 계약 JSON 총액은 전체 품목 금액 합계의 10원 미만 절사다. 기존 품목을 유지하여 총액이 달라지면 저장을 중단한다.
계약 품목은 모든 행의 계약번호·변경차수가 문서의 번호·차수와 일치해야 한다. 계약번호나 변경차수가 다르거나 빠진 행이 있으면 총액을 계산하거나 저장하기 전에 거절한다. 변경계약서 작성처럼 신원을 품목 첫 행에서 읽는 화면도 나머지 행을 모두 대조한다.

예전에 PDF 로 들어온 공고·계약은 진짜 키로 선 자료라 그대로 남는다. 그 위에 수집하면 기존 품목과 새 원천 행의 대응을 고르는 같은 검토를 탄다. 지난 PDF 비교가 남긴 `pdf:` 원천 행은 이번 수집에 없다고 지우자고 하지 않는다.

## 조건부 자동 수집

**설정 → 자동 수집**에서 **자동 수집 사용**을 켠다. 즉시 저장하며 기본은 꺼짐이다.
담당자 이름은 확장 패널의 **설정 → 내 정보**의 이름이다 — 확장이 탭 보고에 실어 보내고(패널이 닫혀 있어도), 앱은 현재 화면의
공고담당자·계약담당자에 **그 이름이 포함될 때만** 저장한다. 내 정보에 이름이 없으면 자동 수집하지 않는다. 접수 화면은 이름과
관계없이 자동 수집하지 않는다(접수는 창의 「지금 보는 화면」 에서 수집한다). 업무 담당자 칸이 없는 화면도 저장하지 않는다.
화면별 선택이나 다른 칸의 조건은 사용하지 않는다.

이름 조건은 이름의 앞뒤 공백을 제외하고 **지금 읽은 화면의 원값**에 포함되는지 부분 비교한다. 예를 들어 `홍길동(☎ 02-1234-5678)`이나 `계약팀 홍길동 대리`는 `홍길동`을 포함한다.
저장하는 담당자 원값은 그대로 유지한다. 칸이 없거나 여러 값으로 읽히거나 이름이 포함되지 않으면
기다린다. 작업자료에 저장된 담당자 값으로 조건을 대신 채우지 않는다. 내 정보의 이름을 고치면 다음 보고(앞 탭을 다시 볼 때)부터
그 이름으로 판단한다. 앱이 실행 중이면 대시보드·설정·트레이에서도 동작하며, 열람 창과 종료된 앱에서는 수집하지 않는다. 켜기 ·
끄기는 홈의 `auto-capture.json`에만 남고 작업자료·백업에 포함되지 않는다.

확장은 현재 앞에 있는 나라장터 탭의 허용된 원값과 표를 관찰한다. 탭을 누르거나 브라우저를 앞으로 가져오거나 스크롤하지
않는다. 잠시 변하지 않은 현재 자료를 저장하는 것이며 모든 내부 탭의 로딩이 끝났다는 뜻은 아니다. 사용자가 직접 다른 탭을
열어 자료가 더 실리면 후속 읽기에 반영한다. 같은 내용은 저장 이력을 반복해서 만들지 않는다.

새 값과 정상적으로 바뀐 원값은 기존 가져오기 기본 선택대로 적용하고, 빈값으로 지우기·사람 정정 복원·사라진 행 삭제는 하지
않는다. 계약 금액 검산이나 현재 작업자료·매핑 확인에 실패하면 보류한다. 설정의 **최근 자동 수집**에서 마지막 결과를 확인하고,
검토가 필요한 것은 **지금 보는 화면**에서 직접 가져온다. 로그인 업무 화면의 실제 담당자·탭별 자료 범위는 현장 확인이 필요하다.

## 매핑 관리

필드 대응 편집에서 원천 경로와 변환을 바꾸거나, JSON 편집에서 표 경로·복합키·필드·코드 대응·전체 건수 선택자를 편집한다. 매핑 파일 불러오기/내보내기를 제공한다.

**편집본 저장 → 샘플로 검증 → 검증한 매핑 활성화** 순서로 적용한다. 변경한 모든 프로필에 샘플 검증이 필요하다. 이전 버전 또는 기본 매핑을 불러와 같은 절차로 복원할 수 있다. 활성화 자체는 기존 업무자료를 다시 쓰지 않는다. 수집 이력의 허용 필드 또는 원본 파일로 재검토한다. 이력에는 매핑 당시 허용했던 필드만 있으므로 새로 추가한 원천 필드는 원본 파일이 필요하다. 이력의 자료에는 메뉴 경로가 남지 않아 저장할 때 읽은 화면의 번호(`screen`)를 함께 적고, 재검토는 그 번호로 가린다 — 번호를 적기 전의 이력은 재검토하지 않고 원본 파일을 열라고 한다.

매핑은 선언형 데이터다. 임의 JavaScript/SQL이나 대상 DB 열을 실행·추가할 수 없다. 민감·내부 경로는 거부한다. 프로필 ID와 자료 종류, 그리고 받는 화면(`screen`)과 그 화면의 고유키(`identitySource`·`baseField`·`seqField`)는 기본 매핑의 것으로 고정한다 — 편집본이 바꾸면 저장·검증에서 거절한다. `screen` 을 적기 전에 저장한 매핑은 읽을 때 기본의 `screen` 을 채우고, 기본에 프로필이 더해지기 전에 저장한 매핑은 빠진 프로필을 기본의 것 그대로 채운다. 알 수 없는 코드는 추정 명칭으로 바꾸지 않고 미확정으로 남긴다.

## 접수

접수의 키는 나라장터의 접수번호(`ctrtDmndRcptNo`)·접수차수(`ctrtDmndRcptOrd`) 그대로다. 접두어를 달지 않는다(ADR-027). 접수는 **확장이나 JSON 으로 수집해야만 선다.**

스키마 17 에 있던 **PDF 접수 대응**(ERP 접수키와 PDF 대표접수키를 손으로 잇는 별칭)은 걷었다. 사람이 순서를 지켜야만 동작해 지키지 않으면 조용히 두 벌이 섰다. 판올림(스키마 18)은 `ERP:X` 를 `X` 로, 별칭으로 이어진 PDF 접수를 그 ERP 접수번호로 옮기고, PDF 에서만 온 접수는 지운다.

명시된 접수·공고 참조로 연결한다. 같은 접수를 참조한 공고를 묶고, 본번호별 최신 차수에서 명시적으로 대체된 공고를 뺀다. 남은 후보가 하나면 그대로 현행이다. 여러 후보 중 재공고가 정확히 하나면 그 재공고를 현행으로 삼고, 재공고가 없거나 여럿이면 **현행 확인 필요**로 남긴다. 날짜·품목·번호 순서는 선정 조건이 아니다. 원공고번호나 관련공고 관계를 만들어 저장하지 않는다.

종류(`notice_kind`)와 상태(`source_status`)는 따로 저장하고, 공고종류를 읽을 때 `실공고`와 `재공고`를 `실공고(재공고)`처럼 결합한다. 일반·변경·취소·재공고 상태만 붙이며 이미 상태명이나 상태 괄호를 가진 완성된 종류는 그대로 쓴다. 종류가 비면 상태를 쓴다. `공고종류` 정정값은 결합한 값보다 우선하며 빈 정정도 유지한다. 상태만 재수집해도 화면과 현행 선정에 같은 값이 반영된다. 정확히 `재공고` 또는 `실공고(재공고)`인 경우만 재공고다.

공고종류 정정·복원과 일괄 편집은 현행과 접수 품목 연결을 함께 다시 계산한다. 스키마 31은 기존 자료의 연결을 재계산했고, 스키마 32는 출처·당시 매핑·영수증으로 입증되는 옛 공고 A의 합성 종류만 원천 종류로 복구한다. 정정값·영수증은 유지하며 입증할 기록이 없으면 기존 값을 바꾸지 않는다. 그런 자료는 원본 재수집이 필요하다.

같은 조달요구번호가 여러 접수에 있으면 가장 작은 접수번호를 사용한다. 접수번호가 시간순으로 채번되므로 가장 이른 접수를 고르는 업무 정책을 유지한다. 계약 여러 건을 한 건으로 축약하지 않는다. 계약 품목 순번을 접수 품목 순번으로 간주하지 않는다.

## Chrome / Edge 확장

앱과 확장을 함께 업데이트한다. 확장은 Native Messaging 프로토콜 2를 사용한다.

확장(「계약 목록 — 나라장터 연결」)은 **연결 다리**다(ADR-042) — 상시 포트를 쥐고 나라장터 탭을 앱의 「지금 보는 화면」 에
비추고, 앱의 명령(다시 읽기·탭 앞으로·엑셀로 내보내기·확장 관리 열기)을 따르며, 현재 화면을 엑셀로 내보낸다. 수집(검토·저장)은
앱에서 한다. 확장에는 페이지 수집기·단축키·배지가 없고, 문서 만들기 사이드 패널(ADR-045)의 「계약목록에 저장」 만 앱과 같은 저장 절차를 탄다.

### 단일 exe로 추가하기

1. `계약목록.exe`를 계속 사용할 위치에 두고 정상 실행한다.
2. **나라장터 → 확장 준비**를 누른다. exe 안의 확장을 `%LOCALAPPDATA%\Pclm\extension`에 꺼내고 현재 사용자 Chrome/Edge Native Host를 이 exe에 연결한다. 관리자 권한·별도 다운로드·PowerShell 스크립트는 필요하지 않다.
3. **Edge 확장 관리 열기** 또는 **Chrome 확장 관리 열기**를 누른다. 브라우저는 명령줄로 받은 `chrome://`·`edge://` 주소를 막고 새 탭만 열기 때문에, 앱은 새 창을 띄워 그 주소창에 주소를 적고 Enter 를 누른다(그 창이 앞에 왔을 때만). 확장이 이미 붙어 있으면 확장에 맡겨(`openExtensions`) 연다. 넣지 못하면 주소를 클립보드에 복사해 두고 알린다 — 주소창에 붙여넣는다.
4. 브라우저에서 **개발자 모드 → 압축해제된 확장 프로그램을 로드합니다**를 누르고 앱에 표시된 확장 폴더를 선택한다. 두 브라우저 모두 사용한다면 각각 추가한다.
5. 나라장터 탭을 연다 — 앱의 「지금 보는 화면」 에 그 탭이 비친다.

배포 파일은 exe 하나지만, 추가 후에는 브라우저가 읽는 확장 폴더를 유지해야 한다. 한 번 준비한 뒤로는 앱을 켤 때마다 확장 파일과 연결 경로를 지금 exe로 고친다(같으면 쓰지 않는다). 확장은 상시 연결이 서거나 호스트가 파일 변경을 알리면 실행 중인 묶음 지문을 준비된 파일의 지문과 비교해 자동으로 다시 불러온다. 나라장터 탭이 없어도 동작하고, 버전 번호가 같아도 파일이 달라지면 감지한다. 공개 키로 확장 ID를 고정하므로 Edge/Chrome 또는 설치 경로가 달라도 같은 ID를 쓴다. 과거 소스 폴더로 로드한 확장은 제거하고 위 폴더를 추가한다.

묶음 지문은 패키지의 모든 파일 이름·길이·바이트를 정렬해 계산한 SHA-256이다. 실행 중인 워커에는 추출할 때 지문을 박아 두고, 홈의 `extension-revision.json`은 파일 동기화를 모두 마친 뒤에만 게시한다. 바뀐 파일을 쓰기 전에는 이 완료 표시를 거둔다. 호스트는 기존 3초 지킴이로 완료 표시 변경을 알리고, 확장은 적용 직전에도 준비 상태를 다시 확인한다. 열린 문서 패널이 하나라도 있거나 문서 요청·내보내기가 진행 중이면 기다린다. 입력 중인 값이 사라지지 않도록 패널은 비어 있어도 닫힐 때까지 기다리며, 앱에 「패널을 닫으면 자동 적용」을 보인다. 대기 조건은 2초마다 다시 확인한다.

적용은 `chrome.runtime.reload()` 후 새 상시 연결이 보고한 실행 지문으로 확인한다. 같은 실행 지문→목표 지문은 한 번만 시도하므로 다른 폴더에서 로드한 확장은 무한 재시작하지 않는다. 실패하면 앱에서 폴더 확인·수동 새로고침을 안내한다. 이 기능이 없는 옛 확장은 최초 한 번 확장 관리에서 새로고침해야 할 수 있다. 이후에는 자동 적용한다. 앱의 최신 파일 적용 여부는 앱 내장 지문·준비된 파일 지문·실행 지문이 모두 일치할 때만 말한다. 연결 기록의 `updated`는 여전히 버전 번호 변화만 나타낸다.

**준비 완료는 브라우저 설치 완료가 아니다.** 일반 Windows 브라우저에서 로컬 확장을 자동 강제 설치하지 않는다. 조직 정책으로 개발자 모드나 사용자 Native Host가 금지되어 있다면 관리자에게 문의한다. 공식 절차: [Edge 로컬 설치](https://learn.microsoft.com/en-us/microsoft-edge/extensions/getting-started/extension-sideloading), [Chrome 배포 제한](https://developer.chrome.com/docs/extensions/how-to/distribute/install-extensions).

화면의 「연결된 확장 판」은 현재 연결이 보고한 버전만 표시한다. 연결이 없으면 `—`이며, 과거 버전은 「최근 연결」과 「마지막 연결 때」에만 남는다. 자동 갱신 실패는 「갱신 실패」, 실행 파일을 확인할 수 없는 옛 확장은 「확인 필요」로 구분한다. `run.ps1`로 실행할 때도 저장소의 `extension/`이 아니라 앱이 준비한 확장 폴더를 브라우저에 로드해야 한다.

업무 홈이 아닌 실행(`--home`·`--erp-dev`)에서는 사람의 브라우저 연결을 덮어쓰지 않도록 내장 확장 준비를 거부한다. 확장 상태 읽기는 막지 않는다 — 그 홈의 파일만 읽는다.

### 가져오기

가져오기는 앱 오른쪽의 **지금 보는 화면**에서 한다. 열린 나라장터 탭이 이 작업자료에서 무엇이 되는지 비추고, 차이는 기본대로
들어간다 — 새 값과 바뀐 값은 적용, 화면이 비워 보낸 칸·사람이 고친 칸·화면에 없는 행은 유지하고, 사람이 고를 때만 비우기·수집
원값으로 복원·지우기를 한다(ADR-041). 짝 없는 화면의 행은 새 행이다. 확장의 툴바 단추는 곧장 그 창의 **문서 만들기** 사이드 패널을 열고(ADR-045 · ADR-046),
수집 화면에는 오른쪽 아래에 같은 패널을 여는 **문서 만들기** 단추가 뜬다. 툴바 팝업은 없다. 확장에는 설정 창(옵션 페이지)도
없다 — 이을 호스트는 확장이 제 ID 로 고른다(아래 「소스·개발 환경 등록」, ADR-048).

확장은 자료 자리를 보지도 옮기지도 않는다 — 작업자료를 옮기거나 바꾸는 일은 앱의 **설정 → 저장 위치**에서만 한다(ADR-032).

### 문서 만들기 패널(ADR-045)

툴바 단추와 수집 화면 오른쪽 아래에 뜨는 **문서 만들기** 단추가 그 창의 사이드 패널을 연다(ADR-046). 패널은 그 창의 활성 탭
하나만 본다(고정 · 최근 건은 없다). 패널을 열 때와 탭이 바뀌거나 그 화면을 다시 읽어 달라졌을 때 호스트 `document {check}` 에
묻고(통로는 아래 「상시 연결」 의 `document`), 답에 따라 다음 중 하나를 보인다.

| 단계 | 보이는 것 |
|---|---|
| 수집 화면이 아님 | 「나라장터 수집 화면을 열면 여기에 건이 보입니다」 와 그 아래 어떤 화면에서 쓰는지 한 줄 |
| 연결 없음 · 준비 필요 | 「계약 목록에 연결되지 않았습니다」 · 「계약 목록을 실행하면 자동으로 이어집니다」 · 「Chrome 확장 상태」 를 확인 |
| 읽는 중 · 읽지 못함 | 그 상태 한 줄 · 읽지 못한 까닭 |
| 저장된 것과 같음 | 통합 뷰에서 읽은 값(건명과 탭의 번호) → 서식 고르기 → 포함할 내용 → 채워질 값 → 한글 파일로 저장(.hwpx) 또는 글 복사(.txt) |
| 다름 | 무엇이 다른지(「저장된 값 → 화면 값」, 호스트 `changes` 앞의 20개)와 그 바로 아래 「계약목록에 저장」 단추 하나. 새 건(차수)이면 목록 대신 「계약목록에 아직 없는 건(차수)입니다」 와 화면에서 읽은 번호. 서식 · 값 · 만들기는 잠근다 |
| 저장할 수 없음 | 호스트가 준 까닭과 「계약 목록 창 오른쪽 「지금 보는 화면」에서 확인」 — 확장에는 창을 앞으로 부르는 길이 없어 글로만 가리킨다 |

저장한 뒤의 답은 호스트가 다시 본 `check` 꼴이라, 같으면 곧장 읽어 보인다. 만들기는 읽은 값만 쓰고(보는 값 = 문서의 값)
계약목록에 쓰지 않는다. 값은 통합 뷰(「문서 서식」, ADR-047 · 052)의 한 줄이고 서식의 칸 이름은 그 뷰의 열 이름이다
([문서 만들기 어휘](../document-vocabulary.md)). 공고 탭이면 통합 뷰의 공고 자리는 그 탭의 공고다(재공고 · 취소공고로 번호가
바뀌어도). 읽은 값 위에는 경우마다 한 줄을 단다 — 계약이 여럿이라 계약마다 다른 칸을 비움, 옛 차수 화면(통합 뷰는 최신
차수의 값을 내므로 만들지 않고 최신 차수를 열라고 한다).

서식은 서식 폴더의 파일이다(ADR-049) — 업무 홈이면 문서 폴더의 「계약문서 서식」, 다른 홈(개발 · `--home`)이면 그 홈 아래
「서식」. 확장은 폴더에 닿지 못하므로 호스트 `templates`(아래 「상시 연결」)가 읽어 넘기고, 패널은 열 때 · 「이 화면 다시 확인」 때 ·
설정에서 돌아올 때 다시 읽는다. 한글 서식은 컴파일 전 모습(항목 표시가 글로 보인다)으로 두고 패널이 컴파일한다(원본 바이트와 엔진이 같으면 확장에 담아 둔 컴파일본을 쓴다).
읽지 못한 서식은 그 줄에 까닭 한 줄을 달고 고를 수 없다. 동봉 서식은 셋(한글 「물품 구매입찰 공고」, 글 「계약방법 결정 및 구매추진
안내」 · 「낙찰자 선정 및 계약체결 안내」)이고 폴더에 없는 이름만 채운다 — 있는 파일은 덮어쓰지 않는다. 서식을 고치는 것은 한글 ·
메모장이고, 패널의 설정은 순서(끌기 · ↑ ↓)와 숨김만 정한다. 「내 정보」(부서 · 이름 · 연락처 · 팩스)와 그 설정(순서 · 숨김 · 고른
항목 · 서식마다의 파일 이름 패턴은 파일 이름이 열쇠)은 이 확장의 IndexedDB 에 둔다. 동봉 공고서의 「① 계약담당자」 줄은 내 정보로,
「② 수요기관 연락처」 줄은 공고의 수요기관 쪽 담당자(통합 뷰의 열)로 채운다 — 고른 서식이 내 정보 칸을 쓰는데 내 이름이 공고담당자에 들어 있지 않거나 연락처가 공고담당 전화번호와 숫자로 다르면 「채워질 값」
머리 아래에 「내 정보가 공고와 다릅니다」 상자를 보이고, 저장 · 복사는 막지 않는다. 만든 파일은 고른 폴더에 File System
Access 로 쓰고 exe 를 거치지 않는다(같은 이름 · 손으로 고친 파일 · 잠긴 파일의 문구는 컴팩트 그대로). 폴더를 고르지 않았으면
「다운로드\계약문서」 에 곧장 내려받는다(ADR-046 덧붙임).

모양은 앱과 한 벌이다 — 패널이 앱의 토큰을 옮긴 `extension/tokens.css` 하나를 읽는다(주 행동 파랑, 됨 초록,
주의 주황, 실패 빨강). 서식은 이름과 종류(한글 · 글)가 붙은 세로 목록이고 포함할 내용은 세그먼트다. 「채워질 값」 은 빈 칸
(【확인 필요】로 남을 칸)만 그 까닭과 함께 늘 펼치고, 채워진 칸은 「채워진 N칸 보기」 로 접어 둔다(펼치면 값). 빈 칸을
남기는 것은 정상 동작이라(ADR-016) 주 단추는 늘 같은 파랑 「한글 파일로 저장」 · 「글 복사」 이고, 빈 칸 수는 단추 위 한 줄로
말한다. 주황은 덮어쓰기 확인 · 옛 값으로 만든 문서 · 다름에만 쓴다.

### 상시 연결(확장 0.8.0, ADR-035)

「마지막 연결」 은 확장이 나라장터 화면에서 인사한 흔적일 뿐이라, 확장이 지금 살아 있는지는 몰랐다. 0.8.0 의 확장은 서비스 워커가 뜰 때(그리고 브라우저 시작 때) `connectNative` 포트 하나를 열어 쥐고 있는다 — 포트가 열려 있는 동안 브라우저는 워커를 살려 두고, 그 포트로 띄워진 호스트는 포트가 닫힐 때까지 산다. 끊기면 1·2·5·15·60초로 물러서며 다시 잇고, 60초 넘게 버틴 포트가 끊기면 다시 1초부터 센다.

- 포트로는 `presence` 인사, 갱신 준비 확인·상태·변경 알림과 지금 보는 화면의 탭 보고·명령(아래)이 오간다. 매핑을 받는 `hello`(`params:{extensionVersion, browser}`)는 요청마다 `sendNativeMessage` 로 간다.
- 문서 만들기 패널(ADR-045)은 `document` 를 요청마다 `sendNativeMessage` 로 보낸다 — `params:{datasetId, op, …}`. 프로토콜 2 · 요청 번호 · 작업자료 · 자료 ID 는 다른 요청과 같이 본다. `op` 는 셋이다.
  - `check` · `snapshot`(탭 보고와 같은 실제 화면) — 지금 화면이 저장된 것과 같은가. 답 `{state:"same"|"differs"|"blocked", entity, entityType, isNew, changedCount, changes, reason?}`. 셈은 자동 수집이 「같은 내용이 이미 저장되어 있습니다」 를 가리는 것과 한 벌(`mirror::plan`)이고, 담당자 이름 조건은 보지 않는다. `isNew` 는 그 차수가 아직 쌓이지 않았는가, `changedCount` 는 기본 규칙으로 바뀔 칸의 수다. `changes` 는 그중 앞의 20개를 `[{label, before, after}]` 로 — 고른 것이 `keep` 이 아닌 바뀜만이고(지키는 덮개 · 화면에 빈 칸 · 화면에 없는 줄은 바뀌지 않으므로 없다), `label` 은 창의 「지금 보는 화면」 이 그 칸에 다는 면 열 이름(딸린 표의 칸은 `품목 2 · 수량` 처럼 표 이름 · 줄 번호 · 면 열 이름 — 품목 칸은 품목 뷰의 열, 그 밖의 딸린 표는 그 칸을 쓰는 머리 면 열이 하나뿐일 때 그 열 — 이어지는 면 열이 없으면 칸 이름 그대로), 값은 그 면 열이 저장한 뒤에 낼 표기(`12,345,000` · `2026/10/30`)다 — 호스트가 뷰의 표기식을 그 칸의 열 꼴로 돌려 내고, 표기가 서지 않는 열(여러 칸을 엮는 열)이나 이어지는 면 열이 없는 칸은 업무 표에 들어갈 글 그대로다(견주지 않는다 · 없으면 빈 글). 바뀐 것이 없거나 짝짓지 못했으면 빈 배열. 화면을 짝짓지 못하면(수집 규칙이 바뀜 따위) `blocked` 이고 `reason` 이 그 거절 글이다 — 이때 `entity`·`entityType` 은 null.
  - `save` · `snapshot` — 같은 규칙으로 앱의 저장(`erp::capture` 의 `save`)을 탄다(새 쓰기 길이 아니다). 바뀐 것이 없으면 쓰지 않는다. 답은 저장한 뒤 다시 본 `check` 꼴에 `saved:true`(쓰지 않았으면 `false`). 저장이 거절되면(품목 금액과 총액이 다름 · 미리보기 이후 자료가 바뀜 따위) `blocked` 와 그 글이고, `changes` 는 저장하려던 바뀜이다.
  - `read` · `entity`·`entityType`(`check` 가 돌려준 것) — 읽기만 한다(읽기 전용 연결). 작업자료의 「문서 서식」 줄(`store::DOCUMENT_VIEW_ID`, 사람이 고쳤으면 고친 것 — ADR-052)의 정의를 읽을 때마다 셈해 그 건의 줄을 고른다. 그 줄이 없으면 exe 에 실린 보기 구성(`presets/builtin-views.json`)의 것이다. 깔린 `u_*` 뷰는 읽지 않는다. 깨진 식의 열은 빈 글이다. 답 `{entityType, entity, values, rows, older, caseKeys}`. `values` 는 통합 뷰의 열 이름 → 글(빈 값은 빈 글)이고, 문서에 찍힐 글 그대로다(「원」 · 공문서 날짜 · 한글 금액 · 오늘도 뷰가 짓는다 — 엔진은 바꾸지 않는다, ADR-051). 줄은 사슬의 본번호(접수 · 공고 · 계약)로 고르고 사용자 열은 보지 않는다. 공고 탭이면 통합 뷰의 공고 자리를 그 탭의 공고로 묶어(재공고 · 취소공고로 같은 사슬에 공고가 둘 이상이어도) 공고 열과 공고 품목을 그 공고에서 읽는다. 접수 · 계약 탭은 사슬의 현행 공고다. 줄이 여럿이면(공고에 계약이 여럿) 줄마다 다른 칸은 빈 글이고 `rows` 가 줄 수다. `older` 는 탭이 같은 번호의 옛 차수인가다 — 값은 최신 차수의 것이다. `caseKeys` 는 그 줄들의 `kind:본번호`(패널이 저장한 파일을 이 건에 잇는 열쇠)다. 그 번호가 계약목록에 없으면 답은 null.
- 서식 폴더(ADR-049)는 `templates` 를 요청마다 `sendNativeMessage` 로 보낸다 — `params:{op, name?}`. 작업자료를 열지 않으므로 자료 ID 를 싣지 않고, 프로토콜 2 만 본다. 실패는 다른 요청과 같은 `{ok:false, error:{code:"invalid_request", message}}` 다.
  - `list` — 폴더가 없으면 짓고 exe 에 실린 동봉 서식 가운데 폴더에 없는 이름만 채운 뒤 답 `{folder, files:[{name, kind:"hwpx"|"txt", size}]}`(이름 차례). 폴더 바로 아래의 `.hwpx` · `.txt` 만 — 하위 폴더 · 숨김 · 이음 · `~` · `.` 로 시작하는 파일은 건너뛴다.
  - `read` · `name` — 답 `{name, kind, data}`(`data` 는 Base64). 경로 구분자 · `:` · `..` · 절대 경로는 거절하고 `list` 에 든 이름만 연다. 답이 응답 한도를 넘으면 「서식이 너무 큽니다」.
  - `open` — 폴더를 짓고(동봉 서식도 채운다) 탐색기로 연다. 답 `{folder}`.
- 호스트는 인사를 받으면 홈의 `extension-live/<pid>.json` 에 브라우저·확장 판·프로세스 번호·시작 시각을 적고(마지막 연결도 함께 적는다), 포트가 닫히면 지운다. 브라우저·판은 마지막 연결과 같은 모양만 받는다.
- 이 인사는 **작업자료를 열기 전에** 받는다 — 브라우저만큼 사는 호스트가 DB 를 쥐거나 잠금을 잡지 않고, 쪽지가 없어도 인사는 된다.
- 붙을 때·끊길 때 홈의 `extension-log.txt` 에 한 줄씩 덧붙인다 — 시각 · 사건(`connected`·`disconnected`·`updated`) · 브라우저 · 확장 판 · 앞의 판(판 바뀜에만), 탭으로 가른다. 읽는 쪽은 모르는 사건을 건너뛴다. 붙을 때 그 브라우저의 바로 앞 기록과 판이 다르면 `updated` 를 먼저 남긴다. 이레가 지난 줄과 500줄을 넘는 앞쪽은 쓸 때 스스로 버린다. Edge·Chrome 의 호스트가 함께 써도 파일을 홀로 열고 막히면 잠깐 기다려 줄이 섞이지 않는다. 쓰지 못해도 연결은 막지 않는다. 끊긴 까닭은 적지 않는다.
- 앱은 어느 화면에서든 2초마다 `extensionStatus` 를 읽어(바뀐 것이 없으면 다시 그리지 않는다) 그 프로세스가 **같은 시작 시각으로** 아직 돌 때만 「연결됨」 으로 센다. 끝난 프로세스의 파일은 거둔다. 같은 답에 오늘의 연결 기록이 실려, 사이드바의 나라장터·통로·Chrome 확장 상태가 한 번 읽은 것으로 같은 말을 한다. 열람 창도 읽기만 하므로 그대로 보인다.
- 실측: 끊겨도 다시 이어지고, 호스트 하나가 ~100MB 로 상주한다. 포트를 쥔 호스트가 exe 를 붙들어 **덮어쓰기는 실패하고 이름 바꾸기는 된다.**
- 그래서 새 판은 옛 exe 의 이름을 바꿔 비킨 뒤 놓는다. 이름은 `계약목록.old.exe` 또는 `계약목록.old-<숫자>.exe` 하나로 정한다. 호스트는 인사를 받은 뒤 3초마다 제 exe(개발 빌드면 `계약목록.dll` 도)의 자리·크기·쓴 때를 보고, 비켜졌거나 다른 파일이 섰으면 끊김을 적고 떠난다 — 확장이 물러서며 다시 붙으면 그 자리의 새 exe 가 뜨고, 나라장터 화면의 `hello` 판 비교로 확장도 새 판을 불러온다. 요청 하나만 받는 수집 호스트는 지켜보지 않는다. 창은 켜질 때 exe 옆과 홈의 옛 exe 를 지우고, 아직 쥐여 있으면 다음 번으로 미룬다.
- `publish.ps1` 은 붙들린 배포물 exe 를 출력 폴더 **밖**(`dist/계약목록.old-<시각>.exe`)으로 비키고 진행하며, 다음 배포 때 치운다. `run.ps1` 은 등록된 업무·개발 호스트가 창 빌드 출력(`target/…`)을 가리키면, 빌드 전에 그 폴더에서 붙들린 `pclm-desktop.exe` 만 같은 자리에서 `<이름>.old-<시각>.exe` 로 비킨다(등록 스크립트의 `pclm-erp-dev.exe` 사본은 건드리지 않는다).

### 지금 보는 화면(ADR-036)

포트가 열린 동안 확장은 나라장터 탭마다 마지막으로 읽은 것(`reading`·`supported`·`unsupported`·`error`, 읽은 때, 머리 제목, 스냅샷)을 `tabs` 로 보고하고, 호스트는 그것을 `extension-live/<pid>.tabs.json` 에 바꿔치기로 쓴다. 탭마다 읽기 번호(`seq`)를 싣고, 앞 탭의 지문이 그대로인 동안은 내용 대신 그 번호와 readiness 만 `beat` 로 보낸다 — 호스트는 `<pid>.beat.json` 에 제자리로 덮어쓰고(fsync·rename 없이), `relay::read_tabs` 가 번호가 같은 탭에만 그 readiness 를 덮는다. 창은 그 스냅샷마다 **창 안에서** inspect 하고 savepoint 위에서 면 뷰로 표기를 읽어 비춘다(같은 스냅샷·같은 dataVersion 이면 다시 하지 않는다). 창의 명령은 `extension-live/<pid>.cmd/` 에 놓이고 호스트가 포트로 넘긴다 — `focusTab`(그 탭·창을 앞으로), `read`(다시 읽기), `export`(그 탭에 내보내기 스크립트를 넣어 현재 화면 엑셀로 내보내기). 창의 가져오기는 수집의 저장과 같은 `erp::capture` 의 `save` 를 쪽지와 함께 부른다. 포트가 없으면 확장은 탭을 읽지도 보고하지도 않는다.

접수·계약 화면의 연결 위치에서 현행 공고를 정하지 못하면 그 건에 수집된 모든 본번호의 최신 차수 번호를 함께 보여 준다. 대표 공고 하나로 확정하지 않으며 정본 `현행공고`는 계속 미정으로 남는다.

포트로 오가는 메시지(모두 `protocolVersion: 2`):

| 쪽 | 메시지 | 실은 것 |
|---|---|---|
| 확장 → 호스트 | `presence` | `{extensionVersion, browser, extensionRevision?}` — 인사. 답의 `expectedRevision`은 준비된 묶음 지문 또는 null이다. 이것을 받아야 아래를 받는다 |
| 확장 → 호스트 | `extensionUpdateCheck` | 적용 직전 준비 확인. 답 `{expectedRevision}`. 작업자료를 열지 않는다 |
| 확장 → 호스트 | `extensionUpdateStatus` | `{state:"preparing"\|"waiting-panel"\|"waiting-work"\|"reloading"\|"failed"\|"current"}` |
| 호스트 → 확장 | 갱신 알림 | `{command:"extensionUpdate", revision}` — 지문 또는 null. null이면 대기 중 적용을 취소한다 |
| 확장 → 호스트 | `tabs` | `{front, frontAt, tabs:[{tabId, windowId, title, state, readAt, screen, menu, snapshot?, screenRows?, message?}], settings, me}` |
| 호스트 → 확장 | 탭 명령 | `{command:"focusTab"\|"read"\|"export", tabId}` |
| 호스트 → 확장 | 브라우저 명령 | `{command:"openExtensions"}` |

- `screenRows:[{group, label, text, source}]` — 화면 그대로. 수집 규칙이 읽는 칸마다 화면의 이름표(aria-label → title → label → `[data-title]`, 없으면 같은 줄의 앞 `th`)와 보이는 글, 가장 가까운 앞의 구역 제목. 품목은 줄마다 `「순번 품명」 / 「수량단위 · 금액」` 원값이고 `source` 는 `table:<대상 표>:<몇째 줄>`. 지원 안 되는 화면은 내보내기의 화면 필드 앞 40줄(`source` 빈 글). 호스트는 글 넷의 줄인지, 400줄을 넘지 않는지만 본다. 창은 면 열마다 그 열을 채우는 자리(`views::face_references` 로 열 정의에서 끌어낸 것)를 이 줄과 이어 「화면 · 이름표」 와 화면 표기를 단다.
- `menu` — 화면의 메뉴 번호(ADR-037). 숫자 다섯이거나, 모르면 빈 글. 빠지면 보고를 받지 않는다.
- `settings:{siteAccess}` — 나라장터 사이트 접근. 바뀌면 다시 보고한다. 확장이 읽지 못했으면 null 이고, 빠지면 보고를 받지 않는다. 창의 「Chrome 확장 상태」 의 확장 정보가 앞 탭의 브라우저(없으면 처음 붙은 것)의 것을 보인다. 다른 칸은 받되 적지 않는다.
- `me:{name}` — 패널 설정의 내 정보 이름(앞뒤 공백을 뗀 글, 없으면 빈 글). 자동 수집의 담당자 조건이다. 바뀌면 다시 보고한다. 이름이 글이 아니거나 빠지면 보고를 받지 않는다. 호스트는 이름 하나만 적는다.

### 소스·개발 환경 등록

저장소의 `extension` 폴더를 직접 로드하는 개발자는 표시된 확장 ID와 빌드한 exe를 지정한다. 이 경로도 현재 사용자 영역에만 등록한다.

```powershell
./scripts/register-erp-host.ps1 -ExtensionId '<확장 ID>' -ExePath '<배포 폴더의 실행 파일>'
```

개발 환경은 앱의 `--erp-dev`, 등록 스크립트의 `-Development`, **개발용 ID 확장**(`scripts/fake-g2b.ps1` 이 개발 홈의 `extension/` 에 띄우는 복사본)을 함께 사용한다. 확장은 제 ID 가 개발용일 때만 개발 호스트에 잇고, 그 밖에는 늘 업무용 호스트에 잇는다 — 바꾸는 스위치는 없다(ADR-048). 업무·개발은 홈으로 갈린다 — 개발 호스트와 `--erp-dev` 창은 홈이 `%LOCALAPPDATA%\Pclm.Erp.Dev` 인 것만 다르다.

호스트는 홈의 쪽지(`config.json`)를 읽기만 하고 쓰지도 판을 올리지도 않는다. 쪽지가 멀쩡하고, 가리키는 파일이 지금 판의 작업자료이고, 그 신원(`datasetId`)이 쪽지와 같을 때만 연다. 저장은 쓰기 잠금을 얻은 뒤 쪽지와 파일의 신원·역할을 **다시** 보고, 그 사이 앱이 작업자료를 바꿨으면 거절한다 — 저장은 바꾸기 전 자료에 들어가거나 거절될 뿐이다(ADR-032). 작업자료를 옮기면 신원이 이어져 열린 검토가 새 자리로 이어지고, 다른 작업자료로 바꾸면 옛 검토의 저장은 거절된다. `--home` 으로 띄운 앱은 업무 홈의 쪽지를 건드리지 않는다.

### 실제 ERP 화면 검증이 필요한 부분

공개 물품공고 기본정보 7개만 읽는 확장 보조 경로는 제거했다. 저장 매핑이 맞지 않으면 DB 저장을 차단하고 엑셀 내보내기를 안내한다. 기존 매핑과 저장 자료의 호환성을 위해 서버의 과거 프로필 정의는 유지하지만 확장의 수집 후보에서는 제외한다. 접수·공고 A/B·계약의 전체 표 수집은 선언형 프로필과 WebSquare DataList 읽기를 사용하며, 실제 로그인 업무 화면의 API·표 범위는 현장 검증이 필요하다.

화면은 **문서 번호 하나로** 가린다. 매핑의 번호·차수(접수 `ctrtDmndRcptNo`·`ctrtDmndRcptOrd`, 공고 `bidPbancNo`·`bidPbancOrd` 또는 `bidPbancText`, 계약 `ctrtNoOrd`)를 읽을 수 있는 매핑이 후보다. 계약 화면은 공고·접수 번호를, 공고 화면은 접수 번호를 참조로 함께 싣기 때문에 후보가 여럿이면 가장 아랫단 문서(계약 → 공고 → 접수)를 고른다. 표·제목은 있으면 담고 없거나 비면 수집하지 않은 것으로 두어 기존 값을 건드리지 않는다. 덜 불러온 표에서 빠진 행은 「행 삭제」 충돌로 나와 사람이 고른다 — 전체 건수를 따로 세어 막지 않는다(`totalSelector`는 읽지 않는다). 화면 값은 컴포넌트 원값을 먼저 읽고, 보이는 칸에 없으면 같은 자료에 묶인 숨은 칸을 쓴다. 부가 필드가 둘 이상의 값으로 관찰되면 그 필드만 수집하지 않는다. 막는 것은 로딩 중, 번호·차수의 형식 오류나 값 충돌, 같은 단의 문서가 둘, 품목 행 키의 누락·중복뿐이다.

### 현재 화면 엑셀 내보내기

앱의 **지금 보는 화면**에서 그 나라장터 탭의 엑셀 내보내기를 누른다 — 확장이 그 탭 안에서 파일을 지어 내려받는다. 활성 매핑·전체 건수 선택자 없이 동작한다. 앱 없이 되던 확장 팝업의 내보내기는 팝업과 함께 걷었다(ADR-046).

- `화면 필드`: 값이 있는 입력·선택·WebSquare 텍스트의 항목명, 표시값, 원본 ID, 참조 필드.
- 표별 시트: 화면에 표시된 WebSquare 표를 보이는 그대로 — 보이는 열만 화면 열 순서로, 화면 머리글과 표시값으로 담는다. 단추·선택 열과 행 번호 열은 뺀다. 칸의 `<br>`은 셀 안 줄바꿈으로 남기고 단추·숨긴 풍선 도움말은 버린다. 표 API가 없거나 읽지 못하면 DataList의 원천 필드 ID와 원값으로 대신한다. 동일 DataList의 중복 표현은 한 번만 내보내며 동일 값을 가진 실제 행은 유지한다. ID와 머리글이 있는 일반 HTML 표도 지원한다.
- `수집 정보`: 화면명, query/hash를 제외한 출처 주소, 수집 시각, 시트별 원본 ID와 행 수, 읽지 못한 표.

빈 열, 숨김 입력, 비밀번호·세션·계좌번호·주민번호로 식별되는 필드, 내부 행 상태값은 제외한다. 표의 중첩 객체는 단일 값만 경로로 펼치고 배열은 제외한다. 병합 셀이 있는 일반 HTML 표는 제외 사유를 기록한다. 열의 값이 모두 자릿점 숫자(`1,234`·`0`·`1,000원`, 네 자리 이상은 자릿점이 있어야 한다)이면 엑셀 숫자로, 모두 같은 구분자의 실제 날짜(`2026/09/21`·`2026-09-21 10:30`)이면 엑셀 날짜로 쓰고 화면과 같은 표시 형식을 붙인다. 하나라도 어긋난 열과 그 밖의 셀은 문자열로 저장하여 번호·선행 0·긴 번호를 보존하고 수식처럼 보이는 원문을 실행하지 않는다. 열 너비는 가장 긴 값(한글은 두 칸)에 맞춘다.

현재 최상위 화면에서 관찰할 수 있는 자료의 스냅샷이다. 다른 페이지·미개방 탭·iframe을 순회하거나 서버를 추가 조회하지 않으며 전체 품목 수를 보장하지 않는다. 최대 200시트·50만 셀·32 MiB이며 Excel 셀 길이·행·열 제한을 넘으면 잘라 저장하지 않고 오류를 표시한다. 자료는 확장에서 `.xlsx`로 생성되어 브라우저 다운로드 설정에 따라 저장된다.

## 데이터와 검증

새 원천/행키/업체 자료는 내보내기에 포함한다. 새 읽기 전용 뷰는 [데이터셋 규약](../dataset-contract.md)을 참고한다.

회귀 검증은 `crates/pclm-core/tests/erp_capture.rs`, `frontend/src/ErpExtension.test.tsx`, `frontend/src/SettingsPanel.test.tsx` 가 한다. 저장 선택, 동시 변경, 재전송, 허용 필드, 복합키를 확인한다.

```powershell
# 개인 JSON 코퍼스는 저장소에 넣지 않는다.
$env:PCLM_JSON_CORPUS = '<로컬 json.zip>'
cargo test --workspace
npm test
npm run build
cargo build -p pclm-desktop --features shell
```

# 접수·공고·계약 수집 UX / UI 설계

상태: 2026-09-24 작은 페이지 수집기 방향 승인. 공고 기본정보 경로의 공통 UI를 구현했다.
접수·공고·계약 전체 수집 범위는 아래 설계 목표이며 구현 완료를 뜻하지 않는다.
**초기 제품은 접수·공고·계약을 누적하는 도구다. 공개 공고 기본정보 7개 수집은 기능 실증이다.**
현재 구현·검증 상태는 [mvp.md](mvp.md)에 별도로 기록한다.

## 제품의 일과 역할

사용자는 나라장터에서 업무 자료를 열고, 수집 대상을 확인해 로컬 자료 목록에 쌓는다.
앱에서는 누적된 접수·공고·계약을 찾아보고 관계와 변경 내용을 검토한다.
사용 모드는 Operate다. 성공 기준은 세 종류를 모두 수집할 수 있고,
각 자료의 저장 범위와 결과, 다른 자료와의 연결 상태를 구분할 수 있는 것이다.

| 화면 | 맡을 일 |
|---|---|
| 크롬 확장 | 현재 화면 인식 → 대상·수집 범위 미리보기 → 명시적 저장 → 결과·복구 |
| 데스크톱 앱 | 누적 목록·검색 → 접수/공고/계약 관계 검토 → 변경차수 비교·정정 → 내보내기 |

확장에 앱의 전체 탐색·편집 기능을 복제하지 않는다. 자료 종류는 열린 화면에서 판별하여
‘접수’, ‘공고’, ‘계약’으로 표시한다. 사용자가 종류 탭을 골라 화면을 다른 자료로 해석하게 하지 않는다.
인식할 수 없는 화면에서는 지원 화면으로 이동하도록 안내한다.

## 초기 제품의 수집 범위

세 종류 각각에 대해 **식별 정보·업무 기본정보·품목·원천 참조**를 수집하는 것을 설계 목표로 삼는다.
세부 필드와 필수 범위는 화면별 매핑 검증에서 확정한다. 공고 실증의 7개 필드를 제품 전체 범위로 삼지 않는다.

| 자료 | 식별·검토의 중심 | 원천 참조와 주의점 |
|---|---|---|
| 접수 | ERP 접수번호·차수, 건명, 해당 업무 기본정보, 품목 | 조달요구번호 등 실제 참조를 보존. 기존 PDF 접수키와 동일하다고 가정하지 않음 |
| 공고 | 공고 본번호·차수, 공고명, 종류·일정 등 업무 기본정보, 품목 | 접수 참조 및 관련공고를 관찰된 범위대로 보존 |
| 계약 | 계약 본번호·변경차수, 계약명, 계약 관련 기본정보, 품목·금액 | 공고 참조 보존. 분할계약은 각각 별도 자료로 유지 |

‘기본정보·품목·참조’는 검토 구역이며 자동으로 세 종류에 같은 필드 집합을 적용한다는 뜻이 아니다.
필수 범위의 완전성이 확인되지 않으면 해당 저장을 막고 부족한 부분을 알린다.
아직 검증하지 않은 일정·담당자 등 세부 필드를 수집 완료로 표시하지 않는다.

## 누적과 연결의 UX

- 접수부터 시작하도록 강제하지 않는다. 공고나 계약을 먼저 저장해도 원천 참조를 보존한다.
- 아직 수집하지 않은 관련 자료는 ‘아직 수집되지 않음’으로 표시한다. 실제 업무가 없거나 지연됐다는 뜻이 아니다.
- 기본 관계는 접수 1 : 공고건 1 : 계약 N이다. 공고건 안의 공고와 각 차수는 유지한다.
- 같은 접수를 참조하는 공고를 묶되, 근거 없는 선후·대체 관계나 현행 공고를 추정하지 않는다.
- 직접 참조가 명확하고 기존 링크와 충돌하지 않을 때 연결한다. 수동 확정·거절은 보존한다.
- 참조가 모호하거나 충돌하면 ‘연결 확인 필요’로 남기고 앱에서 검토한다.
- 자료 저장 성공과 연결 결과는 별도로 알린다. 연결 미확정만으로 ‘저장 실패’라 하지 않는다.
- 기존 PDF 접수와 ERP 접수의 식별자 대응이 미확정이면 자동 병합하지 않는다.

따라서 앱의 통합 화면은 세 칸의 업무 진행률이 아니라 **수집된 자료의 관계**를 보여준다.
‘미수집’, ‘연결 확인 필요’, ‘원천 참조 없음’을 동일한 빈 상태로 뭉개지 않는 것이 목표다.
기존 화면에서 이를 정확히 표시하려면 원천 참조와 수집 이력의 저장 지원이 필요하다.

## 확장의 공통 화면 구조

1. **상단:** ‘자료 가져오기’, 실제 저장 대상. 개발 환경에서만 눈에 띄는 ‘개발용’ 표시.
2. **대상:** 감지된 종류, 본번호·차수, 건명. 확인·저장·복구 중 같은 위치에 유지.
3. **검토:** 기본정보 요약, 품목 행 수와 펼쳐보기, 원천 참조.
4. **수집 범위:** 전체 범위 확인 여부와 누락 이유. 확인되지 않은 수량을 0으로 표시하지 않음.
5. **상태와 행동:** 한 개의 기본 실행 버튼, 필요한 보조 행동.

화면 형태는 **페이지 오른쪽 아래의 작은 수집기 + 동일한 확장 팝업**으로 확정했다.
지원 화면은 자동 확인하고 대상과 범위를 미리 보여준다. 사용자는 저장을 한 번 누른다.
상세는 펼쳐서 확인하고 수집기는 접을 수 있다. 별도의 사이드 패널은 두지 않는다.
페이지 수집기는 확장 설정 창에서 끌 수 있다(「툴바 확장 버튼으로만 열기」). 끄면 화면을 관찰하지 않고,
결과를 확인하지 못한 저장이 있을 때 수집기를 띄우는 대신 툴바 버튼에 !를 붙인다. 기본값은 항상 표시다.
아래는 세 종류 전체를 지원할 때의 정보 배치 목표이며 실제 수집값이 아닌 예시다.

```text
자료 가져오기                      저장 대상: 계약 목록
─────────────────────────────────────────────────────
계약                         <계약 본번호>-<변경차수>
<계약명>

기본정보
  <주요 필드>       <값>
  <주요 필드>       <값>

품목              16행 · 전체 범위 확인됨       펼치기
원천 참조          공고 <본번호>-<차수>
                   관련 공고는 아직 수집되지 않았습니다.
─────────────────────────────────────────────────────
확인한 계약 정보와 품목을 저장합니다.
[                    계약 저장                    ]
                       다시 확인
```

화면에 들어오면 자동으로 화면과 저장 대상을 확인한다. 확인만으로 DB에 저장하지 않으며,
저장은 별도 클릭으로 실행한다. 품목은 요약에서 전체 행 수를 먼저 보여주고 세부 행은 펼쳐 검토한다.
‘전체 범위 확인됨’은 수집기가 실제로 입증한 경우에만 표시한다.
항상 떠 있는 패널을 선택하면 현재 탭과 미리보기 대상의 불일치를 명확히 표시하고 재확인을 요구한다.
팝업에서도 저장 직전에 대상 화면의 변경을 검사한다.

## 상태와 행동

| 상태 | 핵심 안내 | 기본 행동 |
|---|---|---|
| 시작 | 접수·공고·계약 상세 화면을 열어 주세요. | 현재 화면 확인 |
| 확인 중 | 자료 종류와 수집 범위를 확인하고 있습니다. | 확인 중… |
| 저장 준비 | 확인한 [종류] 정보와 품목을 저장합니다. | 접수 저장 / 공고 저장 / 계약 저장 |
| 범위 불완전 | [필요한 정보]를 확인하지 못했습니다. [화면별 해결 방법] | 다시 확인 |
| 저장 중 | [종류] 정보를 저장하고 있습니다. | 저장 중… |
| 저장 완료 | [종류] 정보를 저장했습니다. | 현재 화면 다시 확인 |
| 동일 내용 | 이미 같은 내용이 저장되어 있습니다. | 현재 화면 다시 확인 |
| 결과 미확인 | 저장 여부를 확인하지 못했습니다. | 저장 결과 확인 |
| 조회 결과 저장 기록 없음 | 같은 요청으로 다시 시도할 수 있습니다. | 같은 요청 다시 저장 |
| 화면 또는 저장 자료 변경 | 자료가 바뀌었습니다. 다시 확인해 주세요. | 현재 화면 확인 |
| 지원하지 않는 화면 | 지원하는 접수·공고·계약 상세 화면을 열어 주세요. | 현재 화면 확인 |
| 초기 연결 문제 | 저장 대상에 연결하지 못했습니다. | 다시 확인 + 연결 도움말 |

결과 화면에는 대상과 저장 결과를 유지한다. 원천 참조가 있으면 연결 결과를 별도 줄로 표시한다.
예: ‘계약 저장 완료 / 참조 공고 미수집’. 연결 결과 표시는 실제 백엔드가 확인한 값에 근거해야 한다.
아직 제공되지 않는 신규/수정 구분이나 필드별 변경 비교를 현재 지원 기능처럼 약속하지 않는다.

저장 요청 뒤 연결이 끊기면 기존 요청을 유지하여 결과부터 조회한다. 조회에도 실패하면 계속 미확인 상태다.
저장 기록이 없음을 확인한 뒤에만 동일 식별자·동일 내용으로 재전송한다.
팝업 재개방 시에는 결과를 조회하며 자동 재전송하지 않는다.
현재 복구 정보는 브라우저 세션에만 남는다. 초기 제품에서 브라우저 종료 후에도 복구를 보장할지는
구현 전에 보관 정책과 함께 결정할 항목이며 현재 지원 사실로 표시하지 않는다.

## 자료 보존 원칙이 UI에 미치는 영향

- 품목의 전체 행·필요 열·기존 행 대응이 확인되지 않으면 전체 교체하지 않는다.
- 화면의 일반 표와 Excel용 중복 표를 합산하지 않는다. 값이 같은 실제 업무 행은 유지한다.
- 계약 총액은 전체 품목 수집이 입증된 경우에만 합계의 1원 자리를 버리는 합의 규칙을 적용한다.
  미확인 총액을 0이나 선택 품목 금액으로 보여주지 않는다.
- 차수와 분할계약을 덮어써서 최신 한 건으로 축약하지 않는다.
- 사용자 정정·수기값과 관찰하지 않은 기존 필드는 보존한다.
- 미확인 값을 보기 좋게 추정하여 채우지 않는다. 필요하면 ‘확인되지 않음’으로 표현한다.

## 시각·접근성 방향

기존 앱의 중성 바탕, 파란 기본 동작, 얇은 경계와 여백을 이어간다.
종류별로 화면을 새로 만들기보다 동일 구조에서 필드·품목·참조가 바뀌게 한다.
구체적인 폭과 정보 밀도는 팝업/패널 선택 후 긴 접수·공고·계약 표본으로 검토한다.
새 UI 프레임워크나 아이콘 라이브러리는 필요하지 않다.

- 건명은 줄바꿈하고 본번호·차수를 온전히 읽을 수 있게 한다.
- 성공·주의·오류는 색과 상태 문구로 함께 구분하고 화면에 남긴다.
- 실행 중 중복 클릭을 막고, 상태 전환 후에도 키보드 초점을 잃지 않게 한다.
- 품목 펼치기와 전체 미리보기를 키보드로 조작할 수 있게 한다.
- 연결·설정 문제에만 해당 도움말을 제공한다. 화면 인식 오류와 뒤섞지 않는다.
- 기술 정보는 ‘오류 상세’에 둔다. 일반 흐름에는 Native Host나 프로토콜 식별자를 노출하지 않는다.
- 앱 연결 확인을 ‘앱 실행 중’으로 표현하지 않는다. 확장에는 ‘앱에서 보기’ 버튼을 두지 않는다 — 앱이 상시 연결로
  Chrome 의 나라장터 탭을 스스로 비추므로(창의 「지금 보는 화면」, ADR-036) 확장이 앱을 열 까닭이 없다.

## 설계 확정과 구현 순서

1. 초기 제품 범위: **접수·공고·계약 누적** — 사용자 확인 완료.
2. 공통 흐름: 종류 인식 → 범위 확인 → 저장 → 결과·복구, 앱에서 관계 검토 — 이번 제안.
3. 작은 페이지 수집기와 팝업 공통 UI — 승인·공고 경로 구현. 세 종류 전체의 정상·불완전·충돌 화면은 후속 검증.
4. 종류별 필수 필드·전체 품목 수집 근거·식별자 대응·실사용 저장 대상과 복구 보관 정책 확정.
5. 승인된 설계에 따라 수집 경로와 UI 구현. 세 종류가 초기 제품 범위라는 기준은 유지한다.

기능 실증을 제품 출시에 필요한 세 종류 지원의 대체로 간주하지 않는다.
구현 순서는 기술적인 분할일 뿐 접수·계약을 차기 제품으로 미루는 범위 결정이 아니다.

## 검토 시나리오

- 접수 → 공고 → 계약을 차례로 저장하여 앱에서 관계를 확인한다.
- 계약을 먼저 저장하고 나중에 공고·접수를 추가하여 참조가 해소되는지 확인한다.
- 한 접수의 여러 공고·차수와 복수 계약을 각각 보존한다.
- 같은 자료를 재수집하거나 차수를 추가해도 중복·과거 자료 소실이 없다.
- 품목이 일부만 읽힌 경우 저장 가능한 것처럼 보이지 않는다.
- 저장 응답 단절에서 결과 조회·동일 요청 재시도로 회복한다.
- PDF 접수와 ERP 접수의 대응이 모호할 때 조용히 병합하지 않는다.
- 긴 제목·많은 품목·키보드 조작에서도 대상과 실행 버튼을 확인할 수 있다.

기존 확장 테스트와 종류별 저장 테스트의 소유자를 먼저 확인하고 필요한 증거만 보강한다.
실제 설치 확장과 로그인된 업무 화면의 검증은 DOM 기반 테스트와 별도로 필요하다.

## 승인한 접합 구조와 현재 구현 경계

브라우저는 허용된 화면 사실과 출처를 수집하고, C#은 프로필·형식·저장 범위와 충돌을 검증한다.
페이지 수집기 → 서비스 워커 → 기존 Native Messaging → C# → SQLite 경로를 사용한다.
새 localhost API, 매핑 파일 엔진, 전체 DOM 저장, 자동 저장은 추가하지 않는다.

현재 UI는 공고번호·차수·건명과 **기본정보 7개 / 품목·담당자·관계 제외**를 표시한다.
접수·계약을 지원한다고 표시하지 않는다. 결과·미확인·재시도에는 원래 저장 대상을 유지한다.
범위 불완전과 연결 실패를 구분하고 연결 실패에만 도움말을 제공한다.
복구와 테스트 증거, 확장 갱신 절차는 [mvp.md](mvp.md)의 0.2.0 항목에 기록한다.

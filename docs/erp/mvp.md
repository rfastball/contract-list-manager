# ERP 기능 실증 개발 상태

2026-09-24. 첫 수직 경로 구현이며 전체 ERP 전환 완료를 의미하지 않는다.

공개 공고 수집은 기능 실증 범위다. 초기 제품은 접수·공고·계약 자료를 누적하는 것을 목표로 한다.
제품 UX 설계는 [extension-ux.md](extension-ux.md)에 기록하며, 아래는 현재 구현된 지원 범위다.

## 현재 지원 범위

- 로그인하지 않은 나라장터 **입찰공고상세[내자]** 화면의 기본정보 7칸.
- 공고명, 공고종류, 게시일시, 낙찰방법, 계약방법, 공고기관.
- 지원 화면 자동 확인 → 대상·범위 요약 → 한 번의 명시적 저장 → 개발 SQLite의 기존 공고 목록.
- 페이지 오른쪽 아래 수집기와 확장 팝업은 같은 UI를 사용한다. 접기·상세 펼치기·저장 결과·복구를 제공한다.
- 프로필 `g2b-public-notice-header-v1`. 실제 DOM 식별자와 값만 보존한다.
  WebSquare fullRef/DataList를 확보한 프로필로 간주하지 않는다.
- 같은 captureId 재전송은 같은 영수증 반환, 다른 내용 재사용은 거절한다.
  같은 기본정보의 새 수집은 업무행의 updated_at을 갱신하지 않는다.
- 미리보기 이후 DB 변경은 충돌로 거절한다. 사용자 덮개·수기값·미관찰 열과 모든 자식표를 보존한다.
- 업무행, 허용 필드 원문 스냅샷, 영수증은 한 트랜잭션에서 커밋된다.

현재 지원하지 않는 범위: 품목, 일정, 담당자, 관계, 접수, 계약, 로그인된 ERP 화면.
기존 PDF 기능은 실사용 수집 경로를 검증하기 전까지 유지한다. (이후 걷었다, ADR-028)
이미 합의한 계약금액 절사와 동일 접수의 공고건 묶기는 해당 프로필 구현 때 적용한다.

## 실행 및 연결

### 확장 설치 없이 개발 화면 확인

`npm run dev -- --host 127.0.0.1 --port 5178` 실행 후
`http://127.0.0.1:5178/extension-preview.html`을 연다.
팝업·페이지 수집기, 저장 성공·동일 내용·초기 연결 실패·저장 전/후 응답 단절·충돌을 선택하고
**적용 / 초기화**를 누른다. 원본 버튼으로 상세·저장·결과 조회·재시도를 조작할 수 있다.
280px·360px·960px 너비를 선택할 수 있으며 새로고침하면 예시 저장 기록이 초기화된다.

이 페이지는 원본 `popup.html/css/js`, `capture.js`, `background.js`를 그대로 실행한다.
Chrome API·Native Host·사이트 origin은 함수 인자로 주입한 대역이며 자료와 영수증은 메모리에만 남는다.
실제 나라장터, 개발/운영 DB, 사용자의 Chrome 프로필에는 연결하지 않는다.
Vite 개발 전용 페이지이며 앱 배포 빌드와 확장 패키지에는 포함하지 않는다.

기존 `npm test -- src/ErpExtension.test.tsx`가 동작 회귀 검증을 맡는다.
추가한 미리보기는 실제 렌더링·신뢰된 버튼 클릭·원본 UI와 중계기의 연결을 수동 검토하는 자리다.
설치 권한·실제 서비스 워커 수명·Native Messaging 연결은 설치 환경에서 별도 확인해야 한다.
이번 변경의 자동 테스트 케이스·CI 브라우저 실행 증가는 0이다. 개발 확인에서만 임시 Chrome으로
두 화면 × 여섯 상황과 280px 가로 넘침을 검사했으며, 기존 확장 테스트 5개는 168ms(러너 1.40초)에 통과했다.
직전 실행 179ms와는 실행 조건이 달라 성능 변화로 해석하지 않는다.

### 설치 환경 연결

저장소 루트 PowerShell에서:

```powershell
npm run build
dotnet build src/Pclm.App
& './src/Pclm.App/bin/Debug/net8.0-windows/계약목록.exe' --erp-dev
```

개발 자료는 개발 홈 `%LOCALAPPDATA%\Pclm.Erp.Dev` 의 쪽지가 가리키는 작업자료 하나만 사용한다.
WebView2 캐시와 오류 로그도 `Pclm.Erp.Dev` 아래에 분리한다.
개발 GUI가 생성·판올림하고, Native Host는 기존 DB만 연다.
`--erp-dev`와 `--home`은 함께 쓸 수 없다(`--db`는 걷었다). 개발 홈에서 작업자료를 옮기거나 바꿔도 업무 홈의 쪽지는 건드리지 않는다.
인자 없이 실행하면 기존 운영 모드이므로 이번 검증에는 반드시 `--erp-dev`를 사용한다.

1. Chrome의 `chrome://extensions` 또는 Edge의 `edge://extensions`에서 개발자 모드를 켠다.
2. **압축해제된 확장 로드**로 저장소의 `extension` 폴더를 선택하고 표시된 확장 ID를 확인한다.
3. 아래 명령의 ID를 실제 값으로 바꿔 등록한다. HKCU의 개발 Host 두 키만 등록하며 관리자 권한은 필요 없다.

```powershell
./scripts/register-erp-host.ps1 -ExtensionId '여기에실제32자리확장ID' `
  -ExePath './src/Pclm.App/bin/Debug/net8.0-windows/계약목록.exe'
```

4. `https://www.g2b.go.kr/`에서 검증에 쓸 공고번호(표본 공고 — 원문 생략)를 검색하고 그 상세를 연다.
5. 페이지 오른쪽 아래의 수집기에서 번호·차수·건명과 제외 범위를 확인한 뒤 **공고 기본정보 저장**을 누른다.
   확장 아이콘의 팝업에서도 같은 작업을 할 수 있다.
6. 개발 앱의 공고 목록을 새로고침하거나 개발 앱을 다시 열어 그 공고번호·차수(`-001`)를 확인한다.

확장은 activeTab·scripting·nativeMessaging·storage와 `https://www.g2b.go.kr/*` 접근을 요청한다.
이 사이트의 최상위 화면에서만 수집기를 표시하며, 지원하지 않는 화면에서는 페이지 수집기를 숨긴다.
페이지 안에서 허용 필드를 1초마다 관찰하고 값이 바뀔 때만 저장 대상을 다시 확인한다.
자동 페이지 이동·자동 DB 저장은 없다. 실제 저장은 사용자의 저장 버튼 클릭으로만 실행한다.
원문 요청은 전송 중 한 건만 브라우저 세션에 보존한다. 팝업을 닫았다 열면 영수증을 조회한다.
브라우저를 종료하면 세션 요청은 사라지며 자동 재전송하지 않는다.
통신이 끊겼을 때 **저장 결과 확인**으로 조회하고, 기록이 없으면 같은 요청으로 재시도한다.
등록 해제는 위 등록 명령에 `-Unregister`를 더한다. 개발 DB와 확장 자체는 삭제하지 않는다.

### 수집 UI 0.2.0 적용

기존 사용자는 확장 관리 화면에서 이 확장을 **새로고침**하고 열려 있는 나라장터 탭도 새로고침한다.
사이트 접근 권한을 제한해 둔 경우 `www.g2b.go.kr`에서 실행을 허용해야 페이지 수집기가 나타난다.
Native Host와 C# 코드는 이번 UI 변경에서 바뀌지 않았으므로 기존 등록을 재사용한다.

- 저장 직전 탭·문서·허용 필드를 다시 읽고 미리보기와 비교한다. DB 충돌 검사는 기존 C#이 수행한다.
- 서비스 워커가 중간에 종료돼도 UI의 미리보기 증거와 현재 화면을 다시 검증한다.
- 미확인 요청은 브라우저 전체에서 하나만 보관한다. 다른 탭에서 실행해도 이전 요청 결과부터 조회한다.
- 조회 결과가 `not_found`일 때만 같은 captureId·내용의 명시적 재전송을 허용한다.
  오래된 재시도 버튼으로 다른 요청을 재전송하지 않는다.
- 동일 내용 결과는 C#의 `changed: false`를 표시한다. 저장 전 변경 감지·필드 차이 표시는 아직 제공하지 않는다.
- 접힌 수집기에도 상태를 표시하며, ERP 스크립트가 만든 합성 클릭으로 저장하지 않는다.
- 복구 기록은 기존과 같이 브라우저 세션까지만 유지한다. 브라우저 종료 후 복구는 보장하지 않는다.

검증: 기존 `ErpExtension.test.tsx`의 DOM 수집 증거는 유지하고 팝업 전용 복구 시험을
서비스 워커 복구·신뢰 경계와 공통 UI 시험으로 대체했다. 고유 위험은 화면/탭 전환 후 잘못된 저장,
미확인 요청 덮어쓰기, 자동 재전송, 합성 클릭, 워커 재시작 및 SPA 전환 뒤의 오래된 표시다.
계층은 jsdom·Chrome API 대역이며 실제 앱·DB·네트워크를 자동 테스트에 추가하지 않았다.
케이스는 2개에서 5개(+3), 기준 89ms/러너 1.26초에서 169ms/러너 1.34초로 변했다.
전체 프런트 98개 통과(23.06초). Coverage 기준 변경 없음.
로컬 예시 데이터로 실제 브라우저의 360px/280px 화면·상세·저장 결과·연결 도움말을 확인했다.
이는 설치 확장과 실제 나라장터·Native Host의 종단 검증을 대체하지 않는다.

## 확인한 증거와 남은 경계

- 공개 사이트의 표본 공고 하나(변경공고, 차수 `-001`)에서 실제 기본정보 7개 선택자, 공고번호·차수, readonly 상태 확인.
  공고명·공고번호·게시일시는 원문 생략, 공고기관 `조달청`.
- 화면에 담당자 마스킹 안내가 있으므로 담당자 값은 허용 목록에서 제외했다.
- C# 375개, 프런트 94개 통과. 신규 경계는 아래 테스트가 소유한다.
- 프런트 및 WPF 빌드 성공. 기존 EXE의 `--native-dev` 진단 모드에 길이 접두사+JSON을 보내
  GUI 없이 올바른 프레임과 `setup_required` 응답을 확인했다. 실제 저장 성공으로 세지 않는다.
- 팝업 초기 화면은 로컬 미리보기로 육안 확인했다. 화면 확대 검증은 아직이다.
- 사용자 현장 확인: 안내 절차를 따라 **설치된 확장 → Native Host → 개발 DB → 앱 목록**에 공고가 들어오는 것을 확인했다.
  이어 같은 공고 재저장 후 사용자가 “업서트 멱등 유지 확인”을 보고했다.
  이는 사용자 실행 결과이며 에이전트가 설치 브라우저를 직접 조작하거나 DB 타임스탬프를 별도 조회한 증거는 아니다.
  Chrome/Edge 양쪽 브라우저에서 각각 검증했다는 의미도 아니다.
- 사용자 수정값 보존, 충돌 거절, 통신 단절 복구는 자동 테스트 외에 설치 환경에서도 후속 확인할 항목이다.
- 운영 DB는 열거나 판올림하지 않았다. 스키마 V16 코드가 추가되었으므로 새 빌드의 운영 모드는 기존 GUI의 판올림 정책을 따른다.
- 취합본은 새 datasetId를 갖는다. DB별 수집 영수증·스냅샷은 원본 DB에 보존하고 취합하지 않는다.

## 테스트 변화

기존 소유자 검색: HomeTests·WorkfileSwitchTests(자료 위치), MergeTests(취합 테이블 정책), 기존 프런트 컴포넌트 테스트.
새 통신·수집 경로를 검증하는 기존 소유자는 없었다.

- 고유 위험: 부분수집이 기존 자료를 삭제함, 중복·충돌 요청이 잘못 저장됨, 프레임 오염,
  확장 세션 저장 실패/연결 단절이 다른 요청 저장으로 이어짐.
- 소유자/계층: ErpCaptureTests(임시 SQLite·메모리 스트림), ErpExtension.test.tsx(jsdom·Chrome API 대역).
- 추가 10개(C# 8, 프런트 2), 기존 테스트 삭제/대체 0. 중복된 기존 증거 없음.
- 전체 실행: C# 기준 22초 → 24초, 프런트 기준 24.18초 → 13.32초.
  캐시·동시 실행 영향이 있어 변화량을 기능 성능의 증거로 해석하지 않는다.
- 새 테스트만 실행: C# 775ms, 프런트 83ms(러너 전체 1.22초). 변경 후 재실행 값은 실행 로그 참조.
- 자동 테스트의 브라우저·앱·네트워크 실행 추가 0. Coverage 기준 변경 없음.

기본정보의 설치 환경 종단 연결과 재저장 멱등성은 사용자 확인을 받았다.
다음 범위는 설치 환경의 수정값 보존·복구 확인과 전체 품목 범위가 증명되는 수집 프로필이다.

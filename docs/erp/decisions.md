# ERP 전환 쟁점 정리

검토일: 2026-09-24. 코드 기준: `7c7efd4`, Schema 15.
근거: 사용자 제공 핸드오프 v1.1·표본 분석 v1.1 및 현재 저장소 정적 확인.
PDF 코퍼스 및 제공된 `json.zip`의 식별자·품목·중복 표를 대조했다. 결과는 아래 §2·§3에 기록한다.
2026-09-27 수집 범위와 연결 정책 변경은 §6이 우선한다. 요구사항 확정이며 런타임 변경 완료를 뜻하지 않는다.
원천 ID의 용어·범위 확인은 [전수 매핑표](json-field-mapping.md)와 [사용자 확인 목록](json-field-questions.md)을 먼저 따른다.
§6의 필드 예시는 수집 범위 후보이며 공식 라벨·코드 의미의 확정이 아니다. 사용자 확인 전에 구현 매핑으로 사용하지 않는다.
ERP 실행·DB 쓰기·제품 테스트 실행은 아직 하지 않았다.
아래의 설계 방침은 구현 완료 또는 현장 검증 완료를 뜻하지 않는다.

## 1. 현재 코드에 맞춘 기준선

- 기존 11개 외부 뷰를 보호한다. 정본은 `docs/dataset-contract.md`다.
- 문서의 Schema 13을 출발점으로 사용하지 않는다. 구현 시 현재 마지막 migration 다음에 추가한다.
- `NoticeGroups`와 공고 관계·차수 보기 기능을 재사용 대상으로 삼는다.
- PDF 입력 제거는 ERP 한 화면의 저장·조회 검증 뒤에 진행한다. (진행함, ADR-028 — 스키마 19)

## 2. 계약 총액: 원 단위 절사 규칙 확인, 전체 품목 수집 검증 대기

표본 분석 문서에서 계약 5개의 `pointInfo.ctrtAmt`가 첫 품목 금액과 같다고 보고했다.
이는 선택 품목 값과 헤더 값의 출처를 구별해야 한다는 근거다.
이후 사용자가 시스템에서 원 단위를 항상 절사한다고 확인했다.
여기서는 품목 금액을 전부 합산한 뒤 1원 자리를 버려 10원 단위로 만드는 규칙으로 해석한다.

- 현재 legacy 값은 `ContractRecord.Amount`와 `Quantity`에 매핑하지 않는다.
- 계약 총액은 전체 품목의 원천 금액 합계에 원 단위 절사를 적용해 산출할 수 있다.
  이 규칙은 사용자 확인에 근거하며, 시스템 구현 자체를 직접 검증한 것은 아니다.
- 행별 추가 절사나 수량×단가 재계산은 하지 않는다. 중복 수집원을 제외한 전체 품목 금액을 먼저 합산한다.
- 전체 품목 수집이 입증되지 않으면 총액을 갱신하지 않는다. 계약지분금액을 대체 출처로 사용하지 않는다.
- 이 규칙을 계약 헤더 수량의 합산 규칙으로 확대하지 않는다. 미확인 필드는 기존 값을 보존한다.
- 품목의 금액·수량은 해당 행의 값으로 보존한다.

헤더 원천을 확보할 경우의 추가 대조 절차 (금액 산출 규칙 확정과 별개):

1. 동일한 조회 상태의 다품목 계약에서 화면에 표시된 총액의 위치·라벨을 확인한다.
2. 품목 1행과 2행을 각각 선택해 총액 후보의 component ID, fullRef, 화면/프레임, 값을 비교한다.
3. 선택행 값과 헤더 값의 출처를 구별한다. 값이 고정됐다는 사실만으로 총액이라고 승인하지 않는다.
4. 실제 총액 표시와 바인딩이 대응하는지 확인하고 다른 계약에서도 재확인한다.

### PDF 코퍼스 대조 (2026-09-24)

사용자 요청에 따라 코퍼스의 계약 PDF 8개(초안 2개 포함)의 제목·계약번호·헤더 금액을 검색했다.
이후 제공된 원본 JSON 계약 5건의 번호·차수와 대조했지만 동일 계약 PDF는 없었다.
특히 PDF 표본 F 와 S06(표본 C)은 수요기관도 품목도 다른 건으로, 계약번호와 금액 모두 다르다.

별도로 다음 3건은 PDF의 계약금액과 전체 품목 금액을 원문 페이지 렌더링으로 확인했다.
아래 합계는 인쇄된 행별 계약금액을 더한 값이며 수량×단가의 재계산이 아니다.

| PDF | 헤더 계약금액 | 품목 금액 합계 | 합계−헤더 | 확인 페이지 |
|---|---:|---:|---:|---|
| PDF 표본 F (품목 3행) | 원문 생략 | 원문 생략 | +9 | 1, 3 |
| PDF 표본 G (품목 2행) | 원문 생략 | 원문 생략 | 0 | 1, 2 |
| PDF 표본 H (계약 초안, 품목 2행) | 원문 생략 | 원문 생략 | +9 | 1, 2 |

금액 원문은 생략한다. 세 건 모두 합계와 헤더의 차는 합계의 1원 자리 숫자 그대로였다(9, 0, 9).

사용자 확인 반영: 시스템은 원 단위를 항상 절사한다. 위 세 건은 품목 합계의 1원 자리를 버리면
모두 헤더 계약금액과 일치한다. 앞선 '합계로 총액을 산출할 근거가 부족하다'는 판단은 이 규칙으로 보완한다.
예(지어낸 값): 12,345,671 + 23,456,788 = 35,802,459 → 1원 자리를 버려 35,802,450. 표본 G 처럼
합계의 1원 자리가 이미 0이면 버려도 그대로다.
JSON 표본과 동일 계약 PDF의 직접 대조는 여전히 미수행이다. 남은 저장 관문은 전체 품목 수집의 완전성이다.

## 3. 중복 표와 전체 범위: 수집원 선택 결정, 완전성 확인 대기

- 접수·계약은 문서에서 확인한 일반 표를 대표 수집원으로 삼고 Excel 표를 더하지 않는다.
- 공고 B는 19행의 대표 표 하나를 선택한다. 다른 표의 추가 열은 필요성과 출처 확인 후 채택한다.
- 값이 같은 업무 행은 삭제하지 않는다. 조달요구번호 단독으로 행을 합치지 않는다.
- 원천 행 키는 원래 문자열로 보존한다. 기존 `line_no`와의 대응·유일성은 프로필별로 확인한다.
- `getAllJSON()`·`rowStatus`·페이지 크기만으로 전체 범위나 조회 상태를 확정하지 않는다.

종결에 필요한 현장 관찰:

1. S05 구조에서 활성 화면·조회 상태·로딩 완료의 실제 근거를 확인한다.
2. 대표 grid와 DataList, 관찰 행 수, 같은 품목 집합에 대한 전체 건수 근거를 대응시킨다.
3. 페이지/스크롤/탭에 따른 데이터 로딩 범위를 확인한다. 수집기가 자동 순회하지 않는다.
4. 전체 행뿐 아니라 기존 저장 열을 안전하게 갱신할 수 있는지도 확인한다.

**행이 전부 있어도 열이 일부이면 기존 표의 DELETE/INSERT는 안전하지 않다.**
현재 `Store.Upsert*`는 자식 표를 통째로 교체한다. ERP 경로는 관찰한 열만 갱신하고,
행 대응을 입증할 수 없으면 그 표의 쓰기를 막는다. 전체 교체는 행·필요 열의 완전성과
기존 행 대응이 확인된 경우에만 허용한다. 필수 표 범위가 불명확하면 요청 전체를 거절한다.

### 마크다운 표본 요약과 PDF 대조 (2026-09-24)

사용자가 JSON 근거 위치로 첨부 마크다운을 지정했다. 두 문서에는 실제 JSON의 분석 요약이 있고,
원본 `pointInfo`·`tables` 전체는 없다. 핸드오프 부록 C의 JSON은 합성 프로토콜 예제다.
분석 문서 §2는 원본 재검증에 별도 `json.zip`을 사용한다고 명시한다.

코퍼스 PDF 27개를 검색해 표본 A 변경공고를 대응 후보로 확인했다.
`표본 A 공고 PDF`의 1쪽은 차수 `-001` 의 실공고(변경공고)다(번호·공고명 원문 생략).
3쪽 구매대상물품은 순번 1의 한 행이며 수량·추정단가·세부품명번호·물품식별번호가 적혀 있다(원문 생략).
PDF 원문 렌더링으로 확인했다.

마크다운만으로는 S01의 번호·차수·행별 값이 없어 요약 행 수 1:1 일치까지만 확인했다.
이후 사용자가 원본 ZIP을 제공하여 아래와 같이 직접 검증을 완료했다.

### 원본 JSON과 PDF 직접 대조 (2026-09-24)

입력: 사용자 제공 `json.zip`(로컬 경로 생략)의 JSON 15개와 현재 `corpus/`의 PDF 27개.
ZIP SHA-256은 `a1a2e661cd1ecaba0fcacc9851b318f380066b10fe10ef5891d3279d9ad8ca0c`로 분석 문서와 같다.
원본 업무 JSON을 저장소로 복사하거나 전체 내용을 로그로 남기지 않았다.

공고는 PDF 첫 페이지의 본번호·차수로 매칭했다. 계약은 ERP 번호·변경차수의 구분 하이픈을
제외한 표시와 PDF 계약번호를 대조했다. 접수는 PDF에 ERP 접수번호가 없어 품목 조달요구번호의
교집합으로 후보를 찾았지만 겹치는 자료가 없었다. **직접 확인된 쌍은 표본 A 변경공고 1쌍**이다.

| 항목 | PDF `표본 A 공고 PDF` | JSON S01 | 결과 |
|---|---|---|---|
| 본번호·차수 | 원문 생략 (`-001`) | 원문 생략 (`-001`) | 일치 |
| 전체 품목 행 수 | 1 | 1 | 일치 |
| 품목 순번 / 분류 | 1 / 1 | 1 / 1 | 일치 |
| 세부품명 / 번호 | 원문 생략 | 원문 생략 (같은 값) | 일치 |
| 물품식별번호 | 원문 생략 | 원문 생략 (같은 값) | 일치 |
| 규격 | 원문 생략 | 원문 생략 (같은 값) | 일치 |
| 수량 / 단위 | 자릿점 있는 수 / 포 | 자릿점 없는 같은 수 / 포 | 일치 |
| 추정단가 | 자릿점 있는 수 | 자릿점 없는 같은 수 | 일치 |
| 납품일수 | 0 | 0 | 일치 |
| 납품기한 | `yyyy/MM/dd` (원문 생략) | `yyyyMMdd` 의 같은 날 | 날짜 의미 일치 |

PDF 1·3쪽의 원문 렌더링과 텍스트, JSON 대표 품목 표를 대조했다.
이 쌍의 품목 누락·중복은 없다. S15 취소공고(번호 원문 생략, 차수 `-001`)는 같은 PDF의 관련공고에만
등장하므로 별도의 동일 문서 쌍으로 세지 않았다.

추가로 JSON 일반/Excel 표 8쌍을 전체 행·필드 비교하여 모두 동일함을 재확인했다.
접수의 대표 행 수는 3·4·198, 계약은 3·4·1·2·16이다. 두 표를 합치지 않고 하나만 사용한다.
이 검증은 보유 표본에 대한 것이며 한 행 공고의 성공으로 다페이지·다품목 수집의 완전성을 일반화하지 않는다.

## 4. 관계: 기존 구조 재사용 범위 결정

현재 코드에서 확인한 사항:

- `project_link`: 계약 본번호가 PK이고 공고건에 UNIQUE가 없어 공고건 하나에 여러 계약을 지원한다.
- `request_link`: 접수 본번호가 PK, 공고건이 UNIQUE이므로 접수와 공고건은 1:1이다.
- `request_item_link`: 접수 품목 하나에 공고 품목 하나만 저장한다.
- `NoticeGroups`는 명시된 관련공고를 따라 여러 공고 본번호를 묶는다. 같은 접수번호만으로 묶지는 않는다.
- `NoticeGroups.Rebuild`는 충돌한 접수 링크를 정리할 수 있어 원천 참조 보관소로 쓸 수 없다.

적용 방침:

사용자 확인: 같은 접수의 품목을 나눠 독립된 공고로 발주하는 것은 시스템상 불가능하다.
따라서 동일 ERP 접수에 대한 참조를 공고건 묶기의 근거로 사용한다. 이 업무 규칙은
사용자 확인에 근거하며, 현재 `NoticeGroups`에 이미 구현되어 있다는 뜻은 아니다.

1. ERP 원천 식별자와 참조를 기존 대표 링크와 별도로 보존한다. 물리 스키마는 저장 구현에서 확정한다.
2. 공고·계약은 본번호와 차수별 레코드를 유지한다. 분할계약 3건은 3건으로 남긴다.
3. 같은 ERP 접수를 참조하는 공고들은 하나의 공고건으로 묶는다. 접수번호·관찰된 접수차수를 보존하고,
   기존 PDF 대표키와 혼동하지 않는다. 묶기의 근거는 ERP 접수 참조로 기록하며 원문에 없는 관련공고를 만들어 넣지 않는다.
   같은 건에 속한다는 사실만으로 공고들의 선후·대체 관계나 현행 공고를 추정하지 않는다.
4. 원천 참조가 기존 링크의 유일성과 양립하고 충돌이 없을 때만 연결한다. 수동 확정·거절을 자동으로 덮지 않는다.
5. 공고 차수가 없으면 본번호 수준의 참조로 보존한다. 특정 차수나 품목 짝을 추측하지 않는다.
6. 기본 관계는 접수 1 : 공고건 1 : 계약 N으로 유지한다. 접수 품목 분리 발주를 위한 1:N 관계나 새 뷰는 추가하지 않는다.
   이 업무 규칙과 충돌하는 입력은 오류·식별자 매핑 문제로 확인하고 기존 자료를 조용히 병합하지 않는다.
7. ERP 수집 후 기존 PDF 휴리스틱을 전체 자료에 무조건 실행하지 않는다. 직접 참조의 미확정·충돌을 우회 확정하지 않도록 연결 대상을 제한한다.

추가로 접수 입력 전에 해결할 사항:

- (해결됨, ADR-027) 접수 키는 이제 ERP 접수번호·접수차수 그대로다. 접수서 PDF 는 접수를 세우지 않았고, 이후 PDF 입구 전체를 걷었다(ADR-028).
- 두 식별 체계의 대응과 충돌을 확인하기 전에는 기존 접수에 자동 병합하지 않는다.
- 기존 문서의 '접수 품목 1행 = 조달요구 1건'은 동일 요구번호가 여러 행에 반복되는 ERP 표본과 맞지 않는다.
  행 병합으로 맞추지 말고 기존 뷰 소비자가 요구번호의 유일성을 전제하는지 확인한다.

## 5. 현장 검증에 필요한 입력

- 원본 `json.zip`은 사용자 로컬에서 확보·대조했다(경로 생략).
- 다품목·다페이지 수집의 PDF 직접 대조에는 해당 JSON과 번호·차수가 같은 추가 PDF가 필요하다.
- 사용자 지시에 따라 첫 테스트는 로그인하지 않은 공개 게시 공고로 진행한다.
  로그인된 ERP 접수·계약 화면의 수집은 후속 범위다.
- 사용자 로컬의 `g2b-screen-registry.json`은 과거 연기공고 화면 기록이다.
  `https://www.g2b.go.kr`는 확인 후보지만 S05 프로필·활성 화면·현재 접근 정책의 증거로 대체하지 않는다.

첫 구현 상태·지원 범위·설치 절차는 [mvp.md](mvp.md)에 기록한다.
공개 기본정보 경로 다음으로 S05 및 계약 품목의 전체 행 범위를 확인한다.
계약 총액 산출 규칙과 관계 보존 방침은 정했지만, 실제 매핑 지원은 수집 범위 검증 후 확정한다.

## 6. MVP 범위 보완: JSON 중심 수집과 명시 키 연결 (2026-09-27)

사용자는 기존 PDF 수집 항목을 포함하는 JSON 기반 MVP를 요청했다. 실제 웹페이지 테스트가
불가능해도 보유 JSON 코퍼스로 개발·검증을 진행하며, PDF 입력 처리는 동결하고 연결은
명시 키만 사용한다. 계약보증·선급금·인지세 등 추가 금액·조건과 업체별 지분·공동수급
상세를 처음 MVP에 포함하도록 요청했다. 후속 용어 검토에서 **공동수급 관련은 코퍼스 확보까지
미사용**으로 변경했으며 업체별 현재차수 계약지분율·지분금액은 유지한다.
이 절은 범위 결정이다. 이번 변경은 문서만 수정하며 기존 PDF 입력·자동 연결 코드는 아직 동작한다.

### PDF 정보의 완전 포함 여부

현재 JSON 15개(접수 3, 공고 7, 계약 5)는 PDF 수집 정보의 완전한 상위집합이 아니다.
PDF 파서·Domain 모델과 JSON의 pointInfo·tables 키를 대조했고, 동일 문서인 표본 A
변경공고는 기존 PDF 골든 파싱 결과와 JSON 원문을 추가 대조했다.

| 기존 PDF 수집 정보 | JSON 코퍼스에서 확인한 한계 |
|---|---|
| 표본 A 변경공고 게시일시 | PDF 결과의 게시일시(원문 생략)에 대응하는 게시일시 필드가 없고 해당 시각도 없음. 결재일시를 대신 쓰지 않음 |
| 같은 공고의 기초금액 | PDF 결과의 기초금액(원문 생략)이 해당 JSON에 없음. 사업금액·추정가격으로 대체하지 않음 |
| 같은 공고의 관련공고 | PDF 결과의 원공고·취소공고 참조 3개가 해당 JSON에 없음 |
| 접수 부가세·전담관·담당과·담당자·기타사항 | 접수 JSON에서 직접 대응 필드를 확인하지 못함. 기관 담당자를 접수 담당자로 대체하지 않음 |
| 계약 구매관리번호·기관관리번호·해지 여부/일자 | 계약 JSON에서 직접 대응 필드를 확인하지 못함. 변경사유만으로 해지를 판정하지 않음 |

이는 보유 덤프의 한계이며 실제 ERP 화면에 정보가 없다는 뜻은 아니다. 공고의 다른 화면형에는
게시일시·기초금액 표가 있으나 다른 문서의 값으로 누락을 채울 수 없다. 다른 접수·계약은
동일 문서 PDF 쌍이 없어 전체 값의 동등성까지 검증했다고 보지 않는다.

JSON을 주 입력으로 개발하되 PDF는 기존 누적값 유지·누락값 보완·원문 대조의 보조 경로로
남기는 방향을 제안한다. PDF 파서의 신규 범위 확장은 중단한다. PDF 자동 입력의 즉시 차단·삭제와
100% 대체 선언은 별개다. JSON에 없는 값은 미수집으로 구별하며 기존값을 지우거나 추정 생성하지 않는다.
전체 PDF 문서 본문·첨부파일 내용의 대체는 현재 구조화 필드 수집 범위에 포함하지 않는다.

### 연결은 명시 키만 사용

- 건명·수량·단가·날짜 유사도에 의한 자동 연결과 자동 재평가를 중단한다. 키가 없으면 미연결로 남긴다.
- ERP 접수번호·접수차수·접수 품목순번, 공고번호·차수·분류번호·품목순번,
  계약번호·변경차수·품목순번을 문자열로 보존한다. 번호의 선행 0을 버리지 않는다.
- 원천 참조가 가리키는 수준까지만 연결한다. 공고 본번호만 있으면 차수를 추정하지 않고,
  문서 연결이 가능해도 품목 참조가 없으면 품목끼리는 연결하지 않는다.
- 계약 5개 중 표본 C·표본 D는 품목에 접수 참조가 있지만 표본 E 분할계약
  3개는 품목의 접수번호가 비어 있다. 이 경우 헤더의 접수·공고 참조를 보존하되
  수량·단가로 품목 관계를 보충하지 않는다.
- 같은 ERP 접수에 대한 명시 참조를 공고건 묶기에 사용하고 분할계약은 각각 유지한다.
  관련공고 명시 참조도 사용하되 같은 건이라는 이유만으로 선후·대체 관계를 만들지 않는다.
- PDF의 합성 접수키와 ERP 접수키는 동일시하지 않는다. 기존 휴리스틱 링크를 명시 키 기반
  링크로 승격하지 않는다. 기존 링크·수동 확정·거절은 이번 범위 결정만으로 삭제하지 않으며,
  신규 명시 참조와 충돌하면 자동 덮어쓰기 없이 확인 대상으로 남긴다.
- 기존 런타임 연결 호출은 GUI 가져오기 결과·재평가(Bridge), CLI ingest·link·재평가에 있다.
  ERP 경로만 수정하고 기존 호출이 다시 휴리스틱 연결을 만드는 상태로 종료하지 않는다.

### 추가 금액·조건과 업체별 상세 — 최신 확정 범위

필드별 승인·제외·보류의 상세는 [매핑표](json-field-mapping.md)와
[일괄 답변 반영](json-field-questions.md#일괄-답변-반영-2026-09-27)을 따른다.

| 범위 | 원천 필드 예시 | 보존 단위 |
|---|---|---|
| 계약보증금률·금액·제출방식 | pointInfo의 ctrtGtnrt, ctrtGrnteAmt, ctwtSbmsnMthdCd | 계약 전체 값. 제외한 품목·업체 동명 필드로 확대하지 않음 |
| 접수 선급금 선고지 여부·가능 비율 | advfPinfrmYn, advfPinfrmPsbltyRat | 선고지 가능 비율. advfGivePsbltyYn/Rat는 제외 |
| 계약 선급금 선고지 여부·비율 | advcPinfrmYn, advcPinfrmPsbltyRat | 실제 고지 생성 단계. 저장명 ‘선급금 선고지 비율’ |
| 인지세 부과액 | pointInfo.cgntTxam | 물품제조계약의 부과액. 업체표 및 추가구매·공동부담 값 제외 |
| 업체 식별·현재차수 계약지분 | ctentUntyGrpNo, bzmnRegNo, ctentUntyGrpNm, ctrtSharRat, ctrtSharAmt | 업체별 행 유지. wholSharRat/Amt 미사용 |
| 공동수급 구성·역할·분담 | jintCtrtCmnMthoNm, jintSyddCmnMthoCd/Nm, ctentSeCd, jintShreSeCd 등 | 코퍼스 확보까지 미사용. 기존 포함 요구를 이번 MVP에서는 보류 |
| 부가세 포함 여부·세율 | vatIncsYn, vatRat | 업체표는 미사용. pointInfo 동명 값의 미사용 제안은 별도이며 vatAmt 유지 |

업체 상세는 `grdEtpsLst`를 기준으로 수집한다. pointInfo의 현재 선택 업체만 수집하거나
기존 단일 Counterparty에 여러 업체를 덮어쓰지 않는다. 업체표에는 계좌번호 등도 있으므로
허용 필드만 수집하고 원본 행 전체를 스냅샷에 넣지 않는다.
보유 계약 5개는 모두 업체 1행이다. 공동수급 상세는 사용자 결정으로 코퍼스 확보까지 미사용이며
공동수급 역할·구성 해석이나 이를 위한 합성 테스트를 현재 필수 종료 조건으로 삼지 않는다.
업체별 지분을 보존하는 요구는 유지한다.

### 일괄 용어 검토 후 확정 (2026-09-27)

- 최초계약일·현재차수 계약일, 품목별 수량·단가, 단위·인도조건·납품부대,
  하자기간 연·개월 병기·선고지 여부, 제시된 계약·낙찰 코드 대응, 담당자·직책,
  일정·첨부 매핑을 승인했다. 제시 단계에서 미확정으로 남긴 코드명·역할·단위는 계속 보류한다.
- 공고 종류·상태는 코드 해석보다 같은 원천에 직접 나오는 명칭을 우선한다.
- 표본 E 접수 S14는 오첨부로 인한 접수번호 오류라는 사용자 확인을 받았다.
  대응 계약과의 연결에 쓰거나 올바른 번호를 추정 생성하지 않는다. 구조 조사 자료로는 보존한다.
- 연결은 명시 키만 사용한다. 부가 순번의 의미·서로 다른 ID의 추정 별칭 등 나머지 해석은 미사용이다.
- 표본 B 납품기한 불일치는 메인·품목별 입력란 분리에서 발생한 실제 공고 입력 오류다.
  출처별 값을 유지하며, 사용자가 지정하지 않은 메인/품목 우선순위나 정정 날짜를 새로 정하지 않는다.
- 공동수급 관련은 코퍼스 확보까지 미사용, 검사·검수 해석은 보류한다.

### 코퍼스 기반 종료 기준

접수·공고 두 화면형·계약의 필드 매핑, 중복 표 제외, 전체 품목 보존, 변경·취소·재공고,
분할계약과 명시 참조 누락, 다업체 보존, 추가 금액·비율, 멱등 저장·사용자 정정값 보존을 검증한다.
필드의 미수집·명시적 빈값·0을 구별하고 기존 외부 뷰의 의미를 유지한다.
웹페이지 접근 불가를 구현의 차단 사유로 삼지 않는다. 코퍼스 변환·저장 검증과 실제 브라우저의
화면 인식·로딩·전체 행 수집 검증은 구분하여 기록한다. 테스트 신설·수정에는 write-lean-tests를 먼저 적용한다.

# 맞춤 뷰 — 서식이 읽을 필드를 한 줄에 펴 둔 뷰

2026-10-08. 상태: **지었다(3판)** — 1·2판은 「기준 문서 하나 + 열 목록」 으로 지었다(`57056b5`·`52ef0c1`·`58d6a6e`).
같은 날 받은 피드백으로 기준 고르기를 걷고 줄을 **조달 건**으로 바꾸었다(§12). 후속 탐색 변경은 아래 「현재 화면」을 따른다. 코드 이름(`UserView`·`u_`)은 그대로다.
넓히는 것: [열 관리](column-management.md)의 가공열(흐름식 v2·값 흐름 보표·SQL 탈출구). 바꾸는 것은 없다.

## 현재 화면 — 2026-10-12 후속 수정

- 자료 탐색과 구분한 「내 보기」 구획에 사용자가 저장한 이름을 표시한다. `보기 만들기`는 저장된 항목이 없어도 바로 편집을 연다.
- 이름을 자동으로 채우지 않고 빈 「보기 이름」 입력에 초점을 둔다. 제목은 사용자가 정한 이름, 이름이 없으면 「보기 만들기」다. 저장·이름 변경·지우기는 사이드바에 반영한다.
- 저장하면 설정한 열을 머리글로 둔 일반 자료 표로 전환한다. 저장된 보기를 다시 열어도 표가 기본이며, `보기 편집`으로 이름·열·식·계약 처리의 기존 편집 화면을 연다. 표는 실제 `u_이름` 조회 결과를 읽기 전용으로 보여 주고 기존 표의 검색·정렬·선택·복사를 제공한다.
- 편집 화면의 `표로 돌아가기`도 미저장 변경 확인을 거친다. 변경을 버리면 마지막 저장한 구성으로 돌아가고, 저장 후 이동하면 새 구성의 표를 보여 준다. 조회 오류에는 다시 읽기를 제공하며 열람 창에는 `보기 편집`을 표시하지 않는다.
- 편집 화면은 미리보기와 「열 목록」 두 칸으로 구성한다. 보기 이름과 열 이름을 구분하고, 식으로 만든 열의 이름은 경로 아래의 라벨과 테두리가 있는 입력에서 고친다. 새 열 편집은 이 이름 입력에 초점을 둔다.
- 계약 열이 있으면 「계약마다 한 줄」·「조달 건마다 한 줄」을 고른다. 조달 건마다 모은 계약 값은 `", "`로 이어 붙이며, 금액도 합산하지 않는다.
- 「미리보기 자료」의 이전·다음은 항상 보인다. 번호·건명 검색과 「일반」·「계약 여러 건」·「일부 자료 없음」 조건은 「다른 자료로 확인」 안에 둔다. 이 조건은 미리보기만 바꾸며 저장되는 보기나 내보내기를 거르지 않는다. 일부 자료 없음은 연결 오류를 뜻하지 않는다.
- 단계 편집 위쪽의 테두리 있는 `+ 단계 추가`는 선택한 시작 데이터 또는 단계 뒤에 삽입한다. 추가 위치 안내와 기존 ↑↓·Alt+↑↓·Delete·Enter 조작을 유지한다. 화면에서는 「원천」을 「시작 데이터」로 부르며 흐름식 문법은 유지한다.
- SQL 탭은 자동 생성된 읽기 전용 쿼리를 보여 준다. 직접 편집으로 전환하면 단계·흐름식으로 되돌릴 수 없음을 전환 전에 알린다.
- 자료 탭, 다른 보기, 새 보기로 이동할 때 기존의 미저장 변경 보호를 유지한다. 열람 창에서는 생성하지 않는다.

아래 §7의 화면 도식·문구 표는 3판의 편집 화면 설계 기록이며, 기본 표·편집 진입·탐색·이름·빈 상태는 이 수정 내용이 우선한다.

## 1. 무엇이 구렸나

**1판 이전 — 보조열이 공용 면에 붙었다.** 문서 생성기는 레코드를 평평하게 읽으므로, 공고 기준 서식이 접수·계약 값을 원하면
`연결접수.접수번호` 같은 가공열을 `v_공고` 에 붙여야 했다. 그 열은 표·엑셀·그 뷰를 읽는 모든 소비자에 퍼진다. 열 차례도
소비하는 쪽이 정할 수 없었다.

**1·2판 — 내부 모델을 사람에게 먼저 고르게 했다.** 새 뷰는 「어느 문서마다 한 장을 만듭니까? 접수·공고·계약」 에서 시작했고,
담기는 `기준` · `연결접수` · `연결계약 · 여러 건` 으로 갈렸다. 서식을 짜는 사람에게 있는 것은 `{필드}` 목록이지 기준 개체가 아니다.
「공고명·접수번호·계약번호」 를 함께 원하면 그 셋을 담는 것으로 끝나야 하고, 셋을 잇는 것은 앱이 할 일이다. 들어오는 길도
열 관리 머리의 작은 「뷰」 단추라, 열을 고치러 가지 않는 사람은 찾지 못했다.

**경계(ADR-039).** 평평하게 펴고 가공하는 일은 이쪽이 한다. 받는 쪽은 그 자리에서만 정해지는 것 — 표시형, 문장 속 조각처럼
즉시성·변동성이 강한 가공 — 만 한다.

## 2. 모델

**맞춤 뷰 = 필드 목록 + 「계약이 여럿인 건」 의 처리 하나.** 필드 하나는 `이름 = 흐름식` 이다.

```
u_공고문서   한 줄 = 조달 건 · 계약이 여럿인 건은 한 줄로 모으기
  접수번호 = 접수.접수번호
  공고번호 = 공고.입찰공고번호
  계약번호 = 계약.계약번호                         ← 모으기면 계약마다 셈해 ", " 로 잇는다
  공고명   = 공고.공고명
  대표품명 = 공고.품목 |> 꺼내기 세부품명 |> 고유 |> 줄여쓰기 1 "{앞} 외 {나머지}종"
  진행     = 공고.검토여부
```

- **줄은 조달 건이다.** `v_통합` 과 같은 사슬(접수 · 공고건 · 계약)이고, 그 규칙을 한 벌로 나눠 쓴다(§5). 한 줄에 접수·공고·계약이
  많아야 하나씩이라 **어느 필드도 「여러 건」 이 아니다** — 담으면 그대로 선다. 사람은 기준을 고르지 않는다.
- **계약이 여럿인 건(분할 낙찰·수요기관 복수)** 만 사람이 정한다. 문서를 몇 부 지을지가 걸린 일이라 앱이 짐작하지 않는다.
  - `계약마다 한 줄`(기본) — 사슬 그대로. 통합 표와 같다.
  - `한 줄로 모으기` — 사슬을 (접수, 공고건)으로 접는다. 계약 필드는 **계약마다 그 식을 셈한 뒤** 계약본번호 차례로 `", "` 로
    잇는다. 그래서 둘 사이를 오가도 깨지는 필드가 없다(꼴 검사는 언제나 계약 한 건을 본다).
- **줄 거르기는 하나뿐이다.** 담긴 흐름식 필드가 읽는 문서 종류 중 **하나도 없는** 조달 건은 줄이 서지 않는다 — 공고 필드만
  담으면 공고가 선 건만 나온다. SQL 필드는 거르기에 들지 않고, 흐름식 필드가 없으면 모든 조달 건이 선다.
  그 밖의 거르기·정렬은 넣지 않는다(§11).
- **열은 모두 흐름식이다.** 그대로 옮기는 필드는 단계가 없는 흐름식이다. 「고른 열」 꼴을 따로 두지 않는다.
- 기존 가공열은 그대로 둔다. **앱 안에서 사람이 볼 열은 면 뷰에, 서식 하나를 위한 필드는 맞춤 뷰에.**

## 3. 필드의 원천

| 원천 | 쓰는 꼴 | 저장 꼴(가공식 v2 `from`) |
|---|---|---|
| 접수·공고·계약의 열 — 기본 열·**사람 열·가공열** 모두 | `공고.공고명` | `{"kind":"linked","link":"notice","field":"공고명"}` |
| 그 문서의 품목 | `공고.품목` | `{"kind":"linked","link":"notice","items":true}` |
| 다른 맞춤 뷰 · 같은 뷰의 다른 필드 | — | 읽지 않는다 |
| SQL 탈출구 | 바깥 행을 `접수`·`공고`·`계약` 으로 부른다 | `source:"sql"`. 읽을 수 있는 것은 계약면 뷰 그대로 — 맞춤 뷰는 `SqlColumn.Readable` 에 넣지 않는다 |

- **저장 꼴은 새 원천 종류를 만들지 않는다.** `linked` 를 그대로 쓰고, 맞춤 뷰 환경에서만 글 꼴이 `연결공고.` 가 아니라
  `공고.` 이다(출력·해석 모두). `field`·`items` 원천은 맞춤 뷰에서 쓰지 않는다 — 「이 행」 이 없다.
- 단계가 행의 열을 읽는 자리(`비면`·사칙·`날짜차이`의 열, 값 하나를 견주는 조건의 `field`)가 문서의 열을 가리키면 같은
  `공고.공고명` 꼴로 읽는다. 품목 행·문서 한 행을 견주는 조건의 필드는 그대로다.
- 한 문서의 사람 열·가공열까지 읽는 것은 면 뷰를 조인하기 때문이다 — 맞춤 뷰는 면 뷰 위층이라 순환이 없다. 1·2판의
  「연결 문서의 사람 열은 읽지 않는다」 는 걷힌다.
- 환경(`FlowEnv`)은 `base` 와 `items` 가 비고 `linked` 셋이 모두 한 건(`many` 없음)이다.

## 4. 저장 꼴

스키마 **24**. `user_view` 에서 `base` 를 걷는다.

```sql
CREATE TABLE user_view (
    id         TEXT PRIMARY KEY,               -- 만들 때 뽑는 불투명 ID. 이름을 바꿔도 남는다
    name       TEXT NOT NULL UNIQUE,           -- u_ 를 뺀 이름
    definition TEXT NOT NULL,                  -- 아래 JSON
    sort_order INTEGER NOT NULL DEFAULT 0
);
```

```json
{"version":2,"contracts":"split","columns":[
  {"id":"c1…","name":"접수번호","formula":{"version":2,"source":"flow","flow":{"from":{"kind":"linked","link":"request","field":"접수번호"},"steps":[]}}},
  {"id":"c2…","name":"공고명","formula":{"version":2,"source":"flow","flow":{"from":{"kind":"linked","link":"notice","field":"공고명"},"steps":[]}}}
]}
```

- `contracts` 는 `split`(계약마다 한 줄) · `fold`(한 줄로 모으기). 열의 `formula` 는 가공식 v2 그대로이고 차례는 배열 차례다.
- **23 → 24 판올림.** 정의 v1(기준 있음)을 v2 로 옮긴다:
  - `field f` → `linked(기준) f`, `items` → `linked(기준) items`, 단계가 읽는 행의 열 → `기준` 을 붙인 이름.
  - 기준이 공고·접수이고 열이 `연결계약 |> 꺼내기 f |> 잇기 ", "` **그대로**면 `계약.f` 로 바꾸고 뷰를 `fold` 로 둔다.
    그 밖의 여러 건 열은 옮기지 않고 그대로 둔다 — 깨진 식으로 서서 사람이 고친다(조용히 다른 값을 내지 않는다).
  - 나머지 뷰는 `split`. 줄의 뜻이 「기준 문서 1건」 에서 「조달 건」 으로 바뀌는 것은 판올림 주석과 이 문서에 적는다.
- **이름.** 뷰 이름은 SQLite 에 `u_<이름>` 으로 선다. 비지 않고, 뷰끼리·한 뷰의 필드끼리 겹치지 않는다(대소문자를 가리지 않고, 40자).
- 제출본에 실린다. 취합은 `user_column` 과 같은 **정의 규칙**(`Merger`)을 탄다 — 열쇠는 `name`, 정의가 다르면 먼저 온
  제출본이 이기고 갈린 것은 충돌로 보고한다.

## 5. 뷰가 서는 꼴

```sql
CREATE VIEW "u_공고문서" AS
WITH 사슬(접수, 공고, 계약) AS (…v_통합 과 같은 글…)
SELECT
    COALESCE(접수."접수번호", '')     AS "접수번호",
    COALESCE(공고."입찰공고번호", '') AS "공고번호",
    …
FROM 사슬 s
LEFT JOIN v_접수 AS 접수 ON 접수.접수본번호 = s.접수
LEFT JOIN v_공고 AS 공고 ON 공고.공고본번호 = (그 건의 현행 공고)
LEFT JOIN v_계약 AS 계약 ON 계약.계약본번호 = s.계약
WHERE (s.접수 IS NOT NULL OR s.공고 IS NOT NULL);   -- 담긴 종류에 따라(§2 줄 거르기)
```

- **사슬은 한 벌이다.** `v_통합` 의 `WITH 사슬` 과 현행 공고 고르기를 C# 상수 하나로 꺼내 둘이 부른다. 두 벌로 적으면 한쪽만
  고쳐도 아무것도 실패하지 않고 맞춤 뷰의 줄만 통합과 어긋난다. `v_통합` 의 출력은 한 글자도 바뀌지 않는다(박제가 지킨다).
- `fold` 면 사슬을 (접수, 공고)로 접고, 계약 필드는 그 건의 계약마다 식을 셈해 계약본번호 차례로 `', '` 로 잇는 상관 부분질의다.
  공고건이 없는 사슬(계약만·접수만)은 접히지 않는다.
- 값 표기는 계약면과 같다 — 빈 값은 NULL 이 아니라 빈 문자열.
- 차례는 `Views.Definitions` 의 **치울 때 맨 앞, 지을 때 맨 끝**. 치우는 것은 저장된 목록이 아니라 `sqlite_master` 의 `u_%` 전부다.
- **깨진 필드.** 다시 지을 때 필드마다 따로 준비해 보고, 깨진 필드는 빈 글 + 까닭 주석(`BrokenMarker`)으로 선다. 다른 필드와
  다른 뷰는 그대로 선다.
- **저장.** 꼴 검사 → 컴파일 → SQL 검사 → 같은 트랜잭션에서 뷰를 지어 표본 실행. 하나라도 실패하면 되돌린다. 저장하려는 뷰의
  필드가 깨진 채 서면 거절한다.
- 접수·공고·계약의 사람 열·가공열을 지우거나 이름을 바꾸면 그 열을 읽던 필드가 영향을 받는다. 지우는 쪽 확인 문구가
  「맞춤 뷰 n곳이 이 열을 씁니다」 를 세고, 이름 바꾸기는 `linked(그 종류) 그 열` 원천과 단계 필드를 따라 고쳐 쓴다.

## 6. 계약면과 소비자

- **`v_맞춤뷰`** — 메타 뷰(2판의 `v_사용자뷰` 를 제자리에서 바꾼다, ADR-034: 옛 이름은 `Views.LegacyNames`). 필드 하나당 한 줄:
  `뷰식별자 · 뷰이름 · 열식별자 · 열이름 · 차례 · 결과타입 · 가공식`. `기준` 열은 걷는다. `Views.Names`·`ReadOnly` 에 넣고
  `Exported` 에는 넣지 않는다.
- `u_*` 는 계약면 박제에 들지 않는다(설치마다 다르다). 규약 문서의 「맞춤 뷰」 절: 이름 머리, **한 줄 = 조달 건**(통합과 같은
  사슬, 계약이 여럿인 건은 뷰마다 계약마다/모으기), 담긴 문서 종류가 하나도 없는 건은 줄이 서지 않음, 값 표기, 깨진 필드는
  빈 글, 이름이 바뀌고 사라질 수 있음.
- **hwpx-filler 는 고칠 것이 없다** — `sqlite_master` 의 뷰를 모두 시트로 늘어놓아 `u_*` 가 목록 끝에 선다.
- 엑셀 내보내기에는 싣지 않는다. 엑셀은 사람이 보는 면이고 맞춤 뷰는 소비용이다.

## 7. 화면

**누가.** 서식 하나에 필요한 필드를 **한자리에서 처음부터 끝까지 짜는** 사람이다 — 드물게 오고, 오면 길게 머문다.
옆 창이나 머릿속에 서식의 `{필드}` 목록이 있다. Operate 모드이고, 새 시각 세계는 없다.

**끝났다는 것.** 미리보기 한 건이 서식이 기대하는 필드를 이름 그대로, 찍힐 꼴 그대로 다 갖춘 상태다. 확인할 것은 둘이다 —
이 건의 값, 그리고 그 필드가 전체 건 중 몇 번 비는가.

### 7.1 들어오는 길

**사이드바의 제자리.** 「공고 연결」 아래에 `맞춤 뷰` 를 둔다(같은 `nav-link`, 건수 꼬리 없음 — 사이드바의 건수는 밀린 일이다).
누르면 작업 영역이 맞춤 뷰로 바뀐다(열 관리처럼 `main` 을 대신한다). 열 관리 머리의 「뷰」 분할 단추는 걷는다. 저장하지 않고
떠나면 지금처럼 묻는다.

### 7.2 짜임

필드 목록과 미리보기를 **한 목록**으로 합친 1·2판의 짜임은 그대로 둔다. 한 줄 = 필드 이름 · 식 요약 · 이 표본의 값 · 꼬리.

```
 맞춤 뷰
┌──────────────┬──────────────────────────────────────────────────┬──────────────────────┐
│ 뷰            │ u_ [공고문서      ]  한 줄 = 조달 건 · 1,204건     변경됨 · 저장 │
│ ▸ 공고문서 6   │ 계약이 여럿인 건 (이 자료에 3건)  [계약마다 한 줄][한 줄로 모으기]  │
│   계약서류 9   │──────────────────────────────────────────────────│ 필드          [찾기]  │
│              │ 표본 ‹ R26BK…-000 › [찾기] [계약 여럿] [연결 안 된 건] │ 접수                 │
│ + 새 맞춤 뷰   │ ⋮ 접수번호  = 접수.접수번호          R26…-000      │  ☑ 접수번호  R26…    │
│              │ ⋮ 공고번호  = 공고.입찰공고번호      R26BK…         │ 공고                 │
│              │ ⋮ 계약번호  = 계약.계약번호  ……, ……  이어 붙임 빈 값 8건│  ☑ 공고명    ……      │
│              │ ⋮ 공고명    = 공고.공고명            ……             │  ☐ 기초금액  123,4…  │
│              │ ⋮ 진행      = 공고.검토여부   (빈 값)   빈 값 41건  │  대표품명 · 품목 수   │
│              │ + 식으로 만들기                                     │ 계약                 │
└──────────────┴──────────────────────────────────────────────────┴──────────────────────┘
```

**흐름.** 「새 맞춤 뷰」 는 기준을 묻지 않고 곧장 빈 뷰(이름 `새뷰`, 겹치면 `새뷰2`…)와 열린 필드 목록으로 선다. 체크하면 끝에
줄이 선다. 가공이 필요한 줄은 Enter 로 열고, 가운데가 **지금의 가공열 편집기**(단계·흐름식·SQL, 값 흐름 보표)로 바뀐다 —
경로 「공고문서 › 계약번호」 에서 한 단계 위로 돌아온다.

**중심 순간.** 필드 목록의 모든 필드 옆에 **지금 표본의 값**이 붙는다 — 이름이 아니라 값을 보고 고른다.

### 7.3 상태와 범위

- 분량: 한 뷰에 필드 10–30개(최대 60), 뷰는 몇 개, 조달 건은 수십–수천.
- 처음(뷰 없음): 빈 상태 하나 — 무엇을 하는 자리인지와 「새 맞춤 뷰」 단추.
- **계약이 여럿인 건**: 뷰에 계약 필드가 하나라도 있을 때만 머리 아래 한 줄로 선다. 자료에 그런 건이 몇 건인지 함께 보인다
  (0건이어도 선택은 보인다 — 나중 자료를 위한 것이다). `한 줄로 모으기` 에서 계약 필드 줄에 꼬리 「이어 붙임」. 오갈 때 확인은 없다.
- 빈 값: 이 건에서 비면 warn 글자 「(빈 값)」, 전체 빈 수는 꼬리 「빈 값 41건」. 정정 칸의 blank 바탕은 쓰지 않는다.
- 깨진 식: danger 꼬리 「깨진 식」 + 그 줄 아래 까닭 한 줄. 머리의 수도 「깨진 식 n」 이다(「깨진 열」 은 쓰지 않는다).
- 이름 겹침·빈 이름: 그 줄에서 바로 오류, 저장을 막는다.
- 뷰 지우기: 이름을 보이고 그것을 쓰는 서식이 무엇을 잃는지 말한다.
- 저장 전 이동: 기존 열 관리와 같은 확인.

### 7.4 조작과 배치

- 표본 고르개: ‹ › 넘기기, 찾기(번호·건명), 가장자리 칩 「계약 여럿」 「연결 안 된 건」(접수·공고·계약 중 빠진 단계가 있는 건).
  표본 하나는 조달 건 하나이고, 보이는 번호는 입찰공고번호 → 접수번호 → 계약번호 중 처음 있는 것, 제목은 공고명 → 요청명 → 계약명.
- 필드 줄: 끌어 옮기기·Alt+↑↓ 차례, F2 이름, Delete 빼기(저장 전이라 확인 없음), Enter 열기.
- 필드 이름과 원천 열 이름이 같으면 식 요약을 흐리게 줄인다(`공고명 = 공고.공고명`).
- 필드 목록: `접수` → `공고` → `계약` 세 무리. 무리마다 그 문서의 열(기본 열 → 사람 열·가공열) 뒤에 품목 묶음(대표품명·품목 수·
  금액 합계 — 그 문서의 품목에 금액이 있을 때만)을 둔다. 검색은 이름과 값 모두. 담긴 필드는 체크된 채 남는다.
- 담을 때 이름이 겹치면 문서 종류 이름을 앞에 붙인다(공고와 계약의 `수요기관` → 둘째는 `계약수요기관`).
- 좁은 창(60rem 이하): 뷰 목록은 머리의 고르개로, 필드 목록은 「필드 추가」 서랍으로.
- 식은 고정폭 `--code`, 값은 본문 글꼴과 tabular-nums.

### 7.6 넣지 않는 것 · 다음 후보

- 넣지 않는 것: 표 탭에 세우기, 식 없는 「고른 열」 종류(연산자 문법이 갈라진다), 기준 고르기.
- **다음 후보 — 서식 필드 목록에서 시작:** hwpx 서식의 `{필드}` 이름 목록을 붙여 넣으면 같은 이름의 필드로 미리 세우고, 못 찾은
  것은 「식 없음」 빈 줄로 남긴다. 필드 목록이 무리 셋을 다 보므로 이름 맞추기가 1·2판보다 쉽다.

## 8. 다리

| 부름 | 하는 일 |
|---|---|

**시험.** 저장 왕복과 식별자 유지 · 필드 차례가 뷰 차례와 같음 · 한 뷰에서 접수·공고·계약의 필드(사람 열·가공열 포함)를 함께 읽음 ·
줄이 `v_통합` 과 같은 사슬(split 의 건 수 = 담긴 종류로 거른 `v_통합` 의 줄 수) · fold 에서 계약 여럿인 건이 한 줄이고 계약 필드가
계약본번호 차례로 `', '` 이음 · 계약만·접수만인 사슬이 fold 에서 접히지 않음 · 담긴 종류가 없는 건은 줄이 서지 않음 · `v_통합`
박제가 그대로 · 23 → 24 판올림(field → 기준 linked, 여러 건 잇기 → fold, 그 밖은 깨진 식) · 깨진 필드가 빈 글로 서고 다른 필드·뷰가
섬 · 지운·이름 바꾼 뷰가 `sqlite_master` 에 남지 않음 · 빈 값이 NULL 이 아님 · 취합 충돌 보고 · `v_맞춤뷰` 박제와 `v_사용자뷰` 치움 ·
맞춤 뷰가 SQL 열의 읽을 거리에 들지 않음 · 사람 열 이름 바꾸기가 `linked` 원천을 따라 고침.

## 11. 넣지 않는 것

- 줄 거르기·정렬(§2 의 하나 말고) — 조건 하나로 문서 건수가 오류 없이 줄어든다. 필요가 실제로 서면 따로 정한다.
- 품목·차수 단위의 줄 — 줄은 조달 건 하나뿐이다.
- 필드끼리 참조, 다른 맞춤 뷰 읽기.
- 엑셀 내보내기·소비자 자동 연결.

## 12. 지은 것

- 1판 `57056b5`(화면 시안) · 2판 `52ef0c1`(코어) · `58d6a6e`(다리·화면) — 기준 문서 하나 + 열 목록, 열 관리 머리의 「뷰」.
  미리보기는 savepoint 가 아니라 읽기 전용 연결이고, `v_사용자뷰` 는 뷰를 다 지은 끝에 지었다(결과타입이 지어 본 뒤에야 정해진다).
  이 둘은 3판에서도 그대로다.
- 3판(설계 2026-10-08): 피드백 셋 — 열 관리를 거쳐 들어오는 길이 어색하다 · 기준 고르기는 내부 모델의 투영이다 · 문구가 흐리다.
- 3판 지은 것: `6066eb3`(코어와 다리 — 사슬 한 벌·스키마 24·판올림·v_맞춤뷰·base 인자 걷기) · `694d3c5`(화면 — 사이드바 자리·
  필드 목록 세 무리·계약 처리 한 줄·§7.5 문구·목업 다리) · 이 문서를 고친 커밋(README·DESIGN·ADR 개정 줄).
  §10 의 「코어와 다리를 나눠 커밋한다」 와 달리 **한 커밋**이다 — 코어의 서명이 바뀌어 다리를 따로 두면 앱이 빌드되지 않는다.
  규약 「맞춤 뷰」 절도 문서 커밋이 아니라 코어 커밋에 들었다(뷰 이름을 바꾸는 커밋에서 규약을 고친다, CLAUDE.md).

  이 문서와 다르게, 또는 문서가 정하지 않은 자리에서 이렇게 섰다:
  - **모으기의 계약 하나.** 계약이 하나뿐인 건은 접어도 그 계약을 들고 간다 — 열쇠가 계약마다 한 줄과 같고 계약 필드를 그대로
    셈한다. 계약이 둘 이상일 때만 계약 자리가 비고 계약 필드가 상관 부분질의로 잇는다(빈 값도 그 자리에 낀다).
  - **SQL 필드.** 거르기에도, 계약마다 셈하기에도 들지 않는다 — 글이라 무엇을 읽는지 알 수 없다. 그래서 모으기에서 계약이 둘 이상인
    건의 SQL 필드는 별칭 `계약` 이 NULL 이다. 판올림은 SQL 필드의 글을 고치지 않는다(`현재` 가 없어 깨진 식으로 선다).
  - **거르기의 「있다」.** 문서가 있는지는 사슬의 자리(접수·공고건·계약 본번호)로 본다. 문서를 읽지 않는 흐름식(글자 원천뿐)만
    담으면 읽는 종류가 없어 거르지 않는다 — 「하나도 없는」 이 모든 건을 지우지 않게.
  - **사람 열 이름 바꾸기·지우기 셈**은 `linked(종류) 열` 원천과 단계의 `공고.열`(값을 견주는 조건 마디 포함)에 더해, 원천이
    그 문서 한 행일 때 첫 단계가 짚는 필드(`꺼내기`·`만약`·`서식`)도 따라간다. 읽는 문서 종류(줄 거르기·모으기)도 조건 마디를 센다.
  - **보표.** 모은 건을 고르면 단계는 계약본번호가 가장 앞선 계약 한 건을 보이고, 「열에 찍힐 값」 은 뷰가 낼 이어 붙인 값이다.
    맞춤 뷰의 SQL 필드 검사는 다리 부름을 더하지 않고 그 보표(`traceUserViewColumn`)로 한다. 보표 표본 열쇠는 「|」 가 든
    조달 건 열쇠라 화면이 JSON 으로 싸서 넘긴다.
  - **제목의 셋째**는 `계약건명` 이다(면 뷰 열 이름 그대로 — §7.4 의 「계약명」).
  - **빠른 시작**(편집기)은 맞춤 뷰에서 문서 셋과 `글자` 단추만 둔다. 품목 묶음은 필드 목록의 문서마다 있다.
  - hwpx-filler 의 시트 목록에 `u_*` 가 서는지는 3판에서 다시 보지 않았다(2판에서 본 것 그대로 — 뷰 이름 머리와 꼴은 같다).

## 13. 서식용 예시 보기

hwpx-filler 서식 셋 — 입찰공고 · 계약방법 결정 및 구매추진 안내 · 낙찰자 선정 및 계약체결 안내 — 을 **한 보기로** 채우는 맞춤 뷰
`서식용 예시`(`u_서식용 예시`) 다. 필드 이름은 서식의 `{필드}` 자리 이름 그대로다(띄어쓰기까지). 세 서식이 같은 보기를 읽고 각자
자기 자리만 가져간다.

- **exe 에 실린 보기 구성 파일 하나**다(`src/Pclm.Core/Storage/Presets/builtin-views.json`, 「보기 구성 JSON 파일」 꼴 판 1).
  배포물 옆에 따로 놓이는 파일은 없다.
- **처음부터 들어 있다.** 빈 작업자료를 짓는 길(`PclmFile.Create`, 역할 `work`)이 심는다. 이미 있던 작업자료는 스키마 26 으로
  올릴 때 **한 번** 받는다(`Schema.ExampleViewVersion`) — 같은 이름의 보기가 이미 있으면 그것을 두고 넘어간다. 판이 「심었다」 는
  표지라 사람이 지우면 다시 열어도 되살아나지 않는다. 작업자료가 아닌 파일(제출본·취합본·백업·옮겨진 옛 자료)에는 심지 않는다 —
  읽기로 연 남의 옛 판 파일을 사본 위에서 올려도 그 역할이 `work` 가 아니면 그대로다. 취합본의 맞춤 뷰는 제출본에서만 온다.
- **스키마 27 에서 한 번 고쳐 받는다**(`Schema.ExampleViewUpgradeVersion`). 스키마 26 이 심은 예시는 번호로 시작해 줄을 알아보기
  어려웠다. 작업자료(역할 `work`)에 `서식용 예시` 가 있고 저장된 정의가 스키마 26 이 심은 그것과 **같은 JSON**(키 순서는 보지 않는다)
  이면 — 사람이 손대지 않았으면 — 지금 구성으로 갈아 끼운다. 고쳤거나 지웠거나 이름을 바꾼 보기는 그대로다. 견줄 v26 의 정의는
  얼려 둔 사본(`Presets/example-view-v26.json`)이고, 스키마 26 단계는 여전히 그것을 심는다 — v25 에서 오는 파일은 둘을 다 밟아
  지금 구성이 된다.
- **다시 받기.** 설정 → 보기 구성의 「예시 보기 다시 추가…」 가 다리 `builtinViewPackage()` 로 그 구성을 꺼내 「구성 파일 가져오기…」
  와 같은 미리보기 → 「확인한 구성 추가하기」 를 탄다. 같은 이름의 보기가 있으면 ` (복사본)` 으로 선다. 열람 중에는 막힌다.
  들어온 뒤에는 여느 맞춤 뷰라 고치고 지울 수 있다.
- 맞춤 열에 기대지 않고(`columns: []`) SQL 필드가 없다 — 계약면의 기본 열만 읽으므로 빈 작업자료에서도 깨진 필드 없이 선다.
- 줄은 `split`(계약마다 한 줄)이다 — 계약체결안내가 계약마다 한 장이다. 계약이 여럿인 건은 공고·접수 자리가 계약 수만큼 같은 값으로
  되풀이되고, 계약이 없는 건(공고만·접수만)은 한 줄이다.

**계약 먼저, 없으면 공고.** 계약과 공고에 모두 있는 자리(수요기관·세부품명·수량·단위·납품기한)는 `계약.x |> 비면 공고.y` 다 —
계약 값이 있으면 그것이고, 계약 값이 비었거나 그 줄에 계약이 없으면 공고 값이다. 그래서 계약 전의 입찰공고·구매추진안내는 공고
값을, 계약체결안내는 계약 값을 읽는다. 두 값이 다른지는 보지 않는다(ADR-016).

**사람이 알아보는 것이 먼저다.** 앞의 일곱 필드는 `건명 · 단계 · 수요기관 · 대표계약업체 · 조달요구번호 · 입찰공고번호 ·
계약번호` 다 — 번호보다 이름과 진행이 먼저 보여야 줄을 알아본다. 나머지는 서식 자리 차례(게시일 → … → 계약보증금)다.

- **건명은 알아보기 전용이다.** `공고.공고명 |> 비면 접수.요청명 |> 비면 계약.계약건명` — 줄마다 문서가 하나는 있으므로 비지
  않는다. 서식은 건명을 읽지 않는다. **`공고명` 필드는 그대로 공고의 것**이라 공고가 없거나 공고명이 비면 빈 글이다 — 거기에
  물러섬을 넣으면 받는 쪽의 빈 값 경고가 공고 없는 줄에서 울지 않는다.
- **단계**는 그 줄에 계약번호가 있으면 `계약`, 없고 입찰공고번호가 있으면 `공고`, 둘 다 없으면 `접수` 다. `경우` 한 단계로,
  첫 갈래는 지금 값(계약번호)을, 둘째 갈래는 바깥의 열(`공고.입찰공고번호`)을 견준다:
  `계약.계약번호 |> 경우 안비어있음 → "계약", 공고.입찰공고번호 안비어있음 → "공고", 그외 "접수"`.
- **계약번호**는 `계약.계약번호` — 계약이 여럿인 건은 줄마다 그 계약의 번호라 서식 한 장이 어느 계약의 것인지 갈린다.

| 필드 | 식 |
|---|---|
| 건명 | `공고.공고명 \|> 비면 접수.요청명 \|> 비면 계약.계약건명` |
| 단계 | 위 |
| 계약번호 | `계약.계약번호` |
| 조달요구번호 | `접수.조달요구번호` |
| 입찰공고번호 · 공고명 · 세부품명번호 · 계약방법 · 사업예산 · 추정가격 · 분할납품 · 인도조건 · 하자담보기간 · 입찰개시일시 · 입찰마감일시 · 개찰일시 · 등록마감일시 · 담당부서 · 담당자 | `공고.` 같은 이름 |
| 게시일 | `공고.게시일시 \|> 앞부분 " "` |
| 수요기관 · 수량 · 단위 · 납품기한 | `계약.` 같은 이름 `\|> 비면 공고.` 같은 이름 |
| 세부품명 | `계약.품명 \|> 비면 공고.세부품명` |
| 입찰방법 · 낙찰자결정방법 | `공고.입찰방식` · `공고.낙찰방법` |
| 계약담당자 | `공고.공고담당자 \|> 앞부분 "(" \|> 다듬기` |
| 계약담당 전화번호 | `공고.공고담당자 \|> 뒷부분 "☎" \|> 앞부분 ")" \|> 다듬기` |
| 담당자 전화번호 | `공고.담당자전화` |
| 대표계약업체 · 계약금액 · 계약보증금 | `계약.계약상대자` · `계약.계약금액` · `계약.계약보증금(원)` |

필드 차례는 위 표가 아니라 구성 파일의 차례다(건명 → 단계 → … → 계약번호 → 게시일 → … → 계약보증금).

공고담당자는 `이름 ( ☎ 전화 )` 꼴로 담긴다. 그 꼴이 아니면 계약담당자는 담긴 글 전체, 계약담당 전화번호는 빈 글이 된다 —
검산하지 않는다(ADR-016).

**짝이 없는 서식 자리.** 계약면에 원천이 없어 필드로 세우지 않았다. 서식에서 비어 남는다 — 필요하면 사람 열을 세워 보기에 더한다.

| 서식 | 자리 |
|---|---|
| 입찰공고 | 계약담당 팩스번호 |
| 구매추진안내 | 군품명 |
| 계약체결안내 | 계약보증금납부기한 |
